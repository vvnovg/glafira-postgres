# Queries

The [[ui:diag.tools.queries]] tool sits in the [[ui:sidebar.diagnostics]] group after replication slots. It shows which queries load the node according to the `pg_stat_statements` extension, opens a card for any query with its history and plan, and gives a console for EXPLAIN of arbitrary SQL. The app reads statistics and builds plans; the only thing that changes data is the [plan with execution](queries.md#analyze) of a writing query, and even that runs in a transaction that is always rolled back. The app does not run recommended commands, and the [hypothesis check](queries.md#recommendations) creates a virtual index only in the memory of its own session.

What the server needs: the `pg_stat_statements` extension in `shared_preload_libraries` (the checklist item “pg_stat_statements is loaded”), created in the connection's database (the item “pg_stat_statements extension”); a role with `pg_monitor` (otherwise only the role's own queries are visible); for plans, the right to read the application's tables: `pg_read_all_data` on PostgreSQL 14 and newer (the checklist item “Reading application tables (EXPLAIN)”) or `SELECT` on the tables of the query — on 13 only the latter. `pg_read_all_data` opens reading of all data, so granting it is the administrator's decision; `SELECT` on the tables you need is enough for EXPLAIN, but the checklist item stays a warning. Planning columns are filled only with `pg_stat_statements.track_planning = on` (the item “pg_stat_statements.track_planning”). The optional extensions `hypopg`, `pg_stat_kcache` and `pg_wait_sampling` add index hypothesis checks, CPU and disk reads per query and the exact waits of a query: see [Extensions](queries.md#extensions).

## Top queries {#top}

The table has a row per query (identical queries with different literals are already merged by the extension: the text has `$1`, `$2` instead of values). Click a column header to sort: total time (default), mean, calls, rows per call, hit %, reads, temp, WAL, I/O, planning, JIT, stddev, max and CPU (with `pg_stat_kcache`). Hit % sorts ascending so that the worst come first; the other columns sort descending. A grayed-out sort is unavailable: max and stddev exist only in “since reset” mode, JIT needs pg_stat_statements 1.10 (PostgreSQL 15), CPU needs `pg_stat_kcache`. Filters: database, [[ui:diag.queries.toplevelOnly]] (without statements nested in functions; the checkbox is always visible, but `pg_stat_statements` 1.8 has no `toplevel` column, and there it changes nothing), the number of rows (50, 100 or 200) and the [[ui:diag.queries.search]] field: a part of the query text, case-insensitive. The search runs on the server over the query texts in `pg_stat_statements` and works in both modes; the input is applied after a short delay (about 0.3 s), an empty field removes the filter, and if nothing is found the table says “Nothing found for “…””. The search only narrows the rows: the totals and shares are still computed over the whole load. While the search string and the set of queries in `pg_stat_statements` stay the same, a refresh does not re-read the texts on the server. In the window, a query that has already left `pg_stat_statements` (a reset, an eviction) is found only if Glafira has read its text before. The [[ui:diag.queries.openConsole]] button opens the [console](queries.md#console).

By default the tool reads the leader (“follow the leader”, like the other diagnostics tabs). When the leader changes, the report and the collection move to the new one, and the window of the new node starts at its first tick; there is no “Node changed…” line here, unlike in other tabs. A node chosen in the header stays pinned.

Mode ([[ui:diag.queries.mode]]):

- [[ui:diag.queries.modes.sinceReset]] — statistics accumulated since the last `pg_stat_statements_reset()`. Available at once, refreshed on the header interval.
- Last 5, 15 or 60 minutes — what happened recently. While the tab is open the app reads the statistics once a minute (without query texts) and remembers the growth; the window is computed from that growth and hardly touches the server (texts are requested by the keys of the visible rows). The badge next to the mode shows how many minutes have been collected (“3 of 5 min collected”): right after opening, the window is empty and the badge says “Waiting for the first tick of the sampler…” until a minute has passed. The badge counts the minutes actually collected (ticks with growth), not the time between the first and the last tick: a gap during which collection was stopped (the tab was closed) is not counted, so after a pause the badge shows fewer minutes than have passed on the clock. The history is kept for an hour while the connection is open. Collection runs while the Queries tab or a query card of the same node is open: closing the tab stops it only if no cards of that node remain, and reopening continues with a gap.
- [[ui:diag.queries.modes.between]] — the growth between two saved statistics snapshots; it is turned on from the snapshots panel, see [Snapshots](queries.md#snapshots).

At the bottom are the extension version and the last statistics reset (`pg_stat_statements` 1.8 does not provide it, and the footer says “reset time unavailable”); if `track_planning` is off, it says so there too, and the “Planning” column of the table and the metric of the same name in the card show “—”. If the extension evicted rare queries (`dealloc`), the “The top is incomplete” finding suggests raising `pg_stat_statements.max`.

Glafira's own queries — all of them except the text you typed in the EXPLAIN console: the topology poll, the samplers and the diagnostics reports, as well as one-off ones (the readiness checklist, the catalog and the tree, object tabs, the card, snapshots, hypothesis checks and the service statements of the EXPLAIN transaction) — begin with the comment `/* glafira */`, by which the app recognizes them. The console wrappers `EXPLAIN (FORMAT JSON, VERBOSE, SETTINGS…)` and `EXPLAIN (ANALYZE, BUFFERS, WAL, …)` carry no mark (it would shift the error position in the text) but are recognized too: by the exact prefix of the options Glafira builds. In the table they carry the [[ui:diag.queries.own]] mark; they do not get findings and are left out of the totals the findings are computed from: otherwise the topology poll would give a false N+1 and lower the calls share of the real queries. The “Share” column of every row, own ones included, is computed over the whole load. A query is recognized by its text — by the mark or, for rows recorded by versions without the mark (until the statistics are reset), by the text of the node poll queries. The app reads the texts of the top rows itself, with one query per refresh, and keeps them in memory for the node, so the “Glafira” mark appears at once, without an open window or sampler, and own rows never get findings; a row whose text can no longer be found in `pg_stat_statements` may lack the mark. Own rows are not hidden from the table: they are visible and clickable as well.

Findings of the top (the block above the table): N+1, a tiny query with a large share of all calls (from 20 %, mean up to 1 ms, at least 1000 calls); unstable time (stddev much larger than the mean; only in the “since reset” mode); low cache hit; temp files per call; planning longer than execution (only with `track_planning` on). Findings about a particular query show the beginning of the query text under the title (monospace, up to 90 characters; the full text is in the tooltip) and have the [[ui:diag.findings.openQuery]] button; the “The top is incomplete” finding has neither. If the query is no longer in `pg_stat_statements` (reset or eviction), it cannot be opened from the row, and the tooltip of the inactive button says why.

## Query card {#card}

Clicking the query text in a table row (or the [[ui:diag.findings.openQuery]] button of a finding) opens the query tab. A query in the card is one `queryid` in one database: rows per role and per top-level flag are summed, the breakdown is a separate table (it appears when there is more than one row). The node selector in the header opens the same query on another node in a separate tab, so the primary and a replica can be compared side by side (identifiers match on physical replicas). If the node is no longer in the topology, the card offers to open the query on another node. If the query is no longer in `pg_stat_statements` (it was evicted or the statistics were reset), the card says [[ui:diag.query.gone]]: there is no text, metrics or history, and the running instances and the waits remain.

The card header has the database and the `queryid`, the node selector and the [[ui:diag.header.refresh]] button; in a narrow window “database · queryid” shrinks with “…” (the full text is in the tooltip) while [[ui:diag.header.refresh]] stays visible. The same goes for the headers of the other diagnostics tools: long captions and node lists are no wider than the row. The tab title is the beginning of the query text.

The [[ui:diag.query.overview]] sub-tab: the query text (a text longer than 16 384 characters is truncated, and this is marked), the [[ui:diag.query.sinceReset]] and [[ui:diag.query.lastHour]] metrics side by side (the second column is the growth over the time the sampler ran, an hour at most; the card shows no coverage, and where the query has no growth in the window there are dashes), findings about this query (the share of its calls is computed from all calls on the server, over all databases and nesting levels, so it may differ from the share in the top), two history sparklines (calls per minute and mean time) by sampler ticks — gaps in which collection was stopped break the line — the breakdown by role, instances running right now from `pg_stat_activity` (PostgreSQL 14 and newer, on 13 the card says “Running instances (query_id): PostgreSQL 14+” and has no list; active queries only, without parallel workers; a button opens [[ui:diag.tools.sessions]]), the query's waits from the samples of the wait profile (only the [[ui:diag.tools.waits]] tab collects them; until it has been opened, the hint “Open the wait profile…” stands instead of the table; when the profile is open but the query did not get into the samples, it says that this query was not seen in the “Sessions” samples for the covered period (and, if collection is stopped, suggests opening the profile again); while there are no samples yet, it says so; the caption above the table names the source and its coverage) or, when `pg_wait_sampling` is installed, from its profile (see [Extensions](queries.md#extensions)), the query's CPU and disk when `pg_stat_kcache` is installed, the query's tables, which appear after the first plan; until then a hint stands in their place; the [[ui:diag.query.getPlan]] button is absent from the row when there is no query text or it is truncated. Under the text there is one row of buttons: [[ui:diag.query.getPlan]] (opens the “Plan” sub-tab and builds a trial plan at once), [[ui:diag.query.openConsole]] (the console receives the node, the database and the query text), [[ui:diag.query.copyQuery]] (the normalized text) and [[ui:diag.query.copyLlm]].

[[ui:diag.query.copyLlm]] puts markdown on the clipboard: server and extension versions, node and database, the query text, statistics, the plan as text and the DDL of the tables (at most ten tables and 64 KB; the DDL already contains the `CREATE INDEX` of the indexes, so every index appears in the export once, and the indexes behind constraints are described by the constraints themselves). The text is the normalized one, without parameter values, but the plan may contain the values typed into the parameter form or the literals of a chosen running instance: check the markdown before pasting it into a model. The plan is the last one obtained in this tab on its node: a plan obtained on a replica (this is where the plan with execution of the read tier runs when the tab is open on the leader and a replica is available) is not taken. If there is no suitable plan, the app builds a probe plan without execution (before PostgreSQL 16 this is possible only for a query without `$N`). A truncated text is not planned. The statistics are up to two tables, “Since reset” and “Window up to 60 min (while the sampler ran)”; the “Planning” row is present only if planning was counted (`track_planning`). If the plan or the DDL could not be obtained, the markdown keeps the text and the statistics, and a “Notes” section appears at the end. This is data for a question to a model; there are no prompts in it.

## Plan and EXPLAIN {#plan}

The [[ui:diag.query.plan]] sub-tab builds the plan on the selected node. The text: normalized from `pg_stat_statements` or the text of a running instance with its literals ([[ui:diag.query.source]]; the text of a running instance cannot be chosen if it is truncated, and when the normalized text is truncated, longer than 16 384 characters, its item is grayed out and marked “truncated” — choose an instance with the full text). For the normalized text the parameters `$1…$N` must be given in fields (an empty field is NULL). The number of parameters is the largest `$N` outside strings, comments, quoted identifiers and dollar-quoted bodies: a `$5` inside a literal does not count. On PostgreSQL 16 and newer `GENERIC_PLAN` is the default for the [[ui:diag.plan.run.plan]] button, a plan without values; while the checkbox is on, the button is called [[ui:diag.plan.run.planGeneric]]. If an instance of the query is running while the normalized text is selected, a line “An instance is running (PID …)” with the [[ui:diag.query.runningUse]] link stands above the parameters: it switches the source to that instance. The fields stay on the screen: the [plan with execution](queries.md#analyze) always needs values (`GENERIC_PLAN` cannot be combined with ANALYZE) and takes them from the fields whatever the checkbox says. With more than 100 parameters there are no fields, only a message: runs that need values are unavailable, while [[ui:diag.plan.run.plan]] with `GENERIC_PLAN` (PostgreSQL 16 and newer) works. The execution timeout is 5 seconds to 10 minutes, 30 seconds by default; the probe plan is built for at most 15 seconds. `search_path` can be set in the collapsed field if needed (the server default of the role otherwise).

[[ui:diag.plan.run.plan]] is `EXPLAIN (FORMAT JSON, VERBOSE, SETTINGS[, GENERIC_PLAN])`: the query is not executed. [[ui:diag.plan.run.analyze]] is `EXPLAIN (ANALYZE, BUFFERS, WAL, VERBOSE, SETTINGS, FORMAT JSON)`: the query really runs; see the next section.

Errors and refusals (writing unavailable on a read-only connection or on a replica, more than 100 parameters, a server error, the time limit) are shown next to the buttons as a red banner, and the tree of the previous run stays hidden until the next successful run (editing the text or the values does not bring it back; picking it in the [[ui:diag.plan.history.title]] list does); limits and warnings of the summary (for example, that the query writes) are in a warning color, and neutral notes such as “Generic plan” are plain text. Two statements in the text are not accepted: EXPLAIN is built for exactly one. A parse error is reported with the server's own text, and its place in the query (“Error at line 1, column 8”) is marked in the text. If the role lacks privileges, the message depends on the statement: for `SELECT` it is the right to read the tables (`pg_read_all_data` or `SELECT`), for `INSERT`, `UPDATE`, `DELETE`, `MERGE` and `CREATE …` it is the right to write: PostgreSQL checks it even for EXPLAIN without execution.

The plan tree: indented rows with expandable nodes; inclusive and own time (without children) with a share bar; rows “estimate → actual” with an estimate error of tenfold or more highlighted as “×N” (orange from ×10, red from ×100 and for an infinite error); loops; buffers (hits / reads); marks: disk, lossy, heap fetches, fewer workers than planned, parallel, never executed. Nodes that account for at least 10% of the total (own time, without children) — at most three, the longest first — are highlighted with a colored row background and a “hot” mark in the marks column; in a fast plan with the time spread thin there may be no hot nodes. The “×N” estimate error is not shown for nodes that a `Limit` stopped early (fewer actual rows than estimated), nor for an actual 0 with a modest estimate (under 1000 rows). The time of nodes under `Gather` is converted to wall-clock time (the server reports the mean per process). When the plan has no times (a plain EXPLAIN or ANALYZE with `TIMING OFF`), the cost or a dash is shown instead, and the nodes with a share of own cost of at least 10% count as hot. Clicking a node opens a panel with all its fields. Above the tree is the summary: the node (if the plan was obtained on a node other than the tab's), planning, execution, tier, round trip (from the call to the server to the answer), JIT (the server reports JIT times only for a plan with execution and `TIMING` on; without them the summary says “JIT: N functions” and the plan text has no `Timing:` line), triggers, settings; the summary begins with the mode of the run (“Plan” or “Plan with execution”); the [[ui:diag.plan.copyJson]] and [[ui:diag.plan.copyText]] buttons (psql-style text; if the query has non-default settings, a `Settings:` line follows the tree). Past runs of the tab (up to ten) are in the [[ui:diag.plan.history.title]] list; a run on another node is marked there with “on” and the node name.

## Plan with execution {#analyze}

The [[ui:diag.plan.run.analyze]] button runs the query and shows the actual time, rows, loops and buffers. There are two execution tiers: the app first builds a plain plan and checks whether the query writes.

- **Read** (no `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE … AS`): runs without confirmation in a read-only transaction (`BEGIN READ ONLY`) that is rolled back. If the query tries to write anyway (a function with a side effect, a trigger), the server refuses and the app offers to run it as a write — the [[ui:diag.plan.run.asWrite]] button. When the tab is open on the leader and the topology has an available replica, the read tier runs on the replica by default, so that the primary is not loaded: after the probe plan the [[ui:diag.plan.run.analyzeOn]] field appears next to the buttons, where the leader can be put back (the plan on a replica may differ). The field exists only in the card; in the console the read tier runs on the console's node. The read tier is protected by a `READ ONLY` transaction: it does not stop non-transactional administrative functions — for example `pg_terminate_backend`, `pg_cancel_backend`, `pg_stat_reset*`, `pg_reload_conf`, `pg_drop_replication_slot`, `pg_switch_wal`, `pg_create_restore_point`, `pg_promote` — or external calls (`dblink`, `http`). So a call of such a function in the probe plan moves the statement into the write tier: the confirmation window names the reason, and the run is journaled. Calls inside the body of another function or a trigger are not visible in the plan, and this check does not protect against them.
- **Write**: needs actions enabled on the connection (unavailable on read-only); a dialog with the list of tables and a warning is shown in every environment, and on prod it also asks for the connection name. Then the query runs in a transaction and is rolled back. It runs as the connection's role, so that role needs the right to write to the tables of the query (for this set up a profile under the application's role instead of using the shared diagnostics role — see the administrator guide). Rows change and are rolled back: rollback also undoes the changes made by triggers, and `NOTIFY` is not delivered. It does not undo sequence advances, external calls (`dblink`, `http`) or non-transactional functions, including those called from triggers; the query holds locks while it runs. Such an execution is recorded in the [actions journal](diagnostics.md#journal) as “EXPLAIN ANALYZE (write)”; unlike other actions, a failure to write the journal is silent here. A write cannot run on a replica: choose the primary.

When the timeout expires the server cancels the execution and nothing changes (the message “The plan was not produced in time”); choose a longer timeout and repeat.

## EXPLAIN console {#console}

[[ui:diag.explain.title]] opens from the diagnostics group, from the Queries tool and from the card. There is one console per connection: opening it from the card puts the node, the database and the query text into it, while opening it from the tree keeps what was typed. Pick a node and a database, enter one SQL statement and build plans as in the card (without the replica choice for the plan with execution that the card has); `$1…$N` in the text become parameter fields (up to 100, as in the card). The console has its own [[ui:diag.query.copyLlm]] button (in one row with [[ui:diag.plan.copyJson]] and [[ui:diag.plan.copyText]]): it takes the plan of the last run while the query, the node and the database have not changed. The console puts the query text into the markdown as typed, literals included, and they may hold users' data: check it before pasting it into a model. The second sub-tab is [[ui:diag.explain.sourcePaste]]: paste a plan obtained outside Glafira (from psql, auto_explain or a colleague) and press [[ui:diag.explain.parse]]: the tree is built without the server. The format is detected automatically: `EXPLAIN (FORMAT JSON)` or a plain text `EXPLAIN` (including `ANALYZE`, `BUFFERS`, `VERBOSE`, `SETTINGS`, `WAL` and `TIMING OFF`). The psql framing — the `QUERY PLAN` header, the separator, the `(N rows)` line, the `+` continuation marks — is fine; an auto_explain record from the server log (the `LOG:  duration: … plan:` and `Query Text:` lines) is accepted too. Text that is not understood gives an error with the line number; node lines the app did not recognize stay in the node panel as they are. A psql table with a frame (`\pset border 2`) and a copy from a graphical client (pgAdmin, DBeaver) with quotes around the lines are accepted too; psql Unicode lines (`\pset linestyle unicode`) and expanded output (`\x`) are not supported.

## Plan recommendations {#recommendations}

Below the summary of a plan built in the card or the console there is the [[ui:recommend.title]] block with the number of pieces of advice (a plan from the [[ui:diag.explain.sourcePaste]] sub-tab has it too: the rules only read the plan itself, so there is no [[ui:recommend.hypo.check]] button, which needs a server; for a plan without execution the block suggests pasting `EXPLAIN ANALYZE`). Recommendations are ordered by severity. Each has a severity, a title with numbers, evidence from the plan node (rows, filtered rows, loops, volume, time), a ready command with a [[ui:recommend.copyCommand]] button, the expected effect and risks, a [[ui:recommend.hypo.check]] button (on recommendations with an index, see below) and a [[ui:recommend.showNode]] button. The app does not run the commands, and each one says so: copy them and run them yourself once you are sure the advice fits. [[ui:recommend.showNode]] selects the first node of the recommendation and marks every node related to it (the sort and the `Limit`, the `Nested Loop` and its inner scan, all partitions of a grouped recommendation) with a bar and the “recommendation” badge, expands collapsed parents and scrolls the tree to the node; a click on any tree row clears the marks. When there is nothing to advise, the block says [[ui:recommend.none]].

Rules:

- **Seq Scan with heavy filtering** (at least 10,000 rows read over all loops, ten times more filtered out than returned) — an index on the filter columns. Scans of partitions under one `Append` are merged into one recommendation: the title gives the number of partitions, the evidence the first three by name and “… and N more”, the full list sits in the expandable “All partitions (N)”, and the command has a `CREATE INDEX` line per partition in name order. Numbers in names compare by value: `events_2` comes before `events_10`. For a Bitmap Heap Scan the evidence names the index of the child Bitmap Index Scan, and for an estimate error across the index conditions and the filter together, the `CREATE STATISTICS` advice takes the related columns from both.
- **Index Scan or Bitmap Heap Scan with a filter** (the filter removed at least 1000 rows and ten times more than it returned) — a composite index: the index condition columns, then the filter columns, equalities before ranges.
- **Nested Loop over a Seq Scan** (the inner scan ran 1000 times or more) — an index on the join key.
- **Row estimate error** of ten times or more with the estimate or the actual count at 1000 rows or more — `ANALYZE`, `ALTER TABLE … ALTER COLUMN … SET STATISTICS 1000` for the condition columns and, with two or more columns, `CREATE STATISTICS` named `<table>_<columns>_stat` in the table's schema (PostgreSQL before 16 rejects the command without a name). The rule does not report an overestimate under `Limit`: the node simply stopped early.
- **Sort or hash on disk** — `SET work_mem` (one and a half times the volume on disk, at most 1 GB) for the session or the role, and for a sort by plain table columns also an index on the sort key (when the key is an expression such as `sum(total)`, no index advice is given). A lossy bitmap also calls for `work_mem`, but the volume is not computed: the command is the `SET work_mem = '<work_mem>';` template.
- **Sorting a whole table for `LIMIT`** (the sort input has a hundred times more rows than the `Limit` returns, per execution of the `Limit`; a `Gather Merge` between them is allowed) — an index on the sort key. The rule works without execution too, by estimates, and stays silent when the sort input is a join or an aggregate rather than a table scan.
- **Index Only Scan with heap fetches** (at least 1000 and at least 10 % of the rows) — `VACUUM`: the visibility map is stale.
- **`Append` over all partitions** (ten or more children without `Subplans Removed`) — partition pruning did not work; with execution the rule requires at least half of the children to return no rows, without execution it shows a note. If in every partition the condition is an expression over one column (`col::date = …`, `date_trunc('day', col) = …`), the title and the effect say so, and instead of an empty command a ready range replacement (`col >= … AND col < …`) with a copy button is given: this is what makes pruning and an index on the column work. For `date_trunc` the replacement is given only when the value is the start of the period (`date_trunc('month', col) = '2026-03-15'` finds nothing, while a range from that date would find rows); for a parameter (`$1`) a note under the replacement says it is equivalent only when the parameter is the start of the period. Otherwise there is no command: add a condition on the partition key without a type cast.
- **Fewer workers launched than planned** — the commands `SHOW max_parallel_workers;` and `SHOW max_worker_processes;` to check the limits.
- **A subquery per row** (a SubPlan ran 1000 times or more) — rewrite it as a `JOIN` or `LATERAL`; there is no command.
- **JIT longer than half of execution** — `SET jit = off;` for the session or the role. The server adds up the JIT time of all processes, so in a parallel plan it is divided by the number of processes (the leader and the launched workers).

Index columns are taken from the plan conditions without parsing SQL: the condition is split on `AND`, and each part yields a column if a value is compared with it. A cast to a text type (`::text`, `::varchar`) does not get in the way, while any other cast (for example `::date`) or a function turns the part into an expression that yields no column: an index on the bare column would not help such a condition. When no column is found, the command is a template with `(<columns>)` and the note [[ui:recommend.template]] below it; a template has no hypothesis check.

Nine rules out of eleven need execution facts (all but the sort under `LIMIT` and partition pruning): without [[ui:diag.plan.run.analyze]] the block says how many rules were not checked. A recommendation this version of the app does not know is shown with the rule id, the command and advice to update the app.

[[ui:recommend.hypo.check]] is available on recommendations with an index when the columns were found; it needs `hypopg` created in the plan's database (otherwise the dialog says “hypopg is not installed in this database”). The check runs on the node where the shown plan was built, with the same text, parameters and `search_path` as that run, even if the form fields have been edited since. The app builds the plan without the index, then in one `READ ONLY` transaction creates a virtual index, estimates its size, builds the plan without execution and drops the hypothesis (`hypopg_reset()`) before the rollback; the connection is closed after the check. The dialog shows the command, the plan cost before and after, [[ui:recommend.hypo.used]] or [[ui:recommend.hypo.notUsed]], the estimated index size and the plan tree with the virtual index. Nothing stays on the server: the virtual index lives only in the memory of the check's session, is not written to disk and is not visible to other sessions. If the plan with execution ran on a replica, the check runs on the replica too, and `hypopg` must be installed on its server (the extension package; `CREATE EXTENSION` itself arrives by replication). If the server rejects the index (an unknown column, an unsuitable type), the dialog says “The server rejected the hypothetical index: …”.

## Snapshots {#snapshots}

The [[ui:diag.queries.snapshots]] button in the tool header opens the panel of `pg_stat_statements` snapshots of this connection: time, node, number of rows and file size, newest first. [[ui:diag.snapshots.take]] saves a snapshot of the tool's node: all statistics rows with cumulative counters and the texts of the five hundred longest and five hundred most frequent queries (the texts are normalized by the extension: values are replaced with `$1`, `$2`). The snapshot is kept only on your computer, in the app's data directory (`snapshots/<connection>/<node>/`; characters not allowed in file names are replaced with codes in the node directory name: `db1:5432` → `db1%3A5432`), and only the file's owner can read it. Two snapshots of one node cannot be taken in the same second: the app asks you to wait a second.

Check two snapshots (a third one replaces the earlier of the checked) and press [[ui:diag.snapshots.compare]]. Only snapshots of one node can be compared: the counters of different nodes are unrelated, and the button is disabled with an explanation. The order of checking does not matter: the earlier snapshot is the start. The comparison shows four lists: [[ui:diag.snapshots.degraded]] (the mean time doubled or worse, the query has at least 50 calls), [[ui:diag.snapshots.improved]] (the mean halved or better), [[ui:diag.snapshots.new]] and [[ui:diag.snapshots.gone]] (at most 200 longest queries each; the rest are counted under the list, and the heading shows them all), plus the number of calls in both snapshots. The change in the mean time is written in words — “2.5× faster” or “1.6× slower” (the “Change” column), not as a bare ratio. Glafira's own queries are dimmed and marked in the lists. If statistics were reset between the snapshots, the comparison says [[ui:diag.snapshots.reset]].

[[ui:diag.snapshots.between]] switches the table to [[ui:diag.queries.modes.between]]: the growth of the counters between two snapshots, like a window, but over any interval. Above the table there is a line with the node and the snapshot times and an [[ui:diag.queries.betweenExit]] button; the coverage badge shows the time between the snapshots or, if statistics were reset, the time from the reset to the second snapshot (then the rows of the second snapshot are taken whole, and a note about the reset stands below the findings; CPU and disk reads from `pg_stat_kcache` are then counted over the whole interval between the snapshots, because resetting `pg_stat_statements` does not touch them, and a note says so). There is no [[ui:diag.header.interval]] choice in this mode: the snapshots set the span. Max and stddev cannot be sorted in this mode; sorting by CPU is available only when both snapshots were taken with `pg_stat_kcache`. Search runs over the texts in the snapshots: a query whose text is not in the snapshots is not found. The mode does not touch the server, so it works with a closed connection too: the tool then shows only the snapshots panel, [[ui:diag.snapshots.take]] is disabled, and the top between snapshots opens as usual.

[[ui:common.delete]] on a row asks to confirm the deletion; if the deleted snapshot is used by the current “between snapshots” mode, the table leaves it. A file that cannot be read (damaged or larger than 128 MiB) is listed with the badge [[ui:diag.snapshots.unreadable.corrupt]] or [[ui:diag.snapshots.unreadable.tooLarge]]: it cannot be selected but can be deleted. The snapshots of a connection are deleted with the connection; they are not part of the diagnostics archive.

## Extensions {#extensions}

When `pg_stat_kcache` is installed in the connection's database (loaded via `shared_preload_libraries`, created with `CREATE EXTENSION`, and the role can call `pg_stat_kcache()`), the top gains the [[ui:diag.queries.columns.cpu]] column (processor time in user and system mode, sortable) and the [[ui:diag.queries.columns.disk]] column (bytes read from disk according to the operating system: unlike `shared read`, these are real disk reads, not PostgreSQL cache misses). The card shows the [[ui:diag.query.metric.cpu]] and [[ui:diag.query.metric.disk]] metrics (a dash when the query has no data from the extension), “Copy for LLM” adds them to the statistics, and the lists of new and gone queries in a snapshot comparison get a CPU column. Without the extension the columns are absent altogether and sorting by CPU is unavailable. `pg_stat_statements_reset()` does not reset `pg_stat_kcache`, so in the “since reset” mode CPU and disk may have accumulated over a different period: when only `pg_stat_statements` was reset, the headers of these columns carry a “*” with a tooltip, and the footer says since when `pg_stat_kcache` has accumulated (or that it is reset separately, when the extension does not report that time) and gives the command `SELECT pg_stat_statements_reset(); SELECT pg_stat_kcache_reset();` that resets both. In a window and between snapshots after a `pg_stat_statements` reset, CPU and disk are counted as growth regardless of that reset; when `pg_stat_kcache` 2.3 or newer was also reset between the snapshots, CPU and disk are taken from the second snapshot as a whole. The app checks the extension with a short read before using it and remembers the result for the node for a minute (after a refusal from the server — for 10 minutes): if it is created but not loaded or not available to the role, the top is built without it. With `pg_stat_statements` 1.8 (PostgreSQL 13) and `pg_stat_kcache` 2.2 or newer, only the CPU of top-level statements is counted. In the “last 5, 15 or 60 minutes” window the columns appear after the extension is installed once the sampler restarts (close and reopen the tool and the node's cards).

When `pg_wait_sampling` 1.1 or newer is installed with `pg_wait_sampling.profile_queries = top` or `all` (`on` in old versions), the card's waits come from its profile, and the caption above the table is [[ui:diag.query.waitsSource.pgWaitSampling]]: the profile accumulates since the last `pg_wait_sampling_reset_profile()` and does not depend on whether the [[ui:diag.tools.waits]] tab was opened. The profile has no database, so the waits of one `queryid` in different databases are summed; with `top`, the waits of nested statements are attributed to the top-level statement. The profile is re-read at most once per 30 seconds per query and node. When `profile_queries` is off, a note below the findings says that waits come from the Sessions samples; when the profile cannot be read (the library is not loaded, the role lacks rights, version 1.0 without `queryid`), the card silently uses the samples, as without the extension. The samples caption states their coverage: “From the Sessions sampler over the last 1 h” or less if the sampler started recently.

In the [readiness checklist](connections.md#readiness), while an extension is not created, the items “Extension hypopg”, “Extension pg_stat_kcache” and “Extension pg_wait_sampling” say what it gives and how to enable it, according to the actual state of the server: install the package from PGDG (`postgresql-<version>-<name>`), preload and restart, only `CREATE EXTENSION` (when the library is already loaded), as well as rights and `profile_queries`. Details for the administrator: the administrator guide, section “Role for diagnostics”.

## Rights and load {#load}

The diagnostics role reads other roles' queries with `pg_read_all_stats` (part of `pg_monitor`); without it only its own are visible, and the tool says so. EXPLAIN of application queries needs the right to read their tables (`pg_read_all_data` is a broad right, and granting it is the administrator's decision); a role with `pg_read_all_data` alone is enough only for `SELECT`, while EXPLAIN of a query that writes needs the right to write to its tables even without execution. The sampler reads `pg_stat_statements` without texts once a minute per node while the tool or a card is open; texts are requested by the keys of the visible rows. Besides the sampler, the “since reset” mode re-reads the whole view on every header refresh (every 10 seconds by default while the tab is visible), and every visible card reads the rows of its query, the sums over the view and `pg_stat_activity` every 5 seconds; the query text comes from a cache, and the server hands over the file of texts only on a cache miss for a query that is in `pg_stat_statements`. The “last 5, 15 or 60 minutes” modes hardly read the server: only the header (when there is no buffer yet) and the texts by the keys of the visible rows go to it. After a login refusal, collection, report and card make no further attempts until the connection is opened again: repeated attempts with a wrong password could lock the account. EXPLAIN runs on a separate connection that is closed after the query; so does a hypothesis check, for the duration of the check. The `pg_stat_kcache` columns are read by the same query as `pg_stat_statements`; an open card reads the `pg_wait_sampling` profile at most once per 30 seconds. A snapshot is one read of `pg_stat_statements` with texts; the comparison and the “between snapshots” mode do not read the server. Snapshots are kept in the app's data directory on the user's computer and belong to the user who took them. Details: the administrator guide, section “Diagnostics”.
