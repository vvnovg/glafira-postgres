# Queries

The [[ui:diag.tools.queries]] tool sits in the [[ui:sidebar.diagnostics]] group after replication slots. It shows which queries load the node according to the `pg_stat_statements` extension, opens a card for any query with its history and plan, and gives a console for EXPLAIN of arbitrary SQL. The app reads statistics and builds plans; the only thing that changes data is the [plan with execution](queries.md#analyze) of a writing query, and even that runs in a transaction that is always rolled back.

What the server needs: the `pg_stat_statements` extension in `shared_preload_libraries` (the checklist item “pg_stat_statements is loaded”), created in the connection's database (the item “pg_stat_statements extension”); a role with `pg_monitor` (otherwise only the role's own queries are visible); for plans, the right to read the application's tables (`pg_read_all_data` on PostgreSQL 14 and newer, the checklist item “Reading application tables (EXPLAIN)”; on 13 `SELECT` on the tables of the query is needed). Planning columns are filled only with `pg_stat_statements.track_planning = on` (the item “pg_stat_statements.track_planning”).

## Top queries {#top}

The table has a row per query (identical queries with different literals are already merged by the extension: the text has `$1`, `$2` instead of values). Click a column header to sort: total time (default), mean, calls, rows per call, hit %, reads, temp, WAL, I/O, planning, JIT, stddev and max. Hit % sorts ascending so that the worst come first; the other columns sort descending. A grayed-out sort is unavailable: max and stddev exist only in “since reset” mode, JIT needs pg_stat_statements 1.10 (PostgreSQL 15). Filters: database, [[ui:diag.queries.toplevelOnly]] (without statements nested in functions), the number of rows. The [[ui:diag.queries.openConsole]] button opens the [console](queries.md#console).

Mode ([[ui:diag.queries.mode]]):

- [[ui:diag.queries.modes.sinceReset]] — statistics accumulated since the last `pg_stat_statements_reset()`. Available at once, refreshed on the header interval.
- Last 5, 15 or 60 minutes — what happened recently. While the tab is open the app reads the statistics once a minute (without query texts) and remembers the growth; the window is computed from that growth without touching the server. The badge next to the mode shows how many minutes have been collected (“3 of 5 min collected”): right after opening, the window is empty and the badge says “Waiting for the first tick of the sampler…” until a minute has passed. Coverage is counted from the first tick of the window to the last and may include a gap during which collection was stopped. The history is kept for an hour while the connection is open; closing the tab stops it, reopening continues with a gap.

At the bottom are the extension version and the last statistics reset; if `track_planning` is off, it says so there too. If the extension evicted rare queries (`dealloc`), the “The top is incomplete” finding suggests raising `pg_stat_statements.max`.

Findings of the top (the block above the table): N+1, a tiny query with a huge number of calls; unstable time (stddev much larger than the mean); low cache hit; temp files per call; planning longer than execution. Each has an “Open query” button.

## Query card {#card}

Clicking the query text in a table row (or the “Open query” button of a finding) opens the query tab. A query in the card is one `queryid` in one database: rows per role and per top-level flag are summed, the breakdown is a separate table (it appears when there is more than one row). The node selector in the header opens the same query on another node in a separate tab, so the primary and a replica can be compared side by side (identifiers match on physical replicas). If the node is no longer in the topology, the card offers to open the query on another node.

The card header has the database and the `queryid`, the node selector, and the [[ui:diag.header.refresh]] and [[ui:diag.query.copyLlm]] buttons. The tab title is the beginning of the query text.

The [[ui:diag.query.overview]] sub-tab: the query text (with a copy button; a text longer than 16 384 characters is truncated, and this is marked), metrics since reset and for the last hour side by side, findings about this query, two history sparklines (calls per minute and mean time) by sampler ticks — gaps in which collection was stopped break the line — the breakdown by role, instances running right now from `pg_stat_activity` (PostgreSQL 14 and newer, active queries only, without parallel workers; a button opens Sessions), the query's waits from the samples of the wait profile (only the [[ui:diag.tools.waits]] tab collects them; until it has been opened, a hint stands instead of the table), the query's tables, which appear after the first plan; until then a “Get plan” button stands next to them. The buttons under the text: [[ui:diag.query.plan]] and [[ui:diag.query.openConsole]] (the console receives the node, the database and the query text).

[[ui:diag.query.copyLlm]] puts markdown on the clipboard: server and extension versions, node and database, the query text, statistics, the plan as text and the DDL of the tables with indexes (at most ten tables and 64 KB). The text is the normalized one, without parameter values, but the plan may contain the values typed into the parameter form or the literals of a chosen running instance: check the markdown before pasting it into a model. The plan is the last one obtained in this tab; if there was none yet, the app builds a probe plan without execution (before PostgreSQL 16 this is possible only for a query without `$N`). A truncated text is not planned. If the plan or the DDL could not be obtained, the markdown keeps the text and the statistics, and a “Notes” section appears at the end. This is data for a question to a model; there are no prompts in it.

## Plan and EXPLAIN {#plan}

The [[ui:diag.query.plan]] sub-tab builds the plan on the selected node. The text: normalized from `pg_stat_statements` or the text of a running instance with its literals ([[ui:diag.query.source]]; the text of a running instance cannot be chosen if it is truncated). For the normalized text the parameters `$1…$N` must be given: on PostgreSQL 16 and newer `GENERIC_PLAN` is the default for the “Plan” button, a plan without values; otherwise fill in the fields (an empty field is NULL). The [plan with execution](queries.md#analyze) always needs values: `GENERIC_PLAN` cannot be combined with ANALYZE. The execution timeout is 5 seconds to 10 minutes, 30 seconds by default; the probe plan is built for at most 15 seconds. `search_path` can be set in the collapsed field if needed (the server default of the role otherwise).

[[ui:diag.plan.run.plan]] is `EXPLAIN (FORMAT JSON, VERBOSE, SETTINGS)`: the query is not executed. [[ui:diag.plan.run.analyze]] is `EXPLAIN (ANALYZE, BUFFERS, WAL)`: the query really runs; see the next section.

Errors are shown next to the buttons. Two statements in the text are not accepted: EXPLAIN is built for exactly one. A parse error is reported with the server's own text, and its place in the query (“Error at line 1, column 8”) is marked in the text. If the role lacks privileges, the message depends on the statement: for `SELECT` it is the right to read the tables (`pg_read_all_data` or `SELECT`), for `INSERT`, `UPDATE`, `DELETE`, `MERGE` and `CREATE …` it is the right to write: PostgreSQL checks it even for EXPLAIN without execution.

The plan tree: indented rows with expandable nodes; inclusive and own time (without children) with a share bar; rows “estimate → actual” with an estimate error of tenfold or more highlighted as “×N” (orange from ×10, red from ×100 and for an infinite error); loops; buffers (hits / reads); marks: disk, lossy, heap fetches, fewer workers than planned, parallel, never executed. The three nodes with the largest own time are highlighted. The time of nodes under `Gather` is converted to wall-clock time (the server reports the mean per process). When the plan has no times (a plain EXPLAIN or ANALYZE with `TIMING OFF`), the cost or a dash is shown instead, and the nodes with the largest cost are highlighted. Clicking a node opens a panel with all its fields. Above the tree is the summary: planning, execution, tier, round trip, JIT, triggers, settings; the [[ui:diag.plan.copyJson]] and [[ui:diag.plan.copyText]] buttons (psql-style text). Past runs of the tab (up to ten) are in the [[ui:diag.plan.history.title]] list.

## Plan with execution {#analyze}

The [[ui:diag.plan.run.analyze]] button runs the query and shows the actual time, rows, loops and buffers. There are two execution tiers: the app first builds a plain plan and checks whether the query writes.

- **Read** (no `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE … AS`): runs without confirmation in a read-only transaction (`BEGIN READ ONLY`) that is rolled back. If the query tries to write anyway (a function with a side effect, a trigger), the server refuses and the app offers to run it as a write — the [[ui:diag.plan.run.asWrite]] button. When the tab is open on the leader and the topology has an available replica, the read tier runs on the replica by default, so that the primary is not loaded: after the probe plan the [[ui:diag.plan.run.analyzeOn]] field appears next to the buttons, where the leader can be put back (the plan on a replica may differ). The field exists only in the card; in the console the read tier runs on the console's node. The read tier is protected by a `READ ONLY` transaction: it does not stop non-transactional administrative functions (`pg_terminate_backend`, `pg_cancel_backend`, `pg_stat_reset*`, `pg_reload_conf`), and a `SELECT` with such a function will run without confirmation; the decision on this case is still with the project owner.
- **Write**: needs actions enabled on the connection (unavailable on read-only); a dialog with the list of tables and a warning is shown in every environment, and on prod it also asks for the connection name. Then the query runs in a transaction and is rolled back. It runs as the connection's role, so that role needs the right to write to the tables of the query. Rows change and are rolled back, but rollback does not undo fired triggers, sequence advances, `NOTIFY` and external calls; the query holds locks while it runs. Such an execution is recorded in the [actions journal](diagnostics.md#journal) as “EXPLAIN ANALYZE (write)”. A write cannot run on a replica: choose the primary.

When the timeout expires the server cancels the execution and nothing changes (the message “The plan was not produced in time”); choose a longer timeout and repeat.

## EXPLAIN console {#console}

[[ui:diag.explain.title]] opens from the diagnostics group, from the Queries tool and from the card. There is one console per connection: opening it from the card puts the node, the database and the query text into it, while opening it from the tree keeps what was typed. Pick a node and a database, enter one SQL statement and build plans as in the card (without the replica choice for the plan with execution that the card has); `$1…$N` in the text become parameter fields. The console has its own [[ui:diag.query.copyLlm]] button: it takes the plan of the last run while the query, the node and the database have not changed. The second sub-tab is [[ui:diag.explain.sourcePaste]]: paste the output of `EXPLAIN (FORMAT JSON)` (psql framing with `QUERY PLAN` and `+` is fine) and press [[ui:diag.explain.parse]]: the tree is built without the server. The text format of psql and auto_explain plans comes in the next part.

## Rights and load {#load}

The diagnostics role reads other roles' queries with `pg_read_all_stats` (part of `pg_monitor`); without it only its own are visible, and the tool says so. EXPLAIN of application queries needs the right to read their tables; a role with `pg_read_all_data` alone is enough only for `SELECT`, while EXPLAIN of a query that writes needs the right to write to its tables even without execution. The sampler reads `pg_stat_statements` without texts once a minute per node while the tool or a card is open; texts are requested by the keys of the visible rows. Besides the sampler, the “since reset” mode re-reads the whole view on every header refresh (every 10 seconds by default while the tab is visible), and every visible card reads the rows of its query, the sums over the view and `pg_stat_activity` every 5 seconds; the query text comes from a cache. The “last 5, 15 or 60 minutes” modes do not read the server. EXPLAIN runs on a separate connection that is closed after the query. Details: the administrator guide, section “Diagnostics”.
