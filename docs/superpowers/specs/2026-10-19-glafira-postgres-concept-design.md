# Glafira for PostgreSQL — концепция

**Дата:** 2026-10-19
**Статус:** согласована, на ревью текста
**Тип:** desktop-приложение (Tauri 2 + Rust + React/TypeScript), второй продукт семейства Glafira
**Образец:** Glafira for Apache Kafka (`/Users/vvnovg/kafka-explorer`) — стек, дизайн, модель Free/Pro, политика, MCP-шлюз

Документ фиксирует общее видение, каталог инструментов и этапы. Каждый этап (P1–P6) получает свою спецификацию,
план и реализацию. Первый этап — `2026-10-19-glafira-postgres-p1-design.md`.

---

## 1. Цель и аудитория

Glafira for PostgreSQL — инструмент диагностики текущих проблем PostgreSQL и кластеров Patroni: GUI с деревом
подключений и схем, набор инструментов для типичных инцидентов, поиск тяжёлых запросов с рекомендациями по оптимизации
и MCP-шлюз, через который LLM (Claude Desktop, Claude Code, Cursor) читает диагностику разрешённых подключений.

**Пользователи:** DBA и SRE на дежурстве (инцидент: «всё встало», растёт лаг, кончается диск, переключился лидер)
и разработчики (почему медленный запрос, какой индекс нужен, что изменилось после релиза).

**Ключевые сценарии:**
1. Подключиться к одиночному серверу, к списку узлов (как multi-host JDBC) или к кластеру Patroni — в том числе через
   SSH-бастион — меньше чем за минуту, вставив строку подключения.
2. За минуту понять, что происходит на узле: кто блокирует, что держит vacuum, почему растёт `pg_wal`, какие реплики
   отстают и готов ли кластер к failover.
3. Найти запросы, которые нагружают узел именно сейчас, посмотреть их план и получить обоснованную рекомендацию
   с готовым текстом команды.
4. Безопасно выполнить типичное лечение: отменить запрос, завершить сессию, удалить мёртвый слот, сделать switchover —
   с предпросмотром и подтверждением.
5. Дать LLM-ассистенту прочитать диагностику и предложить решение, не давая ему ничего менять.

**Не-цели:** универсальный SQL-редактор и администрирование схемы (это DBeaver / pgAdmin), фоновый мониторинг
и графики за дни (это Prometheus / pgwatch), метрики ОС, изменение конфигурации из приложения.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Изменения в кластере | Диагностика + безопасные действия с предпросмотром и подтверждением (§6). Конфигурация, индексы, reinit — только готовая команда для копирования |
| Виды подключения | Сервер; список узлов с автоматическим выбором primary (как `targetServerType` JDBC / `target_session_attrs` libpq); кластер Patroni через REST API |
| Patroni | Только REST API (`:8008`): `/cluster` для обнаружения узлов, действия — через тот же API. DCS и Kubernetes — вне объёма |
| Сеть | Напрямую или встроенный SSH-туннель через системный OpenSSH, общий на всё подключение |
| Время | Сессионное сэмплирование в памяти, пока открыта вкладка, + снимки на диск по кнопке. Фонового сбора нет |
| Планы | EXPLAIN без выполнения по умолчанию; EXPLAIN ANALYZE — только человеком по кнопке, в транзакции с ROLLBACK и таймаутом |
| LLM | MCP-шлюз только для чтения; уровни `off` / `diagnostics` / `data` на подключении; `data` добавляет произвольный SELECT с трёхслойной защитой (§7) |
| Продукт | Glafira for PostgreSQL: Free/Pro с офлайн-лицензией, политика администратора, автообновление, руководство; i18n с первого дня, ru + en на старте, остальные 10 языков — этап P6 |
| Код | Отдельный репозиторий. `license-format` — git-зависимость из kafka-explorer; протокол-независимая часть MCP — крейт `glafira-mcp-core` (P4); общие куски UI и Rust — изолированными модулями с тем же интерфейсом, что в Glafira for Kafka, чтобы позже вынести их в общий монорепозиторий механически |
| Версии | PostgreSQL 13+, Patroni 3.0+ (включая 4.x). Каждый SQL-набор выбирается по `server_version_num` и наличию расширений; недоступное помечается «—» с причиной |

## 3. Архитектура

```
┌──────────────────── WebView (React 19 + TS) ───────────────────┐
│ Дерево: подключения → узлы → БД → схемы → объекты │ Вкладки      │
│ api/ — типизированные invoke() и Channel                         │
└───────────────▲─────────────────────────────┬────────────────────┘
                │ events / Channel             │ invoke
┌───────────────┴──────────── Rust core ───────▼────────────────────┐
│ commands/  — IPC, валидация, маппинг ошибок, guard read-only/prod │
│ conn/      — профили, строки подключения, пулы по (узел, БД)       │
│ net/ssh    — туннели через системный OpenSSH, askpass             │
│ topology/  — Patroni REST, опрос узлов списка, журнал событий     │
│ catalog/   — БД, схемы, таблицы, индексы, функции, роли           │
│ diag/      — проверки «сейчас»: SQL-наборы с учётом версии        │
│ sampler/   — сэмплирование активности, дельты pg_stat_statements  │
│ queries/   — топ запросов, EXPLAIN, ANALYZE по кнопке, hypopg     │
│ actions/   — безопасные действия, журнал действий                 │
│ storage/ secrets/ policy/ license/ i18n/  — как в Glafira          │
│ mcp/       — реализация Backend для MCP-шлюза                     │
└────────────────────────────────────────────────────────────────────┘
crates/
  pg-advisor       — чистые функции без I/O: правила диагностики, разбор EXPLAIN (JSON и текст),
                     эвристики планов, маскирование литералов, проверка SQL от LLM
  glafira-mcp-core — транспорт, рукопожатие, сессии, подтверждение клиентов, аудит, лимиты (P4)
  glafira-pg-mcp   — инструменты PG/Patroni поверх core; без драйвера БД (P4)
  license-format   — git-зависимость
```

**Технические решения:**
- Драйвер PG — `tokio-postgres` + `postgres-openssl` (OpenSSL vendored, как в Glafira): `sslmode` от `disable`
  до `verify-full`, клиентские сертификаты PEM / PKCS#12, password / md5 / SCRAM. Пулы — свои (`conn/pool.rs`,
  вместо `deadpool-postgres`: P1b нужен `connect_raw` к порту туннеля с проверкой TLS по исходному имени хоста),
  не больше 3 соединений на пару (узел, БД) для каталога и вкладок плюс одно для опроса топологии. Kerberos/GSSAPI драйвер не поддерживает — вне объёма.
- Patroni — `reqwest`, basic auth, TLS / mTLS.
- SSH — системный `ssh` (учитывает `~/.ssh/config`, ProxyJump, агент, аппаратные ключи); пароли и пассфразы отдаёт
  режим `askpass` нашего бинаря из keychain.
- `pg_query` (настоящий парсер PostgreSQL) — нормализация и маскирование литералов, список таблиц запроса,
  проверка SQL от LLM.

**Принципы:**
- Вся работа с БД и Patroni — в Rust; фронтенд вызывает команды и получает потоки.
- Каждый диагностический запрос именованный, с `statement_timeout` (5 с), `lock_timeout` (1 с),
  `application_name = glafira-pg`; диагностика никогда не берёт тяжёлых блокировок.
- Диагностический пул — `default_transaction_read_only = on`; действия — отдельное соединение.
- Длительные операции (сэмплер, наблюдение после действия, ANALYZE) — tokio-задачи с `SessionId`, данные во фронтенд —
  через `tauri::ipc::Channel` батчами, отмена — `stop_session`.
- `pg-advisor` не делает I/O и тестируется на фикстурах.

## 4. Подключения и дерево

**Виды профиля:**

| Вид | Что вводится | Откуда топология |
|---|---|---|
| Сервер | `host:port` | — |
| Список узлов | `h1:5432, h2:5432, h3:5432` и целевой узел по умолчанию: `primary` / `prefer-standby` / `any` | Опрос всех узлов: роль — `pg_is_in_recovery()`, связи — `pg_stat_replication` на primary и `pg_stat_wal_receiver` на репликах |
| Кластер Patroni | Адреса REST API | `GET /cluster` + таймлайны, история failover, теги, pause, действия |

- Импорт строки подключения: `jdbc:postgresql://h1:5432,h2:5432/db?targetServerType=primary`,
  `postgresql://h1,h2/db?target_session_attrs=read-write`, conninfo `host=h1,h2 port=5432 dbname=db`.
  Пароль из строки уходит в keychain.
- Если узлы списка на самом деле под Patroni, добавление адресов API превращает профиль в кластер Patroni.
- Подмена адресов узлов — когда `/cluster` отдаёт адреса, недоступные с машины пользователя (pod IP, NAT).
- Поля, общие с Glafira: имя, цвет, окружение (`local`…`prod`), read-only, папка, порядок. `llmAccess` — локальное поле
  (P4), не экспортируется.

**Дерево:**
```
📁 Биллинг
  ● billing-prod  [PROD] [Patroni]          ← клик: обзор кластера
     ▸ Узлы
        ★ pg-1   Leader   TL 7
        ○ pg-2   Sync     lag 0 B
        ○ pg-3   Replica  lag 12 MB  ⚠
     ▸ Базы данных
        ▸ orders
           ▸ public
              ▸ Таблицы (142)  ▸ Представления  ▸ Мат. представления
              ▸ Функции        ▸ Последовательности
           ▸ Расширения
     ▸ Роли
     ⚕ Диагностика                          ← вход в инструменты (§5–6)
```
- Топология опрашивается раз в 10 с, пока подключение открыто; смена лидера / primary попадает в журнал событий.
- Каталог читается с лидера, переключатель — с выбранной реплики. Инструменты, зависящие от узла, имеют селектор узла;
  вкладку можно закрепить за узлом или оставить «следовать за лидером».
- Проверка подключения по шагам: SSH → Patroni API → обнаружение узлов → TCP/TLS к каждому узлу → аутентификация →
  чек-лист готовности к диагностике (`pg_monitor`, `pg_signal_backend`, `pg_stat_statements` и
  `shared_preload_libraries`, `track_io_timing`, `compute_query_id`, дополнительные расширения) с объяснением,
  что без пункта не работает.

## 5. Каталог диагностики

Каждый инструмент — вкладка: таблица данных и блок «Находки» (что не так, серьёзность, что сделать, где это сделать
в Glafira). Правила и пороги — в `pg-advisor`. ★ — дежурный набор (этап P2), остальное — P5.

**A. Пульс узла / кластера ★** — плитки со ссылками в инструменты: соединения (занято / `max_connections`, по
состояниям), TPS, commit/rollback, cache hit, temp-файлы, deadlocks, скорость WAL, самая долгая транзакция и запрос,
заблокированные сессии, максимальный возраст XID, максимальный лаг реплик, размер `pg_wal`.

**B. Активность и сессии**
| Инструмент | Что решает |
|---|---|
| ★ Активные сессии | Состояние, wait event, длительность запроса и транзакции, клиент, приложение; группировка по app/user/client/db; cancel / terminate |
| ★ Idle in transaction | Висящие транзакции держат блокировки и мешают vacuum |
| ★ Профиль ожиданий (ASH) | Wait events по времени из сэмплов, топ запросов по числу сэмплов |
| Соединения | Использование лимита, разбивка, частота новых подключений (признак, что нужен пулер) |

**C. Блокировки**
| Инструмент | Что решает |
|---|---|
| ★ Дерево блокировок | Цепочка от корневого блокирующего к жертвам (`pg_blocking_pids`); «завершить корневой» |
| ★ DDL в очереди | Миграция ждёт `ACCESS EXCLUSIVE` за долгим запросом и блокирует всех после себя |
| Advisory-блокировки, рост deadlocks | Детали deadlock — только в логе сервера, это указывается |

**D. Транзакции и wraparound**
| Инструмент | Что решает |
|---|---|
| ★ Что держит горизонт xmin | Долгие транзакции, слоты (`xmin`/`catalog_xmin`), prepared transactions, `hot_standby_feedback` реплик |
| Возраст XID и MultiXact | По БД и таблицам, процент до `autovacuum_freeze_max_age` и до аварийной остановки, прогноз |

**E. Vacuum и bloat**
| Инструмент | Что решает |
|---|---|
| Autovacuum сейчас | Прогресс, занятость воркеров |
| Кандидаты на vacuum/analyze | Порог autovacuum с учётом reloptions, insert-only таблицы, давность прохода |
| Оценка bloat | Статистическая без сканирования; точная — `pgstattuple_approx` по кнопке |
| Прогресс операций | CREATE INDEX, VACUUM, ANALYZE, CLUSTER, COPY, basebackup |

**F. Репликация и WAL** (все виды кластера)
| Инструмент | Что решает |
|---|---|
| ★ Реплики | Лаги write/flush/replay в байтах и времени, sync_state; на реплике — wal receiver, задержка replay, конфликты recovery |
| ★ Слоты репликации | `wal_status`, `safe_wal_size`, удерживаемый WAL, логические слоты, подписки |
| Архивирование | Сбои `archive_command` (`pg_stat_archiver`) |

**G. Patroni**
| Инструмент | Что решает |
|---|---|
| ★ Топология | Роль, состояние, таймлайн, лаг, теги, pending restart, запланированные действия, pause |
| ★ Готовность к failover | Лаг больше `maximum_lag_on_failover`, `nofailover`, synchronous_mode без sync-реплики |
| ★ Матрица health | `/primary`, `/replica`, `/read-only`, `/sync`, `/async`, `/health` по узлам — то, что видит балансировщик |
| История | `/history` на общей оси времени с журналом событий |
| Динамическая конфигурация | `/config` против `pg_settings` каждого узла, расхождения версий, `dcs_last_seen` |

**H. Конфигурация** — значения, отличные от умолчаний, с источником и `pending_restart`; сравнение между узлами;
ошибки `pg_file_settings` и `pg_hba_file_rules`; советы (`work_mem` × соединения, checkpoints и `max_wal_size`,
таймауты, `track_io_timing`, `jit` на OLTP).

**I. Схема и хранилище** — размеры и рост между снимками; здоровье индексов (неиспользуемые, дубликаты,
перекрывающиеся, INVALID, FK без индекса); риски схемы (таблицы без PK, последовательности `int4` у предела);
`pg_stat_io` (16+), `pg_stat_checkpointer` (17+) / `pg_stat_bgwriter`.

**Вне досягаемости SQL (говорится прямо):** метрики ОС (нужен node_exporter); содержимое логов сервера — только при
`pg_read_server_files` (тогда вкладка «Лог»). Размер `pg_wal` и список логов — через `pg_ls_waldir()` / `pg_ls_logdir()`
(разрешены `pg_monitor`).

## 6. Тяжёлые запросы и рекомендации

**6.1 Топ запросов** (`pg_stat_statements`, по каждому узлу):
- режимы: **за окно** 5 / 15 / 60 мин (сэмплер раз в 60 с, `pg_stat_statements(showtext := false)`, тексты — только
  для новых `queryid`), **с момента сброса**, **между снимками**;
- сортировка: доля в общем времени, mean / max / stddev, calls, rows/call, shared read и hit ratio, temp written,
  `wal_bytes`, время I/O, планирования и JIT;
- рост `pg_stat_statements_info.dealloc` → предупреждение о неполном топе;
- карточка: отформатированный текст, спарклайн, метрики, затронутые таблицы (через `pg_query`), выполняющиеся сейчас
  экземпляры, wait events запроса из сэмплов, «План», «Скопировать для LLM» (markdown: запрос, статистика, план,
  DDL таблиц, индексы);
- эвристики без плана: N+1 (огромные calls при крошечном времени), нестабильный план (stddev ≫ mean),
  низкий hit ratio, temp-файлы, планирование дольше выполнения.

**6.2 Планы:**
- EXPLAIN (`FORMAT JSON, VERBOSE, SETTINGS`); для `$1` — `GENERIC_PLAN` на 16+, на старых — форма параметров
  с «Взять из текущего выполнения» (литералы из `pg_stat_activity` по `query_id`);
- EXPLAIN ANALYZE по кнопке (`ANALYZE, BUFFERS, WAL`): `BEGIN` → `SET LOCAL statement_timeout` (30 с) и
  `lock_timeout` → `EXPLAIN` → `ROLLBACK`; узел по умолчанию — реплика; SELECT — с подтверждением, DML — с отдельным
  предупреждением (строки изменятся и откатятся, блокировки, последовательности, триггеры); на read-only профиле —
  только SELECT в `READ ONLY`; на prod — подтверждение именем подключения;
- EXPLAIN-консоль: запрос или готовый план (JSON или текст из psql / auto_explain);
- визуализация — дерево узлов: собственное время и доля, оценка строк против факта (ошибка ×10+ подсвечивается),
  loops, buffers, сбросы на диск, heap fetches.

**6.3 Рекомендации по плану** (`pg-advisor`):
| Признак | Рекомендация |
|---|---|
| Seq Scan большой таблицы, `Rows Removed by Filter` ≫ rows | Индекс по колонкам фильтра |
| Index Scan с большим отсевом фильтром | Составной индекс, порядок колонок |
| Nested Loop, внутри Seq Scan × тысячи loops | Индекс по ключу соединения |
| Оценка строк ошибается в ×10+ | `ANALYZE`, `SET STATISTICS`, `CREATE STATISTICS` |
| Sort / Hash на диск, lossy bitmap | `work_mem` для сессии или роли; индекс под ORDER BY |
| Sort всей таблицы ради LIMIT | Индекс под ORDER BY |
| Index Only Scan с heap fetches | VACUUM (карта видимости) |
| Append по всем партициям | Не работает pruning |
| Workers launched < planned | Исчерпан `max_parallel_workers` |
| SubPlan на каждую строку | Переписать на JOIN / LATERAL |
| JIT дольше выполнения | `jit = off` / выше `jit_above_cost` |

У каждой рекомендации — доказательство (цифры узла плана), готовый текст команды (приложение его **не выполняет**),
ожидаемый эффект и риски, кнопка «Проверить гипотезу» через `hypopg` (виртуальный индекс → EXPLAIN →
«стоимость была / стала», оценка размера → `hypopg_reset()`).

**6.4 Опциональные расширения** (используются, если установлены): `pg_wait_sampling`, `pg_qualstats`, `pg_stat_kcache`.

**6.5 Снимки:** сравнение — новые, исчезнувшие, деградировавшие (mean ×N), ускорившиеся запросы. Хранение —
`snapshots/<подключение>/<узел>/…json`, права 0600, тексты нормализованы.

**После MVP:** индексный советник по нагрузке (набор «добавить / удалить»), разбор auto_explain из логов.

## 7. Безопасные действия

| Действие | Как | Особенности |
|---|---|---|
| Отменить запрос | `pg_cancel_backend` | Из активности, дерева блокировок, карточки запроса |
| Завершить сессию | `pg_terminate_backend` | Поштучно и пакетом («idle in transaction дольше N», «корневой блокирующий») |
| Удалить неактивный слот | `pg_drop_replication_slot` | Двойное подтверждение (§7.2) |
| `ANALYZE` / `VACUUM (ANALYZE)` таблицы | Отдельное соединение | Фоновая задача с прогрессом и отменой. `VACUUM FULL` — нет |
| Перечитать конфигурацию | Patroni `POST /reload` или `pg_reload_conf()` | |
| Switchover | `POST /switchover` | Сейчас или по расписанию; отмена запланированного |
| Failover | `POST /failover` | Только без здорового лидера; усиленное подтверждение |
| Перезапуск узла | `POST /restart` | «Только если pending restart», по расписанию; отмена запланированного |
| Pause / resume | `PATCH /config {"pause": …}` | Из `/config` трогаем только `pause` |

**Не выполняем — даём готовую команду с объяснением рисков:** `ROLLBACK PREPARED`, `REINDEX CONCURRENTLY`,
`CREATE INDEX`, `ALTER SYSTEM`, `patronictl edit-config`, `reinit`, `VACUUM FULL`.

**7.1 Защита** (проверки в Rust):
- read-only профиль: любое действие → `READ_ONLY`, кнопки скрыты;
- prod: каждое действие — ввод имени подключения; пакетное завершение и failover — ещё и имя объекта;
- предпросмотр: для завершения — список сессий; для switchover — готовность кандидата и что почувствуют клиенты;
- защита от переиспользования PID: `pg_terminate_backend(pid) … WHERE pid = $1 AND backend_start = $2`;
- наблюдение после switchover / failover / restart, пока новый лидер не стабилизируется;
- предпроверка прав (`pg_signal_backend`, владение таблицей или `pg_maintain` на 17+, права на Patroni API):
  кнопка неактивна, в подсказке причина;
- журнал действий `actions.jsonl` (ротация 5 МБ, 0600);
- LLM никогда не выполняет действия. На будущее (как G3 Glafira): предложение LLM открывается заполненной формой
  подтверждения.

**7.2 Удаление слота:** ввод имени слота всегда (+ имя подключения на prod); предпросмотр — тип, plugin, БД,
удерживаемый WAL, `wal_status`, `inactive_since` (17+); выполнение `… WHERE slot_name = $1 AND NOT active`.
Слот участника Patroni или постоянный слот из `/config` Patroni пересоздаст — предпросмотр говорит об этом и предлагает
правильное лечение (конфигурация или удаление участника).

## 8. MCP-шлюз

**Архитектура — как в Glafira:** stdio-шим `glafira-pg mcp` → сокет / named pipe приложения; транспорт, рукопожатие,
сессии, подтверждение клиентов, лимиты, аудит — `glafira-mcp-core`; инструменты — `glafira-pg-mcp` без драйвера БД
(тест проверяет `Cargo.toml`). Политика: `mcpEnabled` и `mcpMaxAccess` (ограничить уровень до `diagnostics`).

**Уровни `llmAccess`:**
| Уровень | Что видит LLM |
|---|---|
| `off` | Ничего (`not_allowed`) |
| `diagnostics` | Топология и Patroni, `pg_stat_*`, блокировки, конфиг, схема, нормализованные запросы, EXPLAIN без ANALYZE, hypopg. Литералы маскируются (`pg_query` normalize) в текущих запросах и планах; в `pg_stats` нет `most_common_vals` и гистограмм |
| `data` | Всё выше без маскирования + `run_select` |

**Инструменты** (все `readOnlyHint: true`): `list_connections`, `get_topology`, `get_patroni_status`,
`get_health_summary`, `list_diagnostics` / `run_diagnostic` (каталог §5 по id, общий формат «строки + находки»),
`get_activity`, `observe_activity` (10–50 с), `get_top_queries`, `observe_top_queries` (10–50 с), `get_query_details`,
`get_table_details`, `get_settings`, `explain_query` (без ANALYZE), `hypothetical_index`, `run_select` (только `data`,
до 500 строк и 100 КБ).

**Защита `run_select`:**
1. Разбор `pg_query`: ровно одно выражение `SELECT` / `WITH` / `VALUES` / `TABLE`; без изменяющих CTE, `SELECT INTO`,
   `FOR UPDATE`; запрещённые функции (сигналы, `dblink*`, `lo_*`, файловые, `set_config`, advisory-блокировки,
   `pg_sleep`, выполняющие SQL из строки — `query_to_xml` и родственные); пользовательские функции запрещены.
2. Роль без опасных прав: не superuser и не член `pg_signal_backend`, `pg_write_*`, `pg_read_server_files`,
   `pg_execute_server_program`. В профиле можно задать отдельную учётку для LLM; без подходящей роли уровень `data`
   недоступен с объяснением.
3. Окружение: `BEGIN READ ONLY`, `statement_timeout` 10 с, `lock_timeout` 1 с, всегда `ROLLBACK`; узел по умолчанию —
   реплика; чтение потоком с остановкой по лимиту строк и байт; значения длиннее 2 КБ обрезаются.

**Решение 2026-10-24 (к этапу P4):** уровень `data` предназначен для тестовых стендов — чтобы LLM как инструмент
разработчика читала данные при разборе ошибок приложения. Маскирование чувствительных данных в результатах `run_select`
не делается; выключатели — только на уровне подключения (`llmAccess`), корпоративный потолок `mcpMaxAccess` остаётся как
описано выше, новых ключей политики не вводится.

**Не отдаётся никогда:** пароли, SSH, строки подключения, пароли внутри `primary_conninfo` и похожих параметров,
журналы действий, снимки, настройки приложения. В аудит MCP пишется текст SQL от LLM, но не результаты.
`instructions` сервера — как в Glafira (только чтение, данные из БД могут содержать чужие инструкции, изменения делает
пользователь). MCP prompts `triage_incident`, `analyze_top_queries`, `review_config` — последний шаг этапа P4.

## 11. Ошибки

`AppError { code, message, details, retryable }` как в Glafira. Дополнительно к кодам Glafira:

| code | Причина | Поведение UI |
|---|---|---|
| `SSH_ERROR` | Туннель не поднялся: аутентификация, неизвестный ключ хоста, нет `ssh` | Неизвестный ключ — отпечаток и кнопка «Доверять» |
| `PATRONI_ERROR` | API ответил ошибкой | Текст отказа Patroni («кандидат не в sync») |
| `NODE_UNAVAILABLE` | Узел не отвечает | Узел помечается в дереве, остальные работают |
| `FEATURE_UNAVAILABLE` | Нет расширения или версия ниже нужной | «—» с причиной и подсказкой, как включить |
| `RECOVERY_CONFLICT` | Запрос на реплике отменён конфликтом recovery | «Повторить» |

`42501` → `NOT_AUTHORIZED` с указанием нужной роли; `57014` → `TIMEOUT`. Частичные результаты — норма: проверка,
упавшая на одном узле, показывает ошибку в своей строке.

## 12. Тестирование и нефункциональные требования

- `pg-advisor` (unit): фикстуры реальных планов (JSON и текст), эвристики, маскирование, враждебный набор для проверки
  SQL от LLM (`query_to_xml`, изменяющие CTE, несколько выражений, комментарии, `$$`).
- Матрица версий: каждый SQL-набор выполняется без ошибок на PG 13–18 в Docker.
- Стенд: etcd + 3 узла Patroni (свой образ `postgres` + `patroni[etcd3]`); primary + реплика без Patroni; одиночный PG;
  контейнер OpenSSH как бастион. Интеграционные тесты: обнаружение, switchover, restart, pause, failover, health-матрица,
  туннель, отмена и завершение сессий, удаление слота.
- Фронтенд: Vitest + Testing Library, IPC замокан.
- MCP: шлюз против фейкового `Backend`, сторожок списка инструментов, тест `Cargo.toml`.

| Метрика | Цель |
|---|---|
| Соединения приложения | ≤ 3 на пару (узел, БД) |
| Сэмплер | 1 лёгкий запрос в секунду на узел (активность), 1 в минуту (`pg_stat_statements`) |
| Каталог | Дерево и таблицы виртуализированы, 10 000+ таблиц |
| Холодный старт | < 2 с |
