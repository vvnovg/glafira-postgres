# Glafira for PostgreSQL: руководство администратора

## Установка
| ОС | Файл | Тихая установка |
|---|---|---|
| macOS | `Glafira_for_PostgreSQL_<версия>_aarch64.pkg` / `_x64.pkg` | `sudo installer -pkg <файл>.pkg -target /` (Jamf, Intune, Kandji) |
| Windows | `Glafira_for_PostgreSQL_<версия>_x64_en-US.msi` | `msiexec /i <файл>.msi /qn` (SCCM, Intune) — установка на машину |
| Linux | `Glafira_for_PostgreSQL_<версия>_amd64.deb`, `Glafira_for_PostgreSQL-<версия>-1.x86_64.rpm`, `Glafira_for_PostgreSQL_<версия>_amd64.AppImage` | `sudo apt install ./<файл>.deb`, `sudo dnf install ./<файл>.rpm` |

Установщики — в разделе релизов `https://github.com/vvnovg/glafira-postgres-releases/releases`.
Пробелы в именах файлов заменены на `_` при публикации; точные имена смотрите в релизе.
Исполняемый файл приложения — `glafira-pg` (`glafira-pg.exe` на Windows, `/usr/bin/glafira-pg` на Linux).

### Обновление установленного приложения
Встроенное обновление («О программе» → «Проверить обновления») скачивает пакет того же типа, что установлен (на macOS — архив `.app.tar.gz`):

| Установлено из | Что делает обновление | Права |
|---|---|---|
| `.pkg` / `.dmg` (macOS) | заменяет `.app` на месте | если `.app` принадлежит root (установка из `.pkg` в `/Applications`) — запрос пароля администратора |
| `.msi` (Windows, на машину) | запускает новый MSI | UAC; у пользователя без прав администратора обновление не установится |
| `.deb` / `.rpm` (Linux) | ставит новый пакет через `dpkg -i` / `rpm -U` | пароль администратора (pkexec, иначе zenity/kdialog + sudo) |
| `.AppImage` | заменяет файл AppImage | запись в каталог с AppImage |

**Управляемые парки** (SCCM, Intune, Jamf, Kandji, репозиторий пакетов): обычные пользователи без прав
администратора не смогут установить обновление сами. Рекомендуется политика `updatesEnabled = false` и раздача
новых версий теми же средствами, что и установка (на Linux — через свой репозиторий apt/dnf или `apt install ./<файл>.deb`).

## Политика
Приложение читает политику при запуске. Пользователь не может её изменить.

| ОС | Где |
|---|---|
| macOS | профиль конфигурации MDM, домен `io.github.vvnovg.glafira.postgres` (файл попадает в `/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist`) — пример `admin/policy.mobileconfig` |
| Windows | `HKLM\SOFTWARE\Policies\Glafira\PostgreSQL` (GPO, Intune) — пример `admin/policy.reg` |
| Linux | `/etc/io.github.vvnovg.glafira.postgres/policy.json` — пример `admin/policy.json` |

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `updatesEnabled` | bool (`dword` 0/1 в реестре) | `true` | `false` — приложение не обращается к серверу обновлений |
| `updateUrl` | строка, только `https://` | публичный `latest.json` | зеркало с одобренными версиями (формат — `latest.json` Tauri). Адрес `http://` считается ошибкой политики: обновления выключаются |
| `language` | строка: `en`, `ru` | язык ОС или выбор пользователя | язык интерфейса для всех; пользователь его не меняет. Неизвестный код — ошибка политики (показывается в «О программе»), язык не задаётся, обновления не выключаются |

Ключ `licenseKey` прежних сборок больше не используется: все функции бесплатны, ключ игнорируется, как любой
неизвестный, с предупреждением в логе.

Политика читается один раз при запуске: после изменения перезапустите приложение. Неизвестные ключи игнорируются.
На macOS читается только политика уровня устройства: профиль должен быть установлен на устройство (канал устройства MDM,
`PayloadScope` = `System`), тогда он окажется в `/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist`.
Профиль уровня пользователя (`/Library/Managed Preferences/<пользователь>/…`) приложение не читает.
Значения в реестре Windows — строки (`REG_SZ`), флаги — `dword` 0/1. Состояние политики и её ошибки
(нечитаемый файл, неверный тип значения, неизвестный язык) видны в окне «О программе».

### Проверка политики вручную (macOS)
`defaults write` в `/Library/Managed Preferences` на современной macOS не работает (туда пишет только MDM).
Для проверки соберите plist и скопируйте его от имени администратора:

```bash
rm -f /tmp/policy.plist && plutil -create xml1 /tmp/policy.plist
plutil -insert updatesEnabled -bool NO /tmp/policy.plist
sudo mkdir -p "/Library/Managed Preferences"
sudo cp /tmp/policy.plist "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"
sudo chmod 644 "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"
plutil -p "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"
```
Удалить: `sudo rm "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"`.

## Внутреннее зеркало обновлений
Скопируйте из релиза установщики, `*.sig` и `latest.json`, замените в `latest.json` адреса `url` на адреса зеркала
и укажите адрес `latest.json` в `updateUrl`. Подписи остаются прежними: приложение проверяет их встроенным ключом.
Зеркало должно отдаваться по `https://` (по `http` приложение обновления не загружает).

В `latest.json` по записи на каждый тип установки: `darwin-aarch64`, `darwin-x86_64`, `windows-x86_64`,
`linux-x86_64-deb`, `linux-x86_64-rpm`, `linux-x86_64-appimage` и `linux-x86_64` (тоже AppImage — запасная запись).
Сохраните все записи: установка из `.deb` скачивает только `.deb`, из `.rpm` — только `.rpm`.

## Роль для диагностики
```sql
CREATE ROLE glafira_diag LOGIN PASSWORD '…';
GRANT pg_monitor TO glafira_diag;
GRANT pg_signal_backend TO glafira_diag;   -- отмена и завершение сессий
GRANT pg_maintain TO glafira_diag;         -- PostgreSQL 17+: VACUUM и ANALYZE
-- в каждой БД, где нужен анализ запросов (и pg_stat_statements в shared_preload_libraries):
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```
В `pg_hba.conf` нужна строка, разрешающая роли вход с машин пользователей (`scram-sha-256`).

Роль нужна для полной диагностики; без неё приложение подключается, но чек-лист готовности в проверке подключения
покажет, чего не хватает, и подскажет точную команду (`GRANT … TO "glafira_diag";`). `pg_signal_backend` нужен действиям — отмене запросов и завершению сессий (подраздел «Диагностика» → «Действия»); `pg_maintain` нужен для VACUUM и ANALYZE, которых в приложении пока нет; оба права чек-лист проверяет заранее. `pg_maintain` есть только в PostgreSQL 17 и новее;
в более ранних версиях `VACUUM` и `ANALYZE` могут запускать владелец таблицы, владелец базы или суперпользователь.
`CREATE EXTENSION` выполняет суперпользователь; `shared_preload_libraries` меняется только с перезапуском сервера.

Вкладки таблицы, представления и функции читают только системный каталог и статистику, отдельных прав на сами объекты им не нужно.
Исключение — вкладка последовательности: последнее значение и долю использованного диапазона PostgreSQL отдаёт только роли с правом
`SELECT` или `USAGE` на последовательность. Без него вкладка пишет «Нет права на чтение» вместо чисел. Чтобы дать право:
```sql
GRANT SELECT ON ALL SEQUENCES IN SCHEMA shop TO glafira_diag;   -- для каждой схемы; новые последовательности — отдельным GRANT
-- либо, если допустимо чтение всех данных (PostgreSQL 14+):
GRANT pg_read_all_data TO glafira_diag;
```

### Настройки сервера, которые проверяет чек-лист
| Параметр | Значение | Зачем |
|---|---|---|
| `shared_preload_libraries` | содержит `pg_stat_statements` | статистика запросов; на каждом узле |
| `compute_query_id` | `on` (PostgreSQL 14+; `auto` подходит, если `pg_stat_statements` загружен на всех узлах) | связь запросов в `pg_stat_activity` и `pg_stat_statements` |
| `track_io_timing` | `on` | время ввода-вывода запросов (предупреждение, если выключено) |
| `track_activity_query_size` | не меньше `4096` | длинные тексты запросов не обрезаются (предупреждение) |

Необязательные расширения, которые приложение использует, если они установлены в базе:
`hypopg`, `pgstattuple`, `pg_buffercache`, `pg_wait_sampling`, `pg_qualstats`, `pg_stat_kcache`
(`CREATE EXTENSION IF NOT EXISTS <имя>;`, если пакет расширения установлен на сервере).

### Patroni
Роль и расширения создаются на лидере и доезжают до реплик репликацией. Параметры PostgreSQL в кластере Patroni задаёт
Patroni (`patronictl edit-config`, затем `patronictl restart` для `shared_preload_libraries`), а не `postgresql.conf` на узле.
Если в конфигурации Patroni есть раздел `postgresql.pg_hba`, Patroni сам пишет `pg_hba.conf` — строку для роли добавляйте туда.

## Диагностика
Инструменты группы «Диагностика» в дереве подключения (пульс, сессии, idle in transaction, профиль ожиданий, блокировки, горизонт xmin, реплики,
слоты; у кластера Patroni ещё готовность к failover и матрица health) только читают: на узлы PostgreSQL уходят `SELECT`, в REST API Patroni — `GET`.
Ни PostgreSQL, ни Patroni они не меняют; изменения делают только действия (подраздел «Действия» ниже). Что показывает каждый инструмент — глава «Диагностика» руководства пользователя.

### Права
Роль диагностики (`glafira_diag` выше) должна входить в `pg_monitor` с наследованием прав (`INHERIT`, значение по умолчанию): приложение проверяет
`pg_has_role(current_user, 'pg_read_all_stats', 'USAGE')`, а `pg_monitor` включает `pg_read_all_stats`. Он открывает то, что PostgreSQL прячет от обычных ролей:
- тексты запросов и остальные сведения чужих сессий в `pg_stat_activity` (состояние, ожидание, время запроса и транзакции, `xmin`): без права вместо текста стоит
  `<insufficient privilege>`, остальные поля пусты, поэтому списки сессий и блокировок и профиль ожиданий по чужим сессиям почти пусты;
- состояние отправителей WAL и приёмника на репликах (`pg_stat_replication`, `pg_stat_wal_receiver`): без права инструменты «Реплики» и «Горизонт xmin»
  скрывают подробности и пишут об этом, а находки по репликам не строятся;
- размер каталога `pg_wal` (`pg_ls_waldir()`): без права в «Пульсе» стоит прочерк и пометка.

Недоступное из-за прав, как и недоступное в версии PostgreSQL, инструмент перечисляет серыми строками под блоком находок, а не отказывает целиком.
Права `pg_signal_backend`, `pg_maintain` и `REPLICATION` чтению диагностики не нужны. `pg_signal_backend` и `REPLICATION` нужны действиям (подраздел «Действия» ниже); `pg_maintain` приложение пока не использует, чек-лист лишь проверяет его заранее.

### Нагрузка
- Открытая и видимая вкладка инструмента читает данные по умолчанию раз в 5 секунд (в шапке вкладки интервал меняется: 2, 5, 10, 30 секунд или пауза); скрытую вкладку приложение не опрашивает.
  Инструмент узла — несколько коротких запросов к одному узлу (по умолчанию к лидеру или primary); «Пульс» — по одному запросу и отдельному запросу размера `pg_wal` на каждый доступный узел.
- Patroni: топология — `GET /cluster` и `GET /patroni` раз в 10 секунд; вкладки «Готовность к failover» и «Матрица health» по умолчанию обновляются раз в 10 секунд (интервал меняется в шапке вкладки):
  первая читает `GET /config` (его же при каждом обновлении читают «Слоты репликации» у кластера Patroni), вторая — семь адресов проверки здоровья у каждого участника.
- Сэмплер профиля ожиданий — один лёгкий запрос к `pg_stat_activity` раз в секунду на узел, пока открыта вкладка «Профиль ожиданий», в том числе скрытая; закрытие вкладки его останавливает.
  История хранится в памяти приложения (последние 60 минут, не больше 500 000 строк, порядка 40 МБ на узел), на диск не пишется и пропадает при закрытии подключения.
- Соединения на узел: каталог и все вкладки — до 3, опрос топологии — 1, сэмплер — 1 (только пока открыт профиль ожиданий), действие — 1 на время самого действия (подраздел «Действия»); простаивающие закрываются через 5 минут.
  Учитывайте их в `max_connections` и в лимитах роли, умножая на число одновременно работающих копий приложения.
- Запросы идут на сессии только для чтения (`statement_timeout = 5s`, `lock_timeout = 1s`) с `application_name = glafira-pg` (соединение действия не только для чтения, см. «Действия»); тяжёлых блокировок они не берут:
  размеры отношений не считаются, `pg_blocking_pids` вызывается только для сессий, которые ждут блокировку.

### Patroni API
Диагностика обращается к REST API Patroni только методом `GET`: `/cluster` и `/patroni` (топология), `/config` (динамическая конфигурация: готовность к failover, постоянные слоты)
и адреса проверки здоровья каждого участника — `/primary`, `/standby-leader`, `/replica`, `/read-only`, `/sync`, `/async`, `/health` (матрица health).
Адреса проверки здоровья Patroni отдаёт без авторизации, приложение её для них не передаёт; на остальные адреса идёт basic auth из профиля.
Ответ 503 на адрес здоровья — штатное «я не в этой роли», а не ошибка. Срок одного запроса — 5 секунд. Изменяющие вызовы (switchover, failover, restart, пауза) делают только действия Patroni, следующий подраздел.

### Действия
Действия — единственное, что приложение меняет на серверах. Пользователь запускает их кнопкой во вкладках инструментов и в обзоре кластера; перед выполнением приложение показывает предпросмотр и просит подтверждение. Для сессий и слотов предпросмотр заново читает их с сервера; предпросмотр действий Patroni берёт лидера, участников и готовность реплик из последнего опроса топологии (не старше интервала опроса) и заново читает только динамическую конфигурацию и число сессий лидера. Перед отправкой приложение ещё раз проверяет условия действия по последнему опросу: у failover и switchover с выбранным кандидатом — и готовность кандидата, у switchover — что лидер тот же, что в предпросмотре. Что можно сделать:
- отмена запроса и завершение сессии: поштучно и пакетом «idle in transaction старше N минут» (до 500 сессий за действие);
- удаление слота репликации (только неактивного);
- Patroni: switchover (сейчас и по расписанию), failover, restart (сейчас и по расписанию), отмена запланированных switchover и restart, пауза и её снятие.

`VACUUM`, `ANALYZE` и перечитывание конфигурации приложение не выполняет. Как действия выглядят для пользователя — глава «Диагностика» руководства пользователя, разделы «Действия», «Действия Patroni» и «Журнал действий».

**Защита.** На подключении «только чтение» кнопок действий нет, а приложение отказывает и при прямом вызове. На prod нужно ввести имя подключения; для пакета сессий — ещё и их число, для удаления слота — имя слота (в любом окружении), для failover — имя кандидата. Все проверки выполняются в приложении до обращения к серверу.

**Права PostgreSQL.** Роли, под которой открыто подключение, нужны:

| Действие | Что нужно |
|---|---|
| Отмена запроса, завершение сессии | суперпользователь — любая клиентская сессия; членство в `pg_signal_backend` — любая сессия не суперпользователя; без того и другого — только сессии ролей, членом которых является текущая роль |
| Удаление слота репликации | атрибут `REPLICATION` или суперпользователь |

Сессию суперпользователя завершает только суперпользователь: `pg_signal_backend` на неё не распространяется. Чужие сессии предпросмотр видит только с `pg_read_all_stats` (роль `pg_monitor`): без неё сервер не отдаёт время запуска сессии, по которому приложение её адресует. Действие без права не выполняется: в предпросмотре у сессии стоит причина, кнопка удаления слота неактивна с подсказкой.

**Отдельная роль для действий.** Атрибут `REPLICATION` шире удаления слотов: роль с ним может создавать логические слоты и читать через них изменения всех таблиц базы, а при разрешающей строке `replication` в `pg_hba.conf` для неё — снимать копию всего кластера. Поэтому не добавляйте его роли диагностики, которой пользуются все, а выдавайте отдельной роли для действий — и заведите под неё отдельный профиль подключения для тех, кто выполняет действия, — или не выдавайте вовсе: без него кнопка удаления слота неактивна, а пункт чек-листа «Удаление слотов репликации» показывает предупреждение, и для роли диагностики это штатное состояние.
```sql
CREATE ROLE glafira_ops LOGIN PASSWORD '…';
GRANT pg_monitor TO glafira_ops;            -- видеть чужие сессии
GRANT pg_signal_backend TO glafira_ops;     -- отмена и завершение сессий
ALTER ROLE glafira_ops REPLICATION;         -- только если нужно удалять слоты
```

**Соединение действия.** Действие выполняется не на пулах диагностики, а на отдельном соединении, которое открывается на одно действие или пакет и закрывается после него. Оно не «только для чтения» (нет `default_transaction_read_only`), остальные параметры те же: `statement_timeout = 5s`, `lock_timeout = 1s`, `search_path = pg_catalog`, `DateStyle = ISO`, `application_name = glafira-pg`. Соединение идёт через SSH-туннель подключения, если он включён; база данных — из профиля, а у логического слота — его собственная. Пакет выполняется по одной сессии на одном соединении и укладывается в 60 секунд. Ответа на каждый запрос приложение ждёт не дольше 10 секунд (при обрыве сети серверный `statement_timeout` не сработает), а запрос без ответа или закрытое подключение останавливают пакет: оставшиеся сессии не выполняются. Это ещё одно соединение к узлу на время действия: учитывайте его в `max_connections` и в лимитах роли.

**Учётная запись API Patroni.** Действия Patroni отправляют изменяющие запросы с basic auth. Логин задаётся в профиле подключения (поле «Пользователь API»), пароль хранится в системном хранилище секретов (Keychain, Credential Manager, Secret Service) и не попадает ни в `connections.json`, ни в журнал действий, ни в архив диагностики. Без логина кнопки действий Patroni неактивны. Учётная запись должна быть задана в Patroni (`restapi.authentication`). Пароль не уходит на `http://`-адрес, если все адреса API в профиле — `https://`. Запросы:

| Действие | Запрос |
|---|---|
| switchover | `POST /switchover` (`leader`, `candidate`, `scheduled_at`) на API лидера |
| отмена запланированного switchover | `DELETE /switchover` на API лидера |
| failover | `POST /failover` (`candidate`) на API лидера |
| restart | `POST /restart` (`restart_pending`, `schedule`) на API самого участника |
| отмена запланированного restart | `DELETE /restart` на API самого участника |
| пауза и её снятие | `PATCH /config` с `{"pause": true}` или `{"pause": null}` на API лидера |

Запрос к лидеру пробует адреса по порядку: участники, API которых ответил на последний опрос (лидер среди них первым), затем остальные участники, затем адреса профиля, без повторов; при failover лидер молчит, и запрос не ждёт его. Restart и его отмена идут только к API самого участника. К следующему адресу приложение переходит лишь тогда, когда запрос заведомо не дошёл до Patroni (отказ соединения, срок установки соединения — 3 секунды, TLS, туннель). Через SSH-туннель перед действием приложение читает `GET /patroni` того же адреса: если туннель не пробросил соединение к узлу или оно не установилось за 3 секунды, действие на этот адрес не отправляется и пробуется следующий. Запрос, на который Patroni не ответил после отправки, не повторяется. Перенаправления HTTP не выполняются. Срок ответа — 5 секунд, у switchover, failover и restart «сейчас» — до 60 секунд: Patroni отвечает после выполнения. Пока действие наблюдается, топология опрашивается раз в 2 секунды вместо 10.

**Файл `actions.jsonl`.** Журнал действий лежит в каталоге данных приложения (пути по системам — в разделе «Данные и логи» ниже), по одной JSON-записи на действие. На macOS и Linux права на файл 0600; на Windows доступ определяют права каталога профиля пользователя. При 5 МБ файл переименовывается в `actions.1.jsonl`; хранятся текущий файл и одна старая копия. В записи — время, подключение (имя и окружение), узел, подтверждение prod, итог, а также по каждой сессии её данные и **текст запроса — первые 500 символов, литералы остаются как есть** (так при разборе инцидента видно, что именно завершили), у слота — его параметры, у Patroni — метод, адрес без учётных данных, тело и первые 500 символов ответа. Литералы в тексте запроса могут содержать персональные данные и секреты: относитесь к файлу как к конфиденциальному. Отказы защиты в журнал не пишутся. Журнал локален: он лежит на компьютере пользователя, выполнившего действие, общего журнала у приложения нет. В диагностический архив («О программе») файл не входит.

## Сеть
Прямые подключения (профиль без SSH):

| Куда | Порт | Зачем |
|---|---|---|
| Каждый узел PostgreSQL | 5432 (или ваш) | каталог, топология списка узлов, проверка подключения |
| REST API Patroni каждого узла | 8008 (или ваш) | обнаружение участников (`GET /cluster`, `GET /patroni`); диагностика (`GET /config`, адреса проверки здоровья); действия Patroni (`POST`, `PATCH`, `DELETE`) |
| Сервер обновлений | 443 | `github.com` и хосты, куда GitHub перенаправляет загрузку ассетов релизов (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`), — или хост из `updateUrl`; только если обновления не выключены политикой |

Чтение и диагностика вызывают только `GET`: `/cluster`, `/patroni`, `/config` и адреса проверки здоровья (раздел «Диагностика»); basic auth передаётся, если задан в профиле (кроме адресов проверки здоровья, которым авторизация не нужна). Действия Patroni (подраздел «Действия») добавляют `POST`, `PATCH` и `DELETE`. В Patroni
(проверено на 4.1.5) `restapi.allowlist`, обязательная basic auth для небезопасных вызовов и `restapi.verify_client: optional`
действуют только на изменяющие запросы (PATCH, PUT, POST, DELETE), а чтение они не закрывают, поэтому для чтения и диагностики
`restapi.allowlist` менять не нужно. Действиям он нужен: если он задан, изменяющие запросы Glafira проходят только с адресов из него (при SSH-туннеле — с адреса бастиона), а учётная запись из профиля должна быть в `restapi.authentication`. Не добавляйте в allowlist адреса и подсети пользователей, которым действия не положены: он защищает switchover, restart и reinitialize.
Чтение закрывает только `restapi.verify_client: required` (TLS-рукопожатие требует клиентский сертификат): тогда выдайте
пользователям клиентский сертификат и укажите его в профиле кластера в разделе «TLS для API» — профиль поддерживает HTTPS,
свой CA и клиентский сертификат. Если Patroni отдаёт адреса, недоступные с машин пользователей (pod IP, NAT), в профиле
кластера задаётся подмена адресов участников.

Приложение не отправляет телеметрию и отчёты о сбоях и не загружает удалённое содержимое: сетевые соединения — только с серверами PostgreSQL
и REST API Patroni из профилей подключений (при SSH-туннеле — через бастион) и с сервером обновлений.

### Подключения через бастион (SSH)
Если в профиле включён SSH-туннель, с машины пользователя нужен только SSH до бастиона (порт 22 или заданный в профиле; сервер обновлений — как выше):
прямой доступ к узлам PostgreSQL и к REST API Patroni с машин пользователей не нужен. Все соединения профиля, включая REST API Patroni
и проверку подключения, идут через один процесс `ssh` с динамическим пробросом (`-D`, SOCKS5 на `127.0.0.1`). Бастион должен:
- разрешать TCP-проброс: в `sshd_config` `AllowTcpForwarding yes` (это значение по умолчанию; подходит и `local`), а `PermitOpen`, если он задан, должен включать узлы;
- разрешать имена узлов из профиля (хосты, участники Patroni, адреса REST API) и достигать их портов PostgreSQL (5432 или ваш) и REST API Patroni (8008 или ваш):
  имена разрешает бастион, а не машина пользователя, поэтому отдельная подмена адресов участников за туннелем обычно не нужна;
- принимать вход выбранным в профиле способом: ключ из SSH-агента, файл ключа или пароль.

TLS проверяется по исходному имени узла, а не по адресу туннеля. На серверах PostgreSQL соединения приходят с адреса бастиона: строки
`pg_hba.conf` для таких профилей пишите для адреса бастиона. Подробности об OpenSSH, ключах хоста и логах — в разделе «OpenSSH» ниже.

**Порт SOCKS без аутентификации.** Порт `-D` на `127.0.0.1` пароля не спрашивает: пока подключение открыто, им может воспользоваться
любой локальный пользователь той же машины и попасть всюду, куда пускают учётную запись пользователя на бастионе, — не только к узлам
PostgreSQL, но и, например, к etcd (`:2379`) и к изменяющим вызовам REST API Patroni. На однопользовательском компьютере это неважно.
На многопользовательском (общий Linux-хост для прыжков, Windows RDS/Citrix) либо ограничьте проброс на бастионе, либо не используйте туннель:
- `AllowTcpForwarding` только для тех, кому туннель нужен (`AllowTcpForwarding no` глобально и `yes` в `Match User …`/`Match Group …`);
- `PermitOpen` в том же `Match` (или `permitopen="хост:порт"` у ключа в `authorized_keys`) — только порты PostgreSQL и REST API Patroni
  нужных узлов, например `PermitOpen pg-1:5432 pg-1:8008 pg-2:5432 pg-2:8008`. Имена сравниваются с запросом как строки, без разрешения
  в адреса: перечислите их так, как они записаны в профилях (хосты, участники Patroni, адреса API).

Кроме того, порт выбирается заранее: приложение открывает и сразу закрывает слушатель на `127.0.0.1:0`, а порт занимает ssh — уже после
входа на бастион. В этот короткий промежуток порт может занять другой локальный процесс; на общей машине это ещё один довод против туннеля.

### Как приложение выглядит на сервере
- Соединения идут с `application_name = glafira-pg`: по нему их видно в `pg_stat_activity`.
- Сессии открываются только на чтение: `default_transaction_read_only = on`, `statement_timeout = 5s`, `lock_timeout = 1s`. Исключение — соединение действия (подраздел «Диагностика» → «Действия»): без `default_transaction_read_only`, остальные пределы те же.
  Кроме того, на сеансе задаются `search_path = pg_catalog` и `DateStyle = ISO`: определения объектов и DDL, которые строит приложение, всегда содержат имена схем, а даты в них — в формате ISO.
- Не больше 3 соединений на каждую связку «подключение, узел, база», плюс по одному для опроса топологии и, пока открыт профиль ожиданий, для сэмплера (см. «Диагностика»); простаивающее закрывается через 5 минут. Учитывайте их в `max_connections` и в лимитах роли.
- Проверка подключения («Проверить») не использует этот пул: она открывает свои короткоживущие соединения к узлам (на каждом узле
  несколько за время проверки) и закрывает их по окончании. Запас в `max_connections` и в лимитах роли нужен и для них.
- Топология опрашивается раз в 10 секунд.

## OpenSSH
SSH-туннель использует системный клиент `ssh` (OpenSSH): своего ssh в приложении нет. Клиент ищется в `PATH`; на Windows ещё и в
`%SystemRoot%\System32\OpenSSH` (дополнительный компонент «Клиент OpenSSH»). Не найден — ошибка «OpenSSH client (ssh) was not found» с подсказкой.
Учитываются `~/.ssh/config` пользователя, ProxyJump, агент и аппаратные ключи.

**Версия.** Пароль и пассфраза ключа приложение передаёт через askpass (`SSH_ASKPASS_REQUIRE=force`), а он появился в OpenSSH 8.4:
с более старым клиентом эти способы недоступны (ошибка с объяснением), а агент и ключ без пассфразы работают на любой версии.
В Windows 10 встроен OpenSSH 8.1: для пароля и пассфразы установите Win32-OpenSSH 8.4 или новее и проверьте, что в `PATH` он стоит
раньше встроенного `%SystemRoot%\System32\OpenSSH`; агент и ключ без пассфразы работают и со встроенным клиентом.
Версия клиента видна в шаге «SSH» проверки подключения. На Windows пароль и пассфразу через askpass перед релизом проверяют вручную
(`docs/release-checklist.md`); агент и ключ без пассфразы от askpass не зависят.

**Как запускается ssh.** По одному процессу на открытое подключение:
```
ssh -N -T -E <каталог логов>/ssh-<id>.log -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3
    -o StrictHostKeyChecking=ask -o NumberOfPasswordPrompts=1 -o BatchMode=no -o ControlMaster=no -o ControlPath=none
    [-p <порт>] [-l <пользователь>] [-i <ключ> -o IdentitiesOnly=yes -o PreferredAuthentications=publickey | -o PreferredAuthentications=password]
    -D 127.0.0.1:<порт SOCKS> -- <цель>
```
Опции командной строки главнее `~/.ssh/config`. `ControlMaster=no` и `ControlPath=none` изолируют туннель от общих соединений (`ControlMaster auto`):
туннель не присоединяется к чужому сеансу пользователя и не становится мастером, закрытие которого оборвало бы его сеансы. Порт SOCKS слушает
только `127.0.0.1`. Обрыв связи обнаруживается за минуту (`ServerAliveInterval` 15 с, три пропуска); перезапуск идёт с паузами 1, 2, 5, 10, затем 30 секунд.
После отказа во входе (неверный пароль, отклонённый ключ, заблокированный агент вроде 1Password, ключ хоста не подтверждён или изменился, `ssh` не найден)
повторы прекращаются до «Переподключить»: так устаревший пароль не вызывает неудачный вход раз в 30 секунд, чего хватило бы для блокировки учётной записи
(`pam_faillock`, AD, fail2ban). Не забывайте и о проверке подключения: каждый запуск «Проверить» (и для сохранённого подключения) открывает собственный туннель, то есть делает один дополнительный вход на бастион; при неверном пароле это одна неудачная попытка, без повторов.

**Askpass.** В режиме askpass приложение запускает само себя: путь к его исполняемому файлу ssh получает в `SSH_ASKPASS`, а пароль или пассфразу
процесс askpass читает из системного хранилища секретов (ключи `sshPassword` и `sshPassphrase`). Пассфраза отдаётся только на стандартный запрос OpenSSH
`Enter passphrase for …`; запросы кодов подтверждения и прочие вопросы сервера остаются без ответа. На macOS в неподписанной сборке (например, собранной локально) доступ
второго процесса к Keychain может вызвать запрос разрешения.

**Ключи хоста.** Неизвестный ключ бастиона приложение показывает пользователю с отпечатком; после «Доверять и подключиться» ключ в `~/.ssh/known_hosts` записывает сам ssh.
Приложение `~/.ssh/config` и `~/.ssh/known_hosts` не редактирует. Подтверждение хранится в памяти до выхода из приложения. Для управляемого парка
ключи бастионов можно раздать заранее в общесистемный `/etc/ssh/ssh_known_hosts` (macOS и Linux): тогда диалога нет. Ключ хоста, который изменился,
приложение не принимает: пользователь исправляет `known_hosts` сам (`ssh-keygen -R <хост>`) после проверки у администратора.

**Логи и служебные файлы.** Вывод каждого процесса `ssh` пишется в `ssh-<id подключения>.log` в каталоге логов, предыдущий запуск — в `ssh-<id подключения>.1.log`;
оба файла входят в архив диагностики, паролей в них нет. Файлы `ssh-unsaved-….log` — временные туннели проверки подключения: каждый запуск «Проверить», в том числе для сохранённого подключения, открывает свой туннель под временным id `unsaved-<uuid>`; следующий запуск приложения эти файлы убирает.
В каталоге данных лежит `tunnels.json` (права 0600): PID запущенных процессов `ssh` и путь их лога. Если приложение завершилось аварийно, при следующем старте
оно завершает процессы из этого файла (только те, в командной строке которых есть имя их лога `ssh-<id>.log`, так что чужой процесс с тем же PID не пострадает); то же приложение делает при выходе.
На Windows это делается через PowerShell. Файл руками не правьте.

**Ограничение.** Защиты от второго экземпляра приложения нет: второй запуск при старте завершает процессы `ssh`, записанные в `tunnels.json`, в том числе туннели первого экземпляра.
Предупредите пользователей: приложение должно быть запущено один раз.

|---|---|---|---|

В каталоге данных лежат `connections.json` (профили без паролей), `settings.json`, `tunnels.json` (процессы `ssh` открытых туннелей, см. «OpenSSH») и `actions.jsonl` (журнал действий, см. «Диагностика» → «Действия»; рядом при ротации появляется `actions.1.jsonl`);

На Unix у такого файла должны быть права 0600 (`chmod 0600 ~/.pgpass`): как в libpq, файл, доступный группе или всем
(`mode & 0o077`), игнорируется, и в журнале остаётся только предупреждение.
Окно «О программе» показывает эти каталоги и собирает диагностический архив (версия, логи приложения и туннелей, профили без паролей; `actions.jsonl` в архив не входит);
приложение ничего не отправляет — архив пользователь прикладывает к обращению сам.
