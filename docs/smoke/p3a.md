# Смоук P3a «Видеть» — топ запросов, карточка, EXPLAIN, консоль

Сборка: `pnpm tauri dev`. Стенд: `docker compose -f dev/docker-compose.yml up -d --no-recreate pg-perf` (`localhost:5471`, база `perf`; dev/perf/README.md),
для шага 15 — матрица версий (`docker compose -f dev/docker-compose.yml --profile matrix up -d --no-recreate`, затем `scripts/wait-matrix.sh`),
для шага 14 — одиночный сервер `localhost:5460` из основного стенда. Шаги идут по порядку: часть шагов опирается на данные предыдущих.

**Нагрузка.** **Живой контейнер `gp-pg-perf` может нести `/perf/heavy.sql` старого образа** (12 инструкций, в которых соседние id считались прямо в запросе, так что N+1 недостижим): образ обновится, когда владелец пересоздаст контейнер. Проверьте это до запуска нагрузки, чтобы не стартовать два `pgbench`: `docker exec gp-pg-perf grep -c cid1 /perf/heavy.sql` печатает `0` у старого сценария. Если напечатан `0`, запускайте нагрузку со свежим файлом (вариант ниже), иначе — основной командой.

Сначала сбросить статистику (от интеграционных тестов и прошлых прогонов в ней остаются вызовы, и доля самого частого запроса, а с ней находка N+1, искажается), затем запустить основную нагрузку на час (смоук идёт дольше десяти минут: шаги 3 и 6 ждут минуты):

    docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT pg_stat_statements_reset()"
    docker exec -d gp-pg-perf pgbench -n -U postgres -d perf -f /perf/heavy.sql -c 4 -T 3600

Если проверка напечатала `0`, вместо команды `pgbench` выше:

    docker cp dev/perf/heavy.sql gp-pg-perf:/tmp/heavy.sql
    docker exec -d gp-pg-perf pgbench -n -U postgres -d perf -f /tmp/heavy.sql -c 4 -T 3600

В `heavy.sql` 13 инструкций; три из них — точечный выбор покупателя по `:cid`, `:cid1` и `:cid2` — нормализуются в один `queryid` (~23 % вызовов).

Остановить нагрузку (не `pkill`: его в образе может не быть):

    docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE application_name = 'pgbench'"

Подключения создаются кнопкой «+» над деревом (окружение `dev`, пароли — известные пароли стенда):
- `perf-diag` — сервер `localhost`, порт `5471`, база `perf`, роль `glafira_diag` / `glafira-secret` (`pg_monitor`, `pg_read_all_data`, прав записи в `shop` нет); шаги 1–7 и 11–13;
- `perf-app` — тот же сервер и база, роль `glafira_app` / `app-secret` (права записи в `shop`, не `pg_monitor`), флажок «Только чтение» снят; шаги 8–10;
- `single` — порт `5460`, база `postgres`, роль `glafira_diag` / `glafira-secret`; шаг 14;
- `m13-diag` и `m15-diag` — порты `5513` и `5515`, база `postgres` (там создан `pg_stat_statements`), роль `glafira_diag` / `glafira-secret`; шаг 15.

1. **Готовность.** Форма `perf-diag` → «Проверить»: пункты «pg_stat_statements.track_planning» — Включён, «Чтение таблиц приложения (EXPLAIN)» — Разрешено, расширения hypopg, pg_stat_kcache, pg_wait_sampling — установлены.
2. **Топ «с момента сброса».** Дерево → `perf-diag` → Диагностика → Запросы (режим «С момента сброса»): таблица со строками pgbench, тексты появляются через секунду; сортировка по «Вызовов» ставит наверх точечный выбор покупателя `SELECT * FROM shop.customers WHERE id = $1` (три инструкции `heavy.sql` слились в одну строку, около 23 % вызовов). Находки над таблицей: **N+1** («… всех вызовов по … мс (вызовов: …)», подсказка «Похоже на N+1»; порог — доля вызовов от 20 %, среднее до 1 мс, не меньше 1000 вызовов) — на свежем `heavy.sql` она видна уже в основной нагрузке, это и проверяется; «Temp-файлы: … на вызов»; «Попадание в кэш …»; обычно ещё «Планирование … дольше выполнения …» (info: у точечного выбора планирование дороже выполнения). Находка «Нестабильное время: stddev … при среднем …» на запросе `SELECT count(*) FROM shop.audit WHERE order_id = $1 AND id BETWEEN $2 AND $3` может появиться: среднее этого запроса около 1 мс, то есть на пороге правила, поэтому её отсутствие отказом не считается. «Топ неполный» на стенде не появится: при `pg_stat_statements.max = 5000` вытеснений нет. Подвал — `pg_stat_statements 1.11` и время сброса статистики. Флажок «Только верхний уровень» виден и включён. Если N+1 нет, а `grep` из преамбулы показал `0` — подложить свежий файл и перезапустить нагрузку, а при невозможности — шаг 17.
3. **Окно.** Режим «За 5 мин»: пока минута не прошла, значок «Идёт первый тик сэмплера…», затем «Накоплено 1 из 5 мин» и строки с дельтами; значок растёт раз в минуту — дождаться «Накоплено 5 из 5 мин» (около пяти минут после открытия инструмента). Заголовки «Stddev» и «Max» неактивны (подсказка «Недоступно для этой версии или режима»). Закрыть вкладку «Запросы» (открытых карточек запросов этого узла быть не должно — пока карточка открыта, сбор не останавливается), подождать три минуты (промежуток засчитывается после 2,5 минут), открыть снова — таблица продолжается с прежними данными.
4. **Карточка.** Вернуться в режим «С момента сброса». Кнопка «Открыть запрос» у находки N+1 открывает вкладку запроса `SELECT * FROM shop.customers WHERE id = $1`: в её находках кнопки «Открыть запрос» нет, стоит строка «Промежутков в истории: 1» (сразу), а разрыв на обоих спарклайнах появляется после следующего тика (до минуты): первый тик после паузы только задаёт базу и точки истории не добавляет. Затем клик по строке «SELECT count(*) FROM shop.orders WHERE status = $1» (дальше шаги идут в этой карточке): заголовок вкладки — начало текста, текст запроса с кнопкой «Копировать текст запроса», метрики в две колонки («С момента сброса» и «За 60 мин»), спарклайны растут по минутам, экземпляры (при работающем pgbench); блок «Ожидания» с подсказкой «Откройте «Профиль ожиданий», чтобы собирать ожидания этого запроса», если эта вкладка в сеансе ещё не открывалась (буфера активности нет); открыть «Профиль ожиданий», через несколько секунд вернуться в карточку и нажать «Обновить» — появится таблица событий (если «Профиль ожиданий» открывали раньше, таблица есть сразу); «Таблицы появятся после первого плана» и ссылка «Получить план».
5. **План и ANALYZE чтения.** «Получить план» (или подвкладка «План» → «План»): флажок GENERIC_PLAN включён; дерево с Seq Scan on shop.orders (под Gather — Parallel Seq Scan) и выделенным горячим узлом; в «Обзоре» появилась таблица shop.orders со ссылкой на вкладку таблицы. Поле значения `$1` видно и при включённом GENERIC_PLAN (над полем подсказка, что флажок действует только на «План»): ввести `disputed`, не снимая флажка, «План с выполнением» — факт, буферы, ярус «чтение», без подтверждения; в журнале действий записи нет. «Копировать как текст» (вставить в любой редактор): после дерева идёт строка `Settings: …` (на pg-perf в ней есть `work_mem = '1MB'`), затем Planning Time. Снять GENERIC_PLAN, «План» — план строится по значению из поля.
6. **План из текста выполняющегося экземпляра.** Один раз выполнить запрос, чтобы его нормализованный текст попал в `pg_stat_statements`, затем запустить его же надолго (литералы обоих запусков числовые с точкой — иначе `queryid` разный):
   `docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT pg_sleep(0.1), count(*) FROM shop.customers WHERE region = 'eu'"`;
   `docker exec -d gp-pg-perf psql -U postgres -d perf -c "SELECT pg_sleep(180.0), count(*) FROM shop.customers WHERE region = 'eu'"`.
   В «Запросы» поставить «Строк» 200, обновить («Обновить»), найти строку `SELECT pg_sleep($1), count(*) FROM shop.customers WHERE region = $2`, открыть её. В течение пяти секунд в блоке «Выполняющиеся экземпляры» появляется строка с PID, состоянием `active` и ожиданием `Timeout:PgSleep`. Подвкладка «План» → «Текст запроса» → «Выполняющийся экземпляр PID …» (текст со значением `'eu'`, полей параметров нет) → «План» — дерево Finalize Aggregate → Gather → Partial Aggregate → Parallel Seq Scan on shop.customers с фильтром `region = 'eu'`; план приходит сразу, `pg_sleep` не ждётся: это EXPLAIN без выполнения. Когда экземпляр закончится (через три минуты), пункт остаётся в списке, а текст в форме — тот, что был выбран.
7. **Права на запись.** Консоль EXPLAIN (из дерева) на `perf-diag`, база `perf`: `UPDATE shop.balances SET balance = balance + 1 WHERE customer_id = 1` → «План» → сообщение «Не хватает прав: EXPLAIN пишущей инструкции требует прав INSERT/UPDATE/DELETE на её таблицы даже без выполнения» (а не подсказка про `pg_read_all_data`); `SELECT balance FROM shop.balances WHERE customer_id = 1` → «План» строит дерево.
8. **Запись.** Консоль на `perf-app` (база `perf`), тот же `UPDATE`: «План с выполнением» → окно «Выполнить запрос и откатить» со списком `shop.balances` и предупреждением («Откат отменяет изменения строк, в том числе сделанные триггерами, а NOTIFY не доставляется. Не отменяются сдвиг последовательностей, внешние вызовы (dblink, http) и нетранзакционные функции… Блокировки держатся, пока запрос выполняется.») → «Выполнить и откатить» → дерево с Update on shop.balances, в сводке «Ярус: запись»; журнал действий — строка «EXPLAIN ANALYZE (запись)» с объектом `shop.balances`, при раскрытии — база, срок и начало текста. `docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT balance FROM shop.balances WHERE customer_id = 1"` — значение то же, что до шага.
9. **Защита.** Изменить `perf-app`: поставить «Только чтение» → для `UPDATE` «План с выполнением» даёт подсказку «Запись недоступна: подключение только для чтения», `SELECT` выполняется. Снять «Только чтение» и сменить окружение на `prod` (у существующего подключения флажок при смене окружения сам не меняется — убедиться, что он снят; сам он ставится только у нового подключения): для `UPDATE` окно подтверждения просит ввести имя подключения (`perf-app`), пока оно не введено, «Выполнить и откатить» недоступна; «Отмена» закрывает окно, новой записи в журнале нет. Вернуть окружение `dev`.
10. **Побочный эффект.** Перед шагом: `docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT count(*) FROM pg_largeobject_metadata"`. Консоль на `perf-app`: `SELECT lo_creat(-1)` → «План с выполнением» → сообщение «Запрос пишет данные (volatile-функция или триггер)…», подсказка «Запрос пишет данные в транзакции только для чтения.» и кнопка «Выполнить как запись» → окно подтверждения (таблиц в нём нет) → «Выполнить и откатить» → дерево Result, ярус «запись»; журнал действий — новая строка «EXPLAIN ANALYZE (запись)» (объект — база `perf`); тот же `count(*)` в psql не изменился (откат отменил создание объекта).
11. **Ошибки и параметры.** Консоль на `perf-diag`: `SELECT 1; SELECT 2` → «План» → «Введите ровно одну инструкцию»; `SELECT pg_sleep(10)` со сроком 5 с → «План с выполнением» → «План не получен за отведённое время; выполнение прервано, изменений нет»; `SELEC 1` → «Сервер отверг запрос: …» и «Ошибка в строке 1, позиция 1» с отмеченным символом. Параметры: `SELECT '$5', $1` → «Параметры (1)», одно поле `$1` (`$5` в литерале не считается); `SELECT $101` → «Параметры (101)», вместо полей сообщение «Параметров больше 100 (всего: 101)…», «План с выполнением» неактивна, «План» (с GENERIC_PLAN) строит дерево Result; после снятия флажка `GENERIC_PLAN` неактивной становится и кнопка «План».
12. **Вставка плана.** «Вставить план» ← вывод `docker exec gp-pg-perf psql -U postgres -d perf -c "EXPLAIN (FORMAT JSON) SELECT 1"` целиком (с `QUERY PLAN` и `+`) → «Разобрать» → дерево «Result», без обращения к серверу. Затем вывод `docker exec gp-pg-perf psql -U postgres -d perf -c "EXPLAIN (ANALYZE, TIMING OFF, FORMAT JSON) SELECT count(*) FROM shop.customers"` → дерево с фактическими строками и циклами, в колонке времени у узлов «—», выделены узлы с наибольшей стоимостью.
13. **Для LLM.** В карточке запроса `status = $1` (шаг 4) «Скопировать для LLM» → в буфере markdown с разделами «Среда», «Запрос», «Статистика» (таблицы «С момента сброса» и «Окно до 60 мин (за время работы сэмплера)»), «План» (с строкой `Settings: …` после дерева), «Таблицы» и DDL `shop.orders`. В консоли с запросом `SELECT count(*) FROM shop.orders WHERE status = 'disputed'` та же кнопка даёт markdown без раздела «Статистика», а в блоке запроса — литерал `'disputed'` как введён.
14. **pg-single.** Подключение `single` (`localhost:5460`, база `postgres`, `glafira_diag` / `glafira-secret`): инструмент «Запросы» показывает «Статистика запросов (pg_stat_statements): pg_stat_statements не установлен в этой базе (CREATE EXTENSION pg_stat_statements)», таблицы нет.
15. **Матрица версий.** `m13-diag` (PostgreSQL 13, `pg_stat_statements` 1.8): «Запросы» — таблица строится, заголовок «JIT» неактивен (подсказка «Недоступно для этой версии или режима»; JIT в `pg_stat_statements` — с 1.10), в подвале «pg_stat_statements 1.8» и «track_planning выключен: колонки планирования пустые»; клик по любой строке — в карточке под находками стоит пометка «Выполняющиеся экземпляры (query_id): только с PostgreSQL 14», а в блоке «Выполняющиеся экземпляры» нет ни таблицы, ни слов «Сейчас не выполняется»; остальное (метрики, находки) на месте. `m15-diag` (PostgreSQL 15, `pg_stat_statements` 1.10, GENERIC_PLAN нет — он с 16): `docker exec gp-pg15 psql -U postgres -d postgres -c "SELECT * FROM pg_class WHERE relname = 'pg_class'"`, затем в «Запросы» (режим «С момента сброса», «Строк» 200) строка `SELECT * FROM pg_class WHERE relname = $1` → карточка → «План»: флажка GENERIC_PLAN нет, одно поле `$1` вместо него; ввести `pg_class` → «План» строит дерево по `pg_class`; «План с выполнением» — ярус «чтение», без подтверждения. Заголовок «JIT» активен.
16. **Справка.** F1 на вкладке «Запросы» открывает главу «Запросы» (раздел «Топ запросов»), на карточке — раздел «Карточка запроса», в консоли — «Консоль EXPLAIN».
17. **Запасной вариант N+1 (только для старого стенда, когда свежий `heavy.sql` недоступен).** Остановить нагрузку (команда из преамбулы), сбросить статистику и запустить цикл одной инструкции:
    `docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT pg_stat_statements_reset()"`;
    `docker exec gp-pg-perf sh -c "printf '%s\n' '\\set cid random(1, 200000)' 'SELECT * FROM shop.customers WHERE id = :cid;' > /tmp/n1.sql && pgbench -n -U postgres -d perf -f /tmp/n1.sql -c 4 -T 120"`.
    Через минуту в «Запросы» («С момента сброса») — находка N+1 на `SELECT * FROM shop.customers WHERE id = $1` (почти все вызовы). Этот шаг последний: он гасит основную нагрузку и сбрасывает статистику, поэтому шаги 2–6 после него не повторяются без перезапуска нагрузки и минуты ожидания.
