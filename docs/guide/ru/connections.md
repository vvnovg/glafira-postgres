# Подключения

В этой главе — виды подключений, вставка строки подключения, SSH-туннель, настройки Patroni и чек-лист готовности. Подключение создаётся и правится в форме: нажмите «+» над деревом подключений или выберите [[ui:sidebar.editConnection]] в меню подключения (⋯).

## Виды подключений {#kinds}

В поле [[ui:connections.form.kind]] три значения:

- [[ui:connections.form.kinds.server]] — один сервер PostgreSQL: хост и порт. В дереве нет группы [[ui:sidebar.members]], а роль сервера, primary или реплика, показана рядом с именем подключения.
- [[ui:connections.form.kinds.hostList]] — несколько серверов (до 16), например primary и его реплики без Patroni. Приложение спрашивает каждый сервер, находится ли он в восстановлении, поэтому primary определяется автоматически, как в JDBC-адресе с несколькими хостами. Если primary нет или их несколько, обзор показывает предупреждение (несколько primary могут означать split-brain). [[ui:connections.form.target]] задаёт, с какого узла по умолчанию читается каталог: [[ui:connections.form.targets.primary]], [[ui:connections.form.targets.standby]], [[ui:connections.form.targets.preferStandby]] или [[ui:connections.form.targets.any]].
- [[ui:connections.form.kinds.patroni]] — кластер Patroni. Вместо узлов вы указываете от 1 до 8 адресов в поле [[ui:connections.form.patroniUrls]]. Приложение читает участников, их роли, отставание и таймлайн из REST API Patroni и подключается к PostgreSQL каждого участника по адресу, который сообщает Patroni.

Чтобы превратить список узлов в кластер Patroni, отметьте [[ui:connections.form.underPatroni]]: адреса API заполнятся из хостов, с портом 8008.

Узлы опрашиваются раз в 10 секунд. Для списка узлов и кластера Patroni меню подключения позволяет выбрать узел, с которого читается каталог: [[ui:sidebar.catalogDefault]] или по одному пункту на каждый узел («Каталог — с узла …»). Если выбранный узел станет недоступен, каталог читается с узла по умолчанию, и дерево сообщает об этом.

## Строка подключения {#connection-string}

Вставьте строку подключения в поле [[ui:connections.form.connstr]] и нажмите [[ui:connections.form.connstrApply]]. Поля формы заполнятся, а строка из поля исчезнет. Понимаются три формата:

- JDBC: `jdbc:postgresql://h1:5432,h2:5433/orders?user=app&targetServerType=primary&ssl=true`
- URI: `postgresql://app:secret@h1,h2:5433/orders?target_session_attrs=read-write&sslmode=verify-full` (подходит и `postgres://`)
- conninfo: `host=h1,h2 port=5432,5433 dbname=orders user=app sslmode=require`

Один хост даёт [[ui:connections.form.kinds.server]], несколько хостов — [[ui:connections.form.kinds.hostList]]; кластер Patroni строка не задаёт никогда. У каждого хоста может быть свой порт; иначе берётся общий `port`, иначе 5432. Также заполняются пользователь, база, `sslmode`, файлы CA, сертификата и ключа, таймаут подключения и целевой узел (`target_session_attrs`, `targetServerType`). Строка JDBC с `ssl=true` без `sslmode` означает `verify-full`, как в JDBC-драйвере PostgreSQL.

Пароль из строки попадает в поле пароля и при сохранении подключения записывается в системное хранилище секретов, но не в `connections.json`. Если пароль не сохранён, приложение использует `~/.pgpass`, как `psql`. Unix-сокеты не поддерживаются.

Параметры, которые приложение не использует (`ApplicationName`, `currentSchema`, `options` и другие), пропускаются. Это не ошибка: они перечислены под полем после слов «Не распознано и пропущено».

## SSH-туннель {#ssh}

Если узлы доступны только через бастион (промежуточный хост), включите [[ui:connections.form.ssh.enabled]] в разделе [[ui:connections.form.ssh.section]]. Тогда все соединения профиля идут через туннель: узлы PostgreSQL, REST API Patroni, проверка подключения.

**Как это работает.** Приложение запускает системный клиент OpenSSH, по одному процессу `ssh` на подключение, с динамическим пробросом (`-D`): это порт SOCKS5, который слушает только 127.0.0.1. Имена узлов разрешает бастион, а не ваш компьютер, поэтому бастион должен видеть узлы по именам, записанным в профиле: хосты, участники Patroni, адреса API. Новым участникам Patroni дополнительная настройка не нужна. Сертификаты TLS проверяются по исходному имени хоста, а не по 127.0.0.1. На бастионе sshd должен разрешать проброс (`AllowTcpForwarding yes`).

**Поля.**

- [[ui:connections.form.ssh.target]] — имя хоста или алиас из `~/.ssh/config`. Всё, что вы там настроили, учитывается: ProxyJump, SSH-агент, аппаратные ключи, параметры отдельных хостов.
- [[ui:connections.form.ssh.port]] и [[ui:connections.form.ssh.user]] — оставьте пустыми, чтобы взять значения из `~/.ssh/config`.
- [[ui:connections.form.ssh.auth]] — как входить на бастион:
  - [[ui:connections.form.ssh.auths.agent]] — ключи из SSH-агента, включая агентов менеджеров паролей и аппаратные ключи. В приложении ничего не хранится.
  - [[ui:connections.form.ssh.auths.key]] — файл закрытого ключа; выберите его в поле, которое появится ниже. Серверу предлагается только этот ключ. Для зашифрованного ключа введите ещё и [[ui:connections.form.ssh.passphrase]].
  - [[ui:connections.form.ssh.auths.password]] — пароль для входа, вводится в поле [[ui:connections.form.ssh.password]].

Пассфраза и пароль хранятся в системном хранилище секретов, а не в `connections.json`, файлах экспорта, архиве диагностики и логах.

**Версия OpenSSH.** Для пароля и пассфразы ключа нужен OpenSSH 8.4 или новее: приложение передаёт их через собственный запрос ssh, а более старые клиенты этого не умеют. SSH-агент и ключ без пассфразы работают на любой версии. Приложение отвечает только на стандартные запросы пароля и пассфразы ключа; одноразовые коды и другие вопросы сервера ответить не могут, поэтому для такого бастиона используйте агент или ключ. Если `ssh` не найден, установите клиент OpenSSH (Windows: дополнительный компонент «Клиент OpenSSH»).

**Первый вход: ключ хоста.** Если ключа бастиона ещё нет в `~/.ssh/known_hosts`, приложение показывает диалог [[ui:hostKey.title]] с полями [[ui:hostKey.host]] и [[ui:hostKey.fingerprint]]. Сверьте отпечаток с тем, что дал вам администратор. Кнопка [[ui:hostKey.trust]] повторяет то, что вы делали (подключение, переподключение или проверку), а ключ в `~/.ssh/known_hosts` записывает сам OpenSSH; приложение этот файл не редактирует. Если отказаться, ничему не доверяется.

**Ключ хоста изменился.** Приложение сообщает, что ключ хоста бастиона изменился, и ничего не предлагает нажать: это может быть атака. Уточните у администратора, затем исправьте `~/.ssh/known_hosts` сами, например командой `ssh-keygen -R <хост>`.

**Проверка.** [[ui:connections.form.test]] начинается с шага [[ui:test.step.ssh]]: он показывает версию OpenSSH и что туннель поднят. У подключения без туннеля шаг сообщает [[ui:test.sshNotUsed]].

**Потеря туннеля.** Если процесс `ssh` завершился, например из-за пропавшей сети (обрыв замечается примерно за минуту), подключение получает состояние [[ui:sidebar.state.degraded]], узлы за туннелем помечаются недоступными, а приложение перезапускает туннель с паузами 1, 2, 5 и 10 секунд, затем каждые 30 секунд.

Отказ во входе — другое дело. Если бастион отклонил вход (неверный пароль, неподходящий ключ, агент, который в данный момент заблокирован), либо ключ хоста не подтверждён или изменился, либо `ssh` не найден, приложение перестаёт повторять попытки, чтобы не сыпать неудачными входами на бастион. Подключение остаётся в состоянии [[ui:sidebar.state.degraded]], пока вы не устраните причину и не выберете [[ui:sidebar.reopen]] в меню подключения.

**Ошибки.** Два сообщения означают, что туннель работает, но узел недоступен с бастиона: «Бастион … не смог достучаться до узла (проброс не удался)» и «Бастион не смог подключиться к хост:порт». Проверьте, что имя узла разрешается на бастионе и что его порт открыт оттуда. Второе сообщение появляется и тогда, когда туннель только что остановился; причина — в подробностях под сообщением.

**Логи.** Вывод каждого процесса `ssh` пишется в `ssh-<id подключения>.log` в папке логов (её путь показан рядом с пунктом [[ui:about.logDir]] на экране [[ui:sidebar.about]]); `ssh-<id подключения>.1.log` — предыдущий запуск. Оба файла попадают в архив диагностики.

**Ограничение.** Запускайте только одну копию приложения: вторая копия при старте завершает процессы `ssh`, найденные от прошлого запуска, в том числе процессы первой копии.

## Patroni {#patroni}

Для подключения вида [[ui:connections.form.kinds.patroni]] укажите REST API Patroni в поле [[ui:connections.form.patroniUrls]]: от 1 до 8 адресов, начинающихся с `http://` или `https://`, без `user:password@`. Приложение опрашивает их по порядку, пока один не ответит; список участников берётся из `GET /cluster`. Приложение только читает: кластер оно не меняет.

- [[ui:connections.form.patroniUser]] и [[ui:connections.form.patroniPassword]] — basic-аутентификация, если API её требует. Пароль попадает в системное хранилище секретов. Если все адреса API у вас `https://`, приложение не отправляет пароль участнику, который сообщил адрес `http://`.
- [[ui:connections.form.apiTls]] — настройки TLS для адресов `https://`: файл CA вместо системных корней, проверка имени хоста и клиентский сертификат (PEM или PKCS#12). Клиентский сертификат нужен, если Patroni его требует (`restapi.verify_client: required`).
- [[ui:connections.form.overrides]] — для участников, чьи адреса, сообщённые Patroni, недоступны с вашего компьютера (IP пода, NAT). Для имени участника задайте хост и порт PostgreSQL и адрес его API. За SSH-туннелем имена, которые сообщает Patroni, разрешает бастион, поэтому там подмена обычно не нужна.

В дереве и в обзоре участники показаны с ролями (Leader, Sync, Replica), отставанием и таймлайном. Если API Patroni перестаёт отвечать, приложение продолжает показывать последние известные данные и предупреждение.

## Чек-лист готовности {#readiness}

Нажмите [[ui:connections.form.test]] в форме: подключение проверяется без сохранения. Шаги идут один за другим: [[ui:test.step.ssh]], [[ui:test.step.patroni]] (только для кластера Patroni), [[ui:test.step.discovery]], затем [[ui:test.step.node]] для каждого узла (TCP, TLS, вход, версия, роль) и в конце [[ui:test.step.readiness]]. Упавший шаг показывает ошибку и её подробности; для ошибок SSH это последние строки вывода `ssh`.

Список [[ui:test.readinessTitle]] показывает, что приложению нужно для полной диагностики. Каждый пункт имеет статус [[ui:test.readyStatus.ok]], [[ui:test.readyStatus.warn]] или [[ui:test.readyStatus.missing]], говорит, что перестаёт работать без него, и предлагает точную команду SQL или строку конфигурации для копирования:

- [[ui:readiness.monitorRole.title]] — роль суперпользователь или член `pg_monitor`. Без неё не видны запросы других пользователей, `pg_stat_statements` и размер `pg_wal`.
- [[ui:readiness.signalRole.title]] — членство в `pg_signal_backend`.
- [[ui:readiness.maintainRole.title]] — `pg_maintain` (PostgreSQL 17 и новее); до 17 `VACUUM` и `ANALYZE` работают только для собственных таблиц пользователя.
- `pg_stat_statements` — загружен через `shared_preload_libraries` на каждом узле (нужен перезапуск; в Patroni меняйте через `patronictl edit-config`) и создан в базе командой `CREATE EXTENSION`. Создайте его в каждой базе, где нужен анализ запросов.
- `compute_query_id`, `track_io_timing` и `track_activity_query_size` (не меньше 4096).
- Необязательные расширения, которые дают дополнительные проверки, если установлены: `hypopg`, `pgstattuple`, `pg_buffercache`, `pg_wait_sampling`, `pg_qualstats`, `pg_stat_kcache`.

Если роль мониторинга или роль сигналов отсутствует, раздел [[ui:test.roleScript]] открывает скрипт, который создаёт роль `glafira_diag`; тот же скрипт есть в руководстве администратора. См. также [Роль для диагностики](getting-started.md#diagnostics-role). Проверка использует собственные короткоживущие соединения к каждому узлу, поэтому оставьте запас в `max_connections` и в лимитах роли.

Подключение работает и без этих пунктов, но недостающие ограничивают то, что приложение может показать.
