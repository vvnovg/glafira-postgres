# Glafira for PostgreSQL: руководство администратора

## Установка
| ОС | Файл | Тихая установка |
|---|---|---|
| macOS | `Glafira_for_PostgreSQL_<версия>_aarch64.pkg` / `_x64.pkg` | `sudo installer -pkg <файл>.pkg -target /` (Jamf, Intune, Kandji) |
| Windows | `Glafira_for_PostgreSQL_<версия>_x64_en-US.msi` | `msiexec /i <файл>.msi /qn` (SCCM, Intune) — установка на машину |
| Linux | `Glafira_for_PostgreSQL_<версия>_amd64.deb`, `Glafira_for_PostgreSQL-<версия>-1.x86_64.rpm`, `Glafira_for_PostgreSQL_<версия>_amd64.AppImage` | `sudo apt install ./<файл>.deb`, `sudo dnf install ./<файл>.rpm` |

Установщики — в разделе релизов `https://github.com/vvnovg/glafira-postgres-releases/releases`.
Пробелы в именах файлов заменены на `_` при публикации; точные имена смотрите в релизе.
Исполняемый файл приложения — `glafira-pg` (`glafira-pg.exe` на Windows, `/usr/bin/glafira-pg` на Linux).

### Обновление установленного приложения
Встроенное обновление («О программе» → «Проверить обновления») скачивает пакет того же типа, что установлен (на macOS — архив `.app.tar.gz`):

| Установлено из | Что делает обновление | Права |
|---|---|---|
| `.pkg` / `.dmg` (macOS) | заменяет `.app` на месте | если `.app` принадлежит root (установка из `.pkg` в `/Applications`) — запрос пароля администратора |
| `.msi` (Windows, на машину) | запускает новый MSI | UAC; у пользователя без прав администратора обновление не установится |
| `.deb` / `.rpm` (Linux) | ставит новый пакет через `dpkg -i` / `rpm -U` | пароль администратора (pkexec, иначе zenity/kdialog + sudo) |
| `.AppImage` | заменяет файл AppImage | запись в каталог с AppImage |

**Управляемые парки** (SCCM, Intune, Jamf, Kandji, репозиторий пакетов): обычные пользователи без прав
администратора не смогут установить обновление сами. Рекомендуется политика `updatesEnabled = false` и раздача
новых версий теми же средствами, что и установка (на Linux — через свой репозиторий apt/dnf или `apt install ./<файл>.deb`).

## Политика
Приложение читает политику при запуске. Пользователь не может её изменить.

| ОС | Где |
|---|---|
| macOS | профиль конфигурации MDM, домен `io.github.vvnovg.glafira.postgres` (файл попадает в `/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist`) — пример `admin/policy.mobileconfig` |
| Windows | `HKLM\SOFTWARE\Policies\Glafira\PostgreSQL` (GPO, Intune) — пример `admin/policy.reg` |
| Linux | `/etc/io.github.vvnovg.glafira.postgres/policy.json` — пример `admin/policy.json` |

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `updatesEnabled` | bool (`dword` 0/1 в реестре) | `true` | `false` — приложение не обращается к серверу обновлений |
| `updateUrl` | строка, только `https://` | публичный `latest.json` | зеркало с одобренными версиями (формат — `latest.json` Tauri). Адрес `http://` считается ошибкой политики: обновления выключаются |
| `language` | строка: `en`, `ru` | язык ОС или выбор пользователя | язык интерфейса для всех; пользователь его не меняет. Неизвестный код — ошибка политики (показывается в «О программе»), язык не задаётся, обновления не выключаются |
| `mcpEnabled` | bool (`dword` 0/1 в реестре) | `true` | `false` — MCP-шлюз для LLM-ассистентов запрещён: сервер не запускается, выключатель «Разрешить MCP-сервер» в «Настройках» неактивен с пометкой «Отключено вашей организацией», команда `glafira-pg mcp` завершается с ошибкой «MCP is disabled by your organization». `true` MCP не включает: включает его пользователь |
| `mcpMaxAccess` | строка: `diagnostics`, `data` | `data` | потолок уровня доступа LLM-ассистента к подключениям: действующий уровень — меньший из уровня в профиле подключения («Доступ для LLM» в форме) и этого значения; при `diagnostics` в «Настройках» написано «Доступ к данным ограничен вашей организацией» |

Ключ `licenseKey` прежних сборок больше не используется: все функции бесплатны, ключ игнорируется, как любой
неизвестный, с предупреждением в логе.

Ключи MCP строже остальных: если файл политики есть, но не читается, или у `mcpEnabled` либо `mcpMaxAccess` неверный тип или
значение, MCP-шлюз запрещён целиком, как при `mcpEnabled = false`, — раз политика задана, администратор хотел ограничений
(так же нечитаемая политика выключает обновления). Ошибка видна в окне «О программе».

Политика читается один раз при запуске: после изменения перезапустите приложение. Неизвестные ключи игнорируются.
На macOS читается только политика уровня устройства: профиль должен быть установлен на устройство (канал устройства MDM,
`PayloadScope` = `System`), тогда он окажется в `/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist`.
Профиль уровня пользователя (`/Library/Managed Preferences/<пользователь>/…`) приложение не читает.
Значения в реестре Windows — строки (`REG_SZ`), флаги — `dword` 0/1. Состояние политики и её ошибки
(нечитаемый файл, неверный тип значения, неизвестный язык) видны в окне «О программе».

### Проверка политики вручную (macOS)
`defaults write` в `/Library/Managed Preferences` на современной macOS не работает (туда пишет только MDM).
Для проверки соберите plist и скопируйте его от имени администратора:

```bash
rm -f /tmp/policy.plist && plutil -create xml1 /tmp/policy.plist
plutil -insert updatesEnabled -bool NO /tmp/policy.plist
plutil -insert mcpMaxAccess -string diagnostics /tmp/policy.plist   # или: plutil -insert mcpEnabled -bool NO …
sudo mkdir -p "/Library/Managed Preferences"
sudo cp /tmp/policy.plist "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"
sudo chmod 644 "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"
plutil -p "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"
```
Удалить: `sudo rm "/Library/Managed Preferences/io.github.vvnovg.glafira.postgres.plist"`.

## Внутреннее зеркало обновлений
Скопируйте из релиза установщики, `*.sig` и `latest.json`, замените в `latest.json` адреса `url` на адреса зеркала
и укажите адрес `latest.json` в `updateUrl`. Подписи остаются прежними: приложение проверяет их встроенным ключом.
Зеркало должно отдаваться по `https://` (по `http` приложение обновления не загружает).

В `latest.json` по записи на каждый тип установки: `darwin-aarch64`, `darwin-x86_64`, `windows-x86_64`,
`linux-x86_64-deb`, `linux-x86_64-rpm`, `linux-x86_64-appimage` и `linux-x86_64` (тоже AppImage — запасная запись).
Сохраните все записи: установка из `.deb` скачивает только `.deb`, из `.rpm` — только `.rpm`.

## Роль для диагностики
```sql
CREATE ROLE glafira_diag LOGIN PASSWORD '…';
GRANT pg_monitor TO glafira_diag;
GRANT pg_signal_backend TO glafira_diag;   -- отмена и завершение сессий
GRANT pg_maintain TO glafira_diag;         -- PostgreSQL 17+: VACUUM и ANALYZE
GRANT pg_read_all_data TO glafira_diag;    -- PostgreSQL 14+, по желанию: EXPLAIN запросов приложения, но открывает чтение ВСЕХ данных (см. ниже)
-- в каждой БД, где нужен анализ запросов (и pg_stat_statements в shared_preload_libraries):
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```
В `pg_hba.conf` нужна строка, разрешающая роли вход с машин пользователей (`scram-sha-256`).

Роль нужна для полной диагностики; без неё приложение подключается, но чек-лист готовности в проверке подключения
покажет, чего не хватает, и подскажет точную команду (`GRANT … TO "glafira_diag";`). `pg_signal_backend` нужен действиям — отмене запросов и завершению сессий (подраздел «Диагностика» → «Действия»); `pg_maintain` нужен для VACUUM и ANALYZE, которых в приложении пока нет; оба права чек-лист проверяет заранее. `pg_maintain` есть только в PostgreSQL 17 и новее;
в более ранних версиях `VACUUM` и `ANALYZE` могут запускать владелец таблицы, владелец базы или суперпользователь.
`CREATE EXTENSION` выполняет суперпользователь; `shared_preload_libraries` меняется только с перезапуском сервера.

`pg_read_all_data` нужен только EXPLAIN запросов приложения (инструмент «Запросы»), а выдаёт он много: роль получает чтение всех таблиц, представлений и последовательностей сервера, а не только таблиц нужного запроса. Консоль EXPLAIN выполняет введённые запросы под ролью подключения, поэтому давайте такую роль только тем, кому позволено читать данные приложения. Строку с `pg_read_all_data` из рецепта можно не выполнять: выдайте `SELECT` на конкретные таблицы (и `USAGE` на их схему) — EXPLAIN запросов к ним заработает, но пункт чек-листа «Чтение таблиц приложения (EXPLAIN)» останется предупреждением: он проверяет только членство в `pg_read_all_data`. На PostgreSQL 13 этой роли нет, там остаётся только `SELECT` на таблицы, а пункт показывает предупреждение без готовой команды.

Вкладки таблицы, представления и функции читают только системный каталог и статистику, отдельных прав на сами объекты им не нужно.
Исключение — вкладка последовательности: последнее значение и долю использованного диапазона PostgreSQL отдаёт только роли с правом
`SELECT` или `USAGE` на последовательность. Без него вкладка пишет «Нет права на чтение» вместо чисел. Чтобы дать право:
```sql
GRANT SELECT ON ALL SEQUENCES IN SCHEMA shop TO glafira_diag;   -- для каждой схемы; новые последовательности — отдельным GRANT
-- либо, если допустимо чтение всех данных (PostgreSQL 14+):
GRANT pg_read_all_data TO glafira_diag;
```

### Настройки сервера, которые проверяет чек-лист
| Параметр | Значение | Зачем |
|---|---|---|
| `shared_preload_libraries` | содержит `pg_stat_statements` | статистика запросов; на каждом узле |
| `compute_query_id` | `on` (PostgreSQL 14+; `auto` подходит, если `pg_stat_statements` загружен на всех узлах) | связь запросов в `pg_stat_activity` и `pg_stat_statements` |
| `track_io_timing` | `on` | время ввода-вывода запросов (предупреждение, если выключено) |
| `track_activity_query_size` | не меньше `4096` | длинные тексты запросов не обрезаются (предупреждение) |
| `pg_stat_statements.track_planning` | `on` | колонки планирования в инструменте «Запросы»; пункт показывается, только если расширение создано в базе подключения (предупреждение, если выключено) |

Необязательные расширения, которые приложение использует, если они установлены в базе:
`hypopg`, `pgstattuple`, `pg_buffercache`, `pg_wait_sampling`, `pg_qualstats`, `pg_stat_kcache`
(`CREATE EXTENSION IF NOT EXISTS <имя>;`, если пакет расширения установлен на сервере).

### Необязательные расширения для инструмента «Запросы»
Три расширения добавляют инструменту «Запросы» данные, без них он работает как обычно (глава «Запросы» руководства пользователя, раздел «Расширения»). Чек-лист готовности у пунктов «Расширение hypopg», «Расширение pg_stat_kcache» и «Расширение pg_wait_sampling», пока расширение не создано, пишет, что оно даёт и как его включить — по фактическому состоянию сервера (см. ниже).

| Расширение | Что даёт | Что нужно на сервере |
|---|---|---|
| `hypopg` | «Проверить гипотезу» у рекомендаций по плану: стоимость с виртуальным индексом | пакет расширения и `CREATE EXTENSION` в базе приложения; preload и перезапуск не нужны |
| `pg_stat_kcache` | колонки «CPU» и «Чтение с диска» в топе, CPU и диск в карточке запроса | в `shared_preload_libraries` после `pg_stat_statements`, перезапуск, `CREATE EXTENSION` в базе подключения |
| `pg_wait_sampling` (1.1 и новее) | ожидания запроса в карточке из профиля расширения | в `shared_preload_libraries`, перезапуск, `CREATE EXTENSION` в базе подключения, `pg_wait_sampling.profile_queries = top` (или `all`; в старых версиях параметр логический — `on`) |

Шаги включения зависят от того, в каком состоянии расширение на сервере; чек-лист показывает нужный вариант:

| Состояние | Что делать |
|---|---|
| Пакета нет на сервере | Установить пакет из PGDG: `postgresql-<версия>-<имя>` (apt, например `postgresql-17-pg-stat-kcache`; в имени пакета дефисы вместо подчёркиваний) или `<имя>_<версия>` (RPM, например `pg_stat_kcache_17`); для `pg_stat_kcache` и `pg_wait_sampling` затем preload и перезапуск, потом `CREATE EXTENSION`. У `hypopg` preload не нужен: пакет, затем `CREATE EXTENSION`. Имена пакетов в других дистрибутивах могут отличаться |
| Пакет есть, библиотеки нет в `shared_preload_libraries` (хотя бы на одном узле) | Добавить библиотеку в `shared_preload_libraries`, перезапустить сервер, затем `CREATE EXTENSION` |
| Библиотека загружена | Только `CREATE EXTENSION` в базе подключения, перезапуск не нужен |
| Расширение создано (`CREATE EXTENSION` выполнен), но библиотеки нет в `shared_preload_libraries` хотя бы на одном узле (её убрали из списка, реплика без preload) | Предупреждение «Создано, но библиотека не загружена» с перечнем узлов: добавить библиотеку в `shared_preload_libraries` и перезапустить сервер; до этого расширение не работает, и «Запросы» его не используют |
| Роли не видно значение `shared_preload_libraries` | Чек-лист просит проверить preload самостоятельно |

```
# postgresql.conf или patronictl edit-config, затем перезапуск сервера
shared_preload_libraries = 'pg_stat_statements,pg_stat_kcache,pg_wait_sampling'
pg_wait_sampling.profile_queries = top
```
```sql
-- в базе подключения (суперпользователь):
CREATE EXTENSION IF NOT EXISTS hypopg;
CREATE EXTENSION IF NOT EXISTS pg_stat_kcache;
CREATE EXTENSION IF NOT EXISTS pg_wait_sampling;
-- только если право EXECUTE / SELECT у PUBLIC отозвано (по умолчанию оно есть):
GRANT EXECUTE ON FUNCTION pg_stat_kcache() TO glafira_diag;
GRANT EXECUTE ON FUNCTION pg_wait_sampling_get_profile() TO glafira_diag;
GRANT SELECT ON pg_wait_sampling_profile TO glafira_diag;
```
`pg_monitor` этих прав не даёт: приложение проверяет их само (`has_function_privilege`), и если права нет, библиотека не загружена или профиль без `queryid` (версия 1.0), инструмент молча работает без расширения. С `pg_stat_statements` 1.8 (PostgreSQL 13) и `pg_stat_kcache` 2.2 и новее учитывается CPU только инструкций верхнего уровня. Проверка гипотезы идёт на узле, где построен план: если план с выполнением шёл на реплике, пакет `hypopg` нужен и на сервере реплики (расширение в базе доезжает репликацией, пакет — нет). Работа `hypopg` на hot standby в автотестах не проверялась.

**Сброс статистики.** `pg_stat_statements_reset()` не сбрасывает `pg_stat_kcache`: у расширения свой счётчик и свой сброс. Чтобы CPU и чтение с диска в топе относились к тому же периоду, что остальные колонки, сбрасывайте оба: `SELECT pg_stat_statements_reset(); SELECT pg_stat_kcache_reset();`. Если сброшен только `pg_stat_statements`, режим «с момента сброса» помечает колонки CPU и «Чтение с диска» звёздочкой, а подвал называет время начала накопления `pg_stat_kcache` (по `stats_since`, `pg_stat_kcache` 2.3 и новее) или пишет, что он сбрасывается отдельно (в старых версиях времени нет, и пометка стоит всегда; если прочитать время не удалось, пометки нет). Началом считается самая ранняя строка расширения, так что вытеснение строк сдвигает его. В окне и между снимками после сброса `pg_stat_statements` приращение CPU и диска считается разностью с прошлым значением (расширение не сбрасывалось), а остальные колонки — с момента сброса; при сравнении снимков это помечено в подписи. Если между снимками сбрасывался и `pg_stat_kcache` (видно по `stats_since` в `pg_stat_kcache` 2.3 и новее), CPU и диск берутся значениями второго снимка целиком; в старых версиях такой сброс виден, только если значения уменьшились.

### Patroni
Роль и расширения создаются на лидере и доезжают до реплик репликацией. Параметры PostgreSQL в кластере Patroni задаёт
Patroni (`patronictl edit-config`, затем `patronictl restart` для `shared_preload_libraries`), а не `postgresql.conf` на узле.
Если в конфигурации Patroni есть раздел `postgresql.pg_hba`, Patroni сам пишет `pg_hba.conf` — строку для роли добавляйте туда.

## Диагностика
Инструменты группы «Диагностика» в дереве подключения (пульс, сессии, idle in transaction, профиль ожиданий, блокировки, горизонт xmin, реплики,
слоты; у кластера Patroni ещё готовность к failover и матрица health) только читают: на узлы PostgreSQL уходят `SELECT`, в REST API Patroni — `GET`.
Ни PostgreSQL, ни Patroni они не меняют; изменения делают только действия (подраздел «Действия» ниже). Единственное исключение среди запросов — EXPLAIN ANALYZE запроса, который пишет данные: ярус записи с подтверждением и записью в журнал, выполнение в транзакции с откатом (подраздел «Действия»). Что показывает каждый инструмент — глава «Диагностика» руководства пользователя.
Инструмент «Запросы» читает `pg_stat_statements`; планы (EXPLAIN) строятся на отдельном соединении; «план с выполнением» выполняет запрос в транзакции с откатом — см. ниже. Рекомендованные по плану команды (`CREATE INDEX`, `ANALYZE`, `VACUUM`, `SET work_mem` и другие) приложение только показывает и копирует, но не выполняет. Проверка гипотезы `hypopg` создаёт виртуальный индекс в памяти сессии внутри транзакции `READ ONLY` и удаляет его `hypopg_reset()` до отката: на диск и в каталог ничего не пишется. Снимки `pg_stat_statements` хранятся только на компьютере пользователя (раздел «Данные и логи»). Что показывает инструмент — глава «Запросы» руководства пользователя.

### Права
Роль диагностики (`glafira_diag` выше) должна входить в `pg_monitor` с наследованием прав (`INHERIT`, значение по умолчанию): приложение проверяет
`pg_has_role(current_user, 'pg_read_all_stats', 'USAGE')`, а `pg_monitor` включает `pg_read_all_stats`. Он открывает то, что PostgreSQL прячет от обычных ролей:
- тексты запросов и остальные сведения чужих сессий в `pg_stat_activity` (состояние, ожидание, время запроса и транзакции, `xmin`): без права вместо текста стоит
  `<insufficient privilege>`, остальные поля пусты, поэтому списки сессий и блокировок и профиль ожиданий по чужим сессиям почти пусты;
- состояние отправителей WAL и приёмника на репликах (`pg_stat_replication`, `pg_stat_wal_receiver`): без права инструменты «Реплики» и «Горизонт xmin»
  скрывают подробности и пишут об этом, а находки по репликам не строятся;
- размер каталога `pg_wal` (`pg_ls_waldir()`): без права в «Пульсе» стоит прочерк и пометка.

Недоступное из-за прав, как и недоступное в версии PostgreSQL, инструмент перечисляет серыми строками под блоком находок, а не отказывает целиком.

Инструмент «Запросы» и карточка запроса читают `pg_stat_statements`: строки других ролей видны только с `pg_read_all_stats` (входит в `pg_monitor`), без него сервер скрывает их `queryid` и текст, и инструмент пишет «Запросы других ролей: нужна роль pg_read_all_stats». Расширение должно быть в `shared_preload_libraries` (пункт чек-листа «pg_stat_statements загружен») и создано в базе подключения (`CREATE EXTENSION pg_stat_statements`; пункт чек-листа «Расширение pg_stat_statements»); колонки планирования заполняются при `pg_stat_statements.track_planning = on` (пункт «pg_stat_statements.track_planning»; он показывается, только если расширение создано). EXPLAIN запроса приложения выполняется под ролью подключения и требует права читать таблицы запроса: на PostgreSQL 14 и новее — `GRANT pg_read_all_data TO glafira_diag;` (пункт чек-листа «Чтение таблиц приложения (EXPLAIN)»; это право читать все данные — предостережение в разделе «Роль для диагностики»), на 13 — `SELECT` на нужные таблицы (там пункт чек-листа — предупреждение без готовой команды). `pg_read_all_data` даёт только чтение: EXPLAIN запроса `INSERT`, `UPDATE`, `DELETE` или `MERGE` требует прав на запись в его таблицы даже без выполнения (PostgreSQL проверяет их при построении плана EXPLAIN), а ярус записи EXPLAIN ANALYZE — тем более. Для таких запросов нужен профиль подключения под ролью приложения, а не общая роль диагностики: что именно выдать и почему — в подразделе «Действия», абзац «Роль для EXPLAIN ANALYZE записи».
`hypopg_create_index` и остальные функции `hypopg` доступны любой роли: виртуальный индекс живёт в памяти сессии; проверке гипотезы нужны те же права на таблицы запроса, что EXPLAIN. `pg_stat_kcache` и `pg_wait_sampling` по умолчанию открыты `PUBLIC`; колонки `pg_stat_kcache` приложение присоединяет к строкам `pg_stat_statements`, поэтому CPU и диск чужих запросов, как и сами запросы, видны только с `pg_read_all_stats`; профиль `pg_wait_sampling` читается по `queryid` запроса, открытого из этих строк. Что выдать, если права отозваны, — подраздел «Необязательные расширения для инструмента «Запросы»» выше.
Права `pg_signal_backend`, `pg_maintain` и `REPLICATION` чтению диагностики не нужны. `pg_signal_backend` и `REPLICATION` нужны действиям (подраздел «Действия» ниже); `pg_maintain` приложение пока не использует, чек-лист лишь проверяет его заранее.

### Нагрузка
- Открытая и видимая вкладка инструмента читает данные по умолчанию раз в 5 секунд (инструмент «Запросы» — раз в 10 секунд; в шапке вкладки интервал меняется: 2, 5, 10, 30 секунд или пауза); скрытую вкладку приложение не опрашивает.
  Инструмент узла — несколько коротких запросов к одному узлу (по умолчанию к лидеру или primary); «Пульс» — по одному запросу и отдельному запросу размера `pg_wal` на каждый доступный узел.
- Patroni: топология — `GET /cluster` и `GET /patroni` раз в 10 секунд; вкладки «Готовность к failover» и «Матрица health» по умолчанию обновляются раз в 10 секунд (интервал меняется в шапке вкладки):
  первая читает `GET /config` (его же при каждом обновлении читают «Слоты репликации» у кластера Patroni), вторая — семь адресов проверки здоровья у каждого участника.
- Сэмплер профиля ожиданий — один лёгкий запрос к `pg_stat_activity` раз в секунду на узел, пока открыта вкладка «Профиль ожиданий», в том числе скрытая; закрытие вкладки его останавливает.
  История хранится в памяти приложения (последние 60 минут, не больше 500 000 строк, порядка 40 МБ на узел), на диск не пишется и пропадает при закрытии подключения.
- Инструмент «Запросы» в режиме «с момента сброса» на каждом обновлении (по умолчанию раз в 10 секунд, пока вкладка видна) читает целиком представление `pg_stat_statements` без текстов; в режимах «за 5/15/60 минут» сервер почти не читается: отчёт собирается из памяти по тикам сэмплера, а с сервера уходят только шапка (версия и роль узла), когда буфера ещё нет, и тексты строк топа без известного текста (одним запросом на обновление, не больше числа строк; тексты лежат в кэше узла в памяти приложения и от сэмплера не зависят). Каждая видимая карточка запроса раз в 5 секунд выполняет чтение `query_detail`: строки `pg_stat_statements` этого запроса, `sum()` по всему представлению (для долей) и `pg_stat_activity` по `query_id`; текст запроса берётся из кэша текстов узла в памяти приложения (общего с инструментом «Запросы», от сэмплера не зависит), а файл текстов (`pg_stat_statements(true)`) читается с сервера только при промахе кэша для запроса, который в `pg_stat_statements` есть; если запроса там уже нет или у него нет текста, файл не читается и это запоминается. Это дополняет сэмплер ниже, а не заменяет его.
- Сэмплер запросов — одно чтение `pg_stat_statements(showtext := false)` раз в минуту на узел, пока открыты инструмент «Запросы» или карточка запроса (в том числе скрытые); тексты запросов читаются отдельно по ключам видимых строк. Чтение идёт на соединении сэмплера (общее с сэмплером профиля ожиданий). История дельт хранится в памяти (60 минут, не больше 200 000 записей на узел, порядка 50 МБ) и пропадает при закрытии подключения.
- `pg_stat_kcache` читается тем же запросом, что `pg_stat_statements` (`LEFT JOIN` по `queryid`, `userid`, `dbid` и признаку верхнего уровня); перед использованием приложение проверяет расширение коротким вызовом `pg_stat_kcache()` (если библиотека явно не загружена, проверка не выполняется) и запоминает итог для узла на минуту; если вызов отказал из-за состояния сервера (библиотека не загружена, нет прав или функции), проверка не повторяется 10 минут, так что ошибка в логе сервера появляется не чаще раза в 10 минут на узел. Разовый сбой проверки (отмена, тайм-аут) не запоминается. Профиль `pg_wait_sampling` открытая карточка читает не чаще раза в 30 секунд на запрос и узел (сборщик расширения отдаёт весь профиль, и стоимость чтения растёт с его размером; на стенде около 65 мс при 360 тысячах строк); при каждом обновлении карточки — только лёгкий запрос к каталогу. Если профиль не читается из-за состояния сервера (библиотека не загружена, сборщик не запущен), карточка 10 минут не пробует его снова; после другой ошибки чтения (например, отмены по `statement_timeout`) — 30 секунд.
- Проверка гипотезы `hypopg` — отдельное соединение на время проверки (как EXPLAIN): пробный план без индекса, затем одна транзакция `BEGIN READ ONLY` с `search_path` запроса — `hypopg_create_index`, `hypopg_relation_size`, EXPLAIN без выполнения, `hypopg_reset()`, `ROLLBACK`; соединение закрывается.
- Снимок `pg_stat_statements` — одно чтение всего представления и текстов (до 1000 запросов) по кнопке пользователя; сравнение снимков и режим «между снимками» сервер не читают.
- EXPLAIN и EXPLAIN ANALYZE выполняются на отдельном соединении (как действие), которое открывается на один запрос и закрывается после него; параметры сессии — `statement_timeout = 5s` (внутри транзакции заменяется сроком запроса: 15 с у пробного плана, 5–600 с у выполнения), `lock_timeout = 1s`, без `search_path = pg_catalog` (запрос должен видеть схемы приложения).
- LLM-ассистент (раздел «LLM-ассистенты (MCP)») вызывает те же чтения, что вкладки инструментов, на тех же пулах соединений и с
  теми же таймаутами; закрытое подключение открывается при первом вызове, как щелчком в дереве (может понадобиться хранилище
  секретов и SSH-туннель). Наблюдение за активностью подписывается на общий сэмплер профиля ожиданий узла (нагрузка не
  удваивается), наблюдение за топом читает `pg_stat_statements(showtext := false)` в начале и в конце окна (10–50 с). Сводка
  здоровья опрашивает быстрые инструменты параллельно со сроком 20 секунд. Пределы шлюза: на сессию — 60 вызовов в минуту,
  2 одновременные операции с базой и одно наблюдение за раз; на все сессии — 4 операции с базой; ответ — до 100 КБ. EXPLAIN
  и проверка гипотезы `hypopg` от ассистента — отдельное соединение на вызов, как у EXPLAIN пользователя (`statement_timeout`
  5 с, `lock_timeout` 1 с, `BEGIN READ ONLY … ROLLBACK`).
- Соединения на узел: каталог и все вкладки — до 3, опрос топологии — 1, сэмплер — 1 (общий для профиля ожиданий и запросов, только пока открыт один из этих инструментов или карточка запроса), действие или EXPLAIN — 1 на время самого действия (подраздел «Действия»); простаивающие закрываются через 5 минут.
  Учитывайте их в `max_connections` и в лимитах роли, умножая на число одновременно работающих копий приложения.
- Запросы идут на сессии только для чтения (`statement_timeout = 5s`, `lock_timeout = 1s`) с `application_name = glafira-pg` (соединения действия и EXPLAIN не только для чтения, см. «Действия»); тяжёлых блокировок они не берут:
  размеры отношений не считаются, `pg_blocking_pids` вызывается только для сессий, которые ждут блокировку.

### Patroni API
Диагностика обращается к REST API Patroni только методом `GET`: `/cluster` и `/patroni` (топология), `/config` (динамическая конфигурация: готовность к failover, постоянные слоты)
и адреса проверки здоровья каждого участника — `/primary`, `/standby-leader`, `/replica`, `/read-only`, `/sync`, `/async`, `/health` (матрица health).
Адреса проверки здоровья Patroni отдаёт без авторизации, приложение её для них не передаёт; на остальные адреса идёт basic auth из профиля.
Ответ 503 на адрес здоровья — штатное «я не в этой роли», а не ошибка. Срок одного запроса — 5 секунд. Изменяющие вызовы (switchover, failover, restart, пауза) делают только действия Patroni, следующий подраздел.

### Действия
Действия — единственное, что приложение меняет на серверах (EXPLAIN ANALYZE запроса, который пишет данные, — тоже действие: ярус записи, подтверждение, журнал, выполнение в транзакции с откатом). Пользователь запускает их кнопкой во вкладках инструментов и в обзоре кластера; перед выполнением приложение показывает предпросмотр и просит подтверждение. Для сессий и слотов предпросмотр заново читает их с сервера; предпросмотр действий Patroni берёт лидера, участников и готовность реплик из последнего опроса топологии (не старше интервала опроса) и заново читает только динамическую конфигурацию и число сессий лидера. Перед отправкой приложение ещё раз проверяет условия действия по последнему опросу: у failover и switchover с выбранным кандидатом — и готовность кандидата, у switchover — что лидер тот же, что в предпросмотре. Что можно сделать:
- отмена запроса и завершение сессии: поштучно и пакетом «idle in transaction старше N минут» (до 500 сессий за действие);
- удаление слота репликации (только неактивного);
- Patroni: switchover (сейчас и по расписанию), failover, restart (сейчас и по расписанию), отмена запланированных switchover и restart, пауза и её снятие;
- EXPLAIN ANALYZE запроса, который пишет данные: выполнение в транзакции с откатом (ярус записи, см. ниже).

`VACUUM`, `ANALYZE` и перечитывание конфигурации приложение не выполняет. Как действия выглядят для пользователя — глава «Диагностика» руководства пользователя, разделы «Действия», «Действия Patroni» и «Журнал действий».

**EXPLAIN ANALYZE в два яруса.** «План с выполнением» сначала строит обычный план и по нему определяет ярус. Чтение (нет `ModifyTable` в плане и инструкция не `CREATE … AS`) выполняется в транзакции `BEGIN READ ONLY … ROLLBACK` без подтверждения и в журнал не пишется: сервер сам отвергнет попытку записи (SQLSTATE 25006), и приложение предложит выполнить запрос как запись. Граница этой защиты: `READ ONLY` не останавливает нетранзакционные административные функции — например `pg_terminate_backend`, `pg_cancel_backend`, `pg_stat_reset*`, `pg_stat_statements_reset`, `pg_reload_conf`, `pg_drop_replication_slot`, `pg_switch_wal`, `pg_create_restore_point`, `pg_promote` — и внешние вызовы (`dblink`, `http`). Поэтому вызов функции из списка в VERBOSE-плане пробы (`explain::tier::ADMIN_FUNCTIONS`) переводит инструкцию в ярус записи — с подтверждением и записью в журнал (спека P3 §15, п. 10). В тот же ярус переводит вызов функций, выполняющих SQL из строки (`query_to_xml*`, `cursor_to_xml*`, `ts_stat`, `ts_rewrite`): их аргумент приложение не разбирает, а внутри может быть запись. Вызовы внутри тела другой функции или триггера план не показывает: от них защищает только роль без прав на эти функции. Запись требует включённых действий (на подключении «только чтение» недоступна, на prod вводится имя подключения), подтверждения со списком таблиц (окно подтверждения выставляет в запросе флаг `writeConfirmed`, и без него приложение отказывает ярусу записи в любом окружении: запрос «Выполнить как запись» — до соединения с сервером, ярус записи, найденный пробным планом, — после пробы `READ ONLY` и до выполнения) и выполняется в `BEGIN … ROLLBACK`; на реплике недоступна. Кнопка «Выполнить как запись» после отказа яруса чтения идёт тем же путём подтверждения, но проверка защиты выполняется до пробного плана, а сам пробный план строится без `READ ONLY`. Откат отменяет изменения строк, в том числе сделанные триггерами, и `NOTIFY` не доставляется; не отменяются сдвиг последовательностей, внешние вызовы (`dblink`, `http`) и нетранзакционные функции, в том числе вызванные из триггеров, а блокировки запрос держит, пока выполняется, — предупреждение об этом стоит в окне подтверждения. Каждое выполнение яруса записи записывается в `actions.jsonl` действием `explainAnalyze` с базой, списком таблиц, сроком и первыми 200 символами текста (литералы остаются); в списке — все отношения плана, в том числе те, что запрос только читает. У других действий сбой записи журнала окно сообщает, а у `explainAnalyze` он тихий: к этому моменту запрос уже выполнен и откатан, и план показан как обычно.

**Защита.** На подключении «только чтение» кнопок действий нет, а приложение отказывает и при прямом вызове. На prod нужно ввести имя подключения; для пакета сессий — ещё и их число, для удаления слота — имя слота (в любом окружении), для failover — имя кандидата. Все проверки выполняются в приложении до обращения к серверу; исключение — ярус записи EXPLAIN ANALYZE, который становится известен только по пробному плану `READ ONLY`: его отказ приходит после пробы, но до выполнения.

**Права PostgreSQL.** Роли, под которой открыто подключение, нужны:

| Действие | Что нужно |
|---|---|
| Отмена запроса, завершение сессии | суперпользователь — любая клиентская сессия; членство в `pg_signal_backend` — любая сессия не суперпользователя; без того и другого — только сессии ролей, членом которых является текущая роль |
| Удаление слота репликации | атрибут `REPLICATION` или суперпользователь |
| EXPLAIN ANALYZE запроса, который пишет (ярус записи) | `SELECT` и `INSERT`/`UPDATE`/`DELETE` на таблицы запроса; только на primary |

Сессию суперпользователя завершает только суперпользователь: `pg_signal_backend` на неё не распространяется. Чужие сессии предпросмотр видит только с `pg_read_all_stats` (роль `pg_monitor`): без неё сервер не отдаёт время запуска сессии, по которому приложение её адресует. Действие без права не выполняется: в предпросмотре у сессии стоит причина, кнопка удаления слота неактивна с подсказкой.

**Роль для EXPLAIN ANALYZE записи.** Ярус записи выполняет запрос по-настоящему (с откатом), поэтому права на запись нужны той роли, под которой открыто подключение, и нужны на все таблицы запроса — это же требование PostgreSQL предъявляет и к EXPLAIN без выполнения. Заведите для этого профиль подключения под ролью приложения (на стенде — `glafira_app`: права на таблицы схемы `shop`, без `pg_monitor`) и не выдавайте права записи общей роли диагностики, которой пользуются все: иначе любой, у кого она есть, мог бы выполнять запросы с записью, а откат не отменяет сдвиг последовательностей, внешние вызовы и нетранзакционные функции. Права ровно те, что нужны самому запросу:
```sql
GRANT USAGE ON SCHEMA shop TO glafira_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.orders TO glafira_app;   -- таблицы запросов, которые надо разбирать с выполнением
```
Нужны ещё включённые действия на подключении (на «только чтение» ярус записи недоступен) и узел-primary; если в запросе есть `nextval` или столбец `serial`, нужен и `USAGE` на последовательность.

**Отдельная роль для действий.** Атрибут `REPLICATION` шире удаления слотов: роль с ним может создавать логические слоты и читать через них изменения всех таблиц базы, а при разрешающей строке `replication` в `pg_hba.conf` для неё — снимать копию всего кластера. Поэтому не добавляйте его роли диагностики, которой пользуются все, а выдавайте отдельной роли для действий — и заведите под неё отдельный профиль подключения для тех, кто выполняет действия, — или не выдавайте вовсе: без него кнопка удаления слота неактивна, а пункт чек-листа «Удаление слотов репликации» показывает предупреждение, и для роли диагностики это штатное состояние.
```sql
CREATE ROLE glafira_ops LOGIN PASSWORD '…';
GRANT pg_monitor TO glafira_ops;            -- видеть чужие сессии
GRANT pg_signal_backend TO glafira_ops;     -- отмена и завершение сессий
ALTER ROLE glafira_ops REPLICATION;         -- только если нужно удалять слоты
```

**Соединение действия.** Действие выполняется не на пулах диагностики, а на отдельном соединении, которое открывается на одно действие или пакет и закрывается после него. Оно не «только для чтения» (нет `default_transaction_read_only`), остальные параметры те же: `statement_timeout = 5s`, `lock_timeout = 1s`, `search_path = pg_catalog`, `DateStyle = ISO`, `application_name = glafira-pg`. Соединение идёт через SSH-туннель подключения, если он включён; база данных — из профиля, а у логического слота — его собственная. Пакет выполняется по одной сессии на одном соединении и укладывается в 60 секунд. Ответа на каждый запрос приложение ждёт не дольше 10 секунд (при обрыве сети серверный `statement_timeout` не сработает), а запрос без ответа или закрытое подключение останавливают пакет: оставшиеся сессии не выполняются. Если срок истёк у самого запроса с сигналом, сигнал мог дойти — исход неизвестен; повтор по той же паре (PID и время старта сессии) безопасен. Это ещё одно соединение к узлу на время действия: учитывайте его в `max_connections` и в лимитах роли.

**Учётная запись API Patroni.** Действия Patroni отправляют изменяющие запросы с basic auth. Логин задаётся в профиле подключения (поле «Пользователь API»), пароль хранится в системном хранилище секретов (Keychain, Credential Manager, Secret Service) и не попадает ни в `connections.json`, ни в журнал действий, ни в архив диагностики. Без логина кнопки действий Patroni неактивны. Учётная запись должна быть задана в Patroni (`restapi.authentication`). Пароль не уходит на `http://`-адрес, если все адреса API в профиле — `https://`. Запросы:

| Действие | Запрос |
|---|---|
| switchover | `POST /switchover` (`leader`, `candidate`, `scheduled_at`) на API лидера |
| отмена запланированного switchover | `DELETE /switchover` на API лидера |
| failover | `POST /failover` (`candidate`) на API лидера |
| restart | `POST /restart` (`restart_pending`, `schedule`) на API самого участника |
| отмена запланированного restart | `DELETE /restart` на API самого участника |
| пауза и её снятие | `PATCH /config` с `{"pause": true}` или `{"pause": null}` на API лидера |

Запрос к лидеру пробует адреса по порядку: участники, API которых ответил на последний опрос (лидер среди них первым), затем остальные участники, затем адреса профиля, без повторов; при failover лидер молчит, и запрос не ждёт его. Restart и его отмена идут только к API самого участника. К следующему адресу приложение переходит лишь тогда, когда запрос заведомо не дошёл до Patroni (отказ соединения, срок установки соединения — 3 секунды, TLS, туннель). Через SSH-туннель перед действием приложение читает `GET /patroni` того же адреса: если туннель не пробросил соединение к узлу, оно не установилось за 3 секунды или узел не ответил на чтение за 5 секунд, действие на этот адрес не отправляется и пробуется следующий. Запрос, на который Patroni не ответил после отправки, не повторяется. Перенаправления HTTP не выполняются. Срок ответа — 5 секунд, у switchover, failover и restart «сейчас» — до 60 секунд: Patroni отвечает после выполнения. Пока действие наблюдается, топология опрашивается раз в 2 секунды вместо 10.

**Файл `actions.jsonl`.** Журнал действий лежит в каталоге данных приложения (пути по системам — в разделе «Данные и логи» ниже), по одной JSON-записи на действие. На macOS и Linux права на файл 0600; на Windows доступ определяют права каталога профиля пользователя. При 5 МБ файл переименовывается в `actions.1.jsonl`; хранятся текущий файл и одна старая копия. В записи — время, подключение (имя и окружение), узел, подтверждение prod, итог, а также по каждой сессии её данные и **текст запроса — первые 500 символов, литералы остаются как есть** (так при разборе инцидента видно, что именно завершили), у слота — его параметры, у Patroni — метод, адрес без учётных данных, тело и первые 500 символов ответа, у EXPLAIN ANALYZE — база, таблицы, срок и первые 200 символов текста запроса. Литералы в тексте запроса (в том числе в записях `explainAnalyze`) могут содержать персональные данные и секреты: относитесь к файлу как к конфиденциальному. Отказы защиты в журнал не пишутся. Журнал локален: он лежит на компьютере пользователя, выполнившего действие, общего журнала у приложения нет. В диагностический архив («О программе») файл не входит.

## LLM-ассистенты (MCP)
Приложение может отдавать диагностику LLM-ассистенту (Qwen Code, Claude Code, Claude Desktop, Cursor и другие клиенты MCP).
По умолчанию это выключено: пользователь включает сервер в «Настройки» → «LLM-ассистенты (MCP)» и открывает ассистенту каждое
подключение отдельно — группа «Доступ для LLM» в форме подключения, по умолчанию «Нет». Уровень хранится только на этом
компьютере: экспорт подключений его не пишет, импорт не переносит. Запретить MCP или ограничить уровень можно политикой
(`mcpEnabled`, `mcpMaxAccess`, раздел «Политика»). Как этим пользоваться — глава «LLM-ассистенты (MCP)» руководства пользователя.

**Как устроено.** Клиент запускает `glafira-pg mcp` — тот же исполняемый файл без окна. Команда читает `mcp.json` в каталоге
данных (раздел «Данные и логи») и соединяется с работающим приложением: на macOS и Linux — через Unix-сокет `mcp.sock` в каталоге
данных с правами 0600 (если путь длиннее 100 байт — `$XDG_RUNTIME_DIR/glafira-pg-mcp.sock` на Linux или временный каталог
пользователя), на Windows — через именованный канал `\\.\pipe\glafira-pg-mcp-<16 hex>`, который не принимает удалённых клиентов.
До протокола MCP команда предъявляет токен из `mcp.json` (32 случайных байта, новый при каждом запуске сервера). Сетевых портов
шлюз не открывает. Если приложение не запущено, команда запускает его и ждёт до 25 секунд. Каждого нового клиента пользователь
подтверждает в диалоге; подтверждённые клиенты хранятся в `settings.json` (раздел `mcp`). Имя клиента подделать можно — защищает
токен в файле, доступном только владельцу.

**Что получает модель.** Только чтение: топология, отчёты инструментов диагностики с находками, активность, топ запросов
и карточки, таблицы со статистикой колонок `pg_stats` без значений, параметры сервера (пароли в `primary_conninfo`, в том числе в виде URI, и в командах
`*_command` заменены на `***`, `ssl_passphrase_command` и параметры с секретными именами скрыты целиком), планы без выполнения и гипотезы индексов `hypopg`. Литералы в текстах запросов и в условиях
планов заменяются на `$N` при любом значении `standard_conforming_strings` узла: если границы литерала при разных значениях
расходятся, остаётся общее начало текста и одна метка `$N…`. Поиск `search` на уровне «Диагностика» идёт по замаскированному
тексту среди 200 первых строк топа. Сессия шлюза открывается с `default_transaction_read_only = on`; ошибки SSH-туннеля модель
получает общим текстом, без адреса бастиона, а ошибки узлов в отчётах — без подробностей и путей. SQL модели разбирается (`pg_query`) и принимается, только если это одна инструкция `SELECT`, `INSERT`,
`UPDATE`, `DELETE` или `MERGE` без запрещённых функций (сигналы и сбросы, файловые функции, `dblink`, `lo_*`, `set_config`,
advisory-блокировки, `pg_sleep`, `ts_stat`, `ts_rewrite`, `pg_stat_reset*`, `pg_start_backup`, `pg_stop_backup`, `pg_sync_replication_slots`, `pg_log_standby_snapshot` и другие); EXPLAIN выполняется без ANALYZE в транзакции `BEGIN READ ONLY … ROLLBACK`, а план
дополнительно проверяется на запрещённые функции. Никогда не отдаются пароли и секреты хранилища, настройки SSH, строки
подключения профилей, журнал действий, журнал MCP и настройки приложения. Ни один инструмент шлюза не меняет базы и Patroni.

**Права.** Отдельной роли шлюзу не нужно: ассистент читает под ролью профиля подключения то же, что видит пользователь. EXPLAIN
запросов приложения, как и у пользователя, требует права читать их таблицы (раздел «Диагностика» → «Права»).

**Журнал.** Вызовы инструментов, начало и конец сессий, подтверждение, отказ и отзыв клиентов, запуск и остановка сервера
пишутся в `mcp-audit.jsonl` в каталоге данных (0600; при 5 МБ файл переименовывается в `mcp-audit.1.jsonl`, хранятся два файла):
время, сессия, клиент, инструмент, подключение (id и имя), узел, аргументы (до 1 КБ; SQL модели — целиком до 16 КБ, с
литералами), итог, код ошибки, размер ответа, длительность, число замаскированных литералов. Ответы инструментов не пишутся.
Последние 200 записей видны в «Настройках».

**Второй экземпляр.** Если `mcp.json` уже указывает на работающий сервер, другое окно приложения MCP не запускает и файл не
трогает: статус «Сервер работает в другом окне Glafira».

**Известные ограничения.** Принятые риски (спека P4 §15): текст ошибки сервера в ответе по `queryId` из `pg_stat_statements` может
содержать значения данных; ранее созданная пользовательская функция, ошибочно помеченная `IMMUTABLE`, может вычисляться при
построении плана, и её результат попадёт в подробный план (запись блокирует `READ ONLY`). На Linux без `XDG_RUNTIME_DIR` (и при
длинном пути каталога данных) сокет создаётся под фиксированным именем `<временный каталог>/glafira-pg-mcp.sock` — в общем
`/tmp`, где его имя может занять другой пользователь машины; защищает токен, но на многопользовательских хостах задайте
`XDG_RUNTIME_DIR` (так делает сеанс systemd).

## Сеть
Прямые подключения (профиль без SSH):

| Куда | Порт | Зачем |
|---|---|---|
| Каждый узел PostgreSQL | 5432 (или ваш) | каталог, топология списка узлов, проверка подключения |
| REST API Patroni каждого узла | 8008 (или ваш) | обнаружение участников (`GET /cluster`, `GET /patroni`); диагностика (`GET /config`, адреса проверки здоровья); действия Patroni (`POST`, `PATCH`, `DELETE`) |
| Сервер обновлений | 443 | `github.com` и хосты, куда GitHub перенаправляет загрузку ассетов релизов (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`), — или хост из `updateUrl`; только если обновления не выключены политикой |

Чтение и диагностика вызывают только `GET`: `/cluster`, `/patroni`, `/config` и адреса проверки здоровья (раздел «Диагностика»); basic auth передаётся, если задан в профиле (кроме адресов проверки здоровья, которым авторизация не нужна). Действия Patroni (подраздел «Действия») добавляют `POST`, `PATCH` и `DELETE`. В Patroni
(проверено на 4.1.5) `restapi.allowlist`, обязательная basic auth для небезопасных вызовов и `restapi.verify_client: optional`
действуют только на изменяющие запросы (PATCH, PUT, POST, DELETE), а чтение они не закрывают, поэтому для чтения и диагностики
`restapi.allowlist` менять не нужно. Действиям он нужен: если он задан, изменяющие запросы Glafira проходят только с адресов из него (при SSH-туннеле — с адреса бастиона), а учётная запись из профиля должна быть в `restapi.authentication`. Не добавляйте в allowlist адреса и подсети пользователей, которым действия не положены: он защищает switchover, restart и reinitialize.
Чтение закрывает только `restapi.verify_client: required` (TLS-рукопожатие требует клиентский сертификат): тогда выдайте
пользователям клиентский сертификат и укажите его в профиле кластера в разделе «TLS для API» — профиль поддерживает HTTPS,
свой CA и клиентский сертификат. Если Patroni отдаёт адреса, недоступные с машин пользователей (pod IP, NAT), в профиле
кластера задаётся подмена адресов участников.

Приложение не отправляет телеметрию и отчёты о сбоях и не загружает удалённое содержимое: сетевые соединения — только с серверами PostgreSQL
и REST API Patroni из профилей подключений (при SSH-туннеле — через бастион) и с сервером обновлений.

MCP-шлюз для LLM-ассистентов сетевых портов не открывает: клиент подключается к приложению через локальный сокет или
именованный канал (раздел «LLM-ассистенты (MCP)»). С провайдером модели общается сам клиент (Qwen Code, Claude Code…),
а не приложение.

### Подключения через бастион (SSH)
Если в профиле включён SSH-туннель, с машины пользователя нужен только SSH до бастиона (порт 22 или заданный в профиле; сервер обновлений — как выше):
прямой доступ к узлам PostgreSQL и к REST API Patroni с машин пользователей не нужен. Все соединения профиля, включая REST API Patroni
и проверку подключения, идут через один процесс `ssh` с динамическим пробросом (`-D`, SOCKS5 на `127.0.0.1`). Бастион должен:
- разрешать TCP-проброс: в `sshd_config` `AllowTcpForwarding yes` (это значение по умолчанию; подходит и `local`), а `PermitOpen`, если он задан, должен включать узлы;
- разрешать имена узлов из профиля (хосты, участники Patroni, адреса REST API) и достигать их портов PostgreSQL (5432 или ваш) и REST API Patroni (8008 или ваш):
  имена разрешает бастион, а не машина пользователя, поэтому отдельная подмена адресов участников за туннелем обычно не нужна;
- принимать вход выбранным в профиле способом: ключ из SSH-агента, файл ключа или пароль.

TLS проверяется по исходному имени узла, а не по адресу туннеля. На серверах PostgreSQL соединения приходят с адреса бастиона: строки
`pg_hba.conf` для таких профилей пишите для адреса бастиона. Подробности об OpenSSH, ключах хоста и логах — в разделе «OpenSSH» ниже.

**Порт SOCKS без аутентификации.** Порт `-D` на `127.0.0.1` пароля не спрашивает: пока подключение открыто, им может воспользоваться
любой локальный пользователь той же машины и попасть всюду, куда пускают учётную запись пользователя на бастионе, — не только к узлам
PostgreSQL, но и, например, к etcd (`:2379`) и к изменяющим вызовам REST API Patroni. На однопользовательском компьютере это неважно.
На многопользовательском (общий Linux-хост для прыжков, Windows RDS/Citrix) либо ограничьте проброс на бастионе, либо не используйте туннель:
- `AllowTcpForwarding` только для тех, кому туннель нужен (`AllowTcpForwarding no` глобально и `yes` в `Match User …`/`Match Group …`);
- `PermitOpen` в том же `Match` (или `permitopen="хост:порт"` у ключа в `authorized_keys`) — только порты PostgreSQL и REST API Patroni
  нужных узлов, например `PermitOpen pg-1:5432 pg-1:8008 pg-2:5432 pg-2:8008`. Имена сравниваются с запросом как строки, без разрешения
  в адреса: перечислите их так, как они записаны в профилях (хосты, участники Patroni, адреса API).

Кроме того, порт выбирается заранее: приложение открывает и сразу закрывает слушатель на `127.0.0.1:0`, а порт занимает ssh — уже после
входа на бастион. В этот короткий промежуток порт может занять другой локальный процесс; на общей машине это ещё один довод против туннеля.

### Как приложение выглядит на сервере
- Соединения идут с `application_name = glafira-pg`: по нему их видно в `pg_stat_activity`.
- Соединения для SQL LLM-ассистента (EXPLAIN и проверка гипотез `hypopg` через MCP) идут с `application_name = glafira-pg-mcp`:
  нагрузку модели видно в `pg_stat_activity` отдельно от остальных запросов приложения. Остальные вызовы ассистента идут через
  общие соединения с `application_name = glafira-pg`.
- Сессии открываются только на чтение: `default_transaction_read_only = on`, `statement_timeout = 5s`, `lock_timeout = 1s`. Исключение — соединение действия (подраздел «Диагностика» → «Действия»): без `default_transaction_read_only`, остальные пределы те же.
  Кроме того, на сеансе задаются `search_path = pg_catalog` и `DateStyle = ISO`: определения объектов и DDL, которые строит приложение, всегда содержат имена схем, а даты в них — в формате ISO.
- Не больше 3 соединений на каждую связку «подключение, узел, база», плюс по одному для опроса топологии и, пока открыт профиль ожиданий, для сэмплера (см. «Диагностика»); простаивающее закрывается через 5 минут. Учитывайте их в `max_connections` и в лимитах роли.
- Проверка подключения («Проверить») не использует этот пул: она открывает свои короткоживущие соединения к узлам (на каждом узле
  несколько за время проверки) и закрывает их по окончании. Запас в `max_connections` и в лимитах роли нужен и для них.
- Топология опрашивается раз в 10 секунд.
- Все запросы приложения, кроме текста, введённого пользователем в консоли EXPLAIN, начинаются с комментария `/* glafira */` — и периодические (опрос топологии, сэмплеры, отчёты), и разовые (чек-лист готовности, каталог и дерево, вкладки объектов, карточка запроса, снимки, действия, `hypopg`), в том числе служебные инструкции транзакции EXPLAIN (`BEGIN`, `SET LOCAL`, `SAVEPOINT`, `ROLLBACK`): `pg_stat_statements` хранит комментарий у каждой инструкции. Обёртки консоли `EXPLAIN (FORMAT JSON, VERBOSE, SETTINGS…)` и `EXPLAIN (ANALYZE, BUFFERS, WAL, …)` метки не несут (она сместила бы позицию ошибки), но Глафира узнаёт их по точному префиксу своих опций. По метке приложение отличает свои запросы в топе: пометка «Глафира», без находок. Запросы Глафиры в `pg_stat_statements` можно отсечь по этому комментарию.

## OpenSSH
SSH-туннель использует системный клиент `ssh` (OpenSSH): своего ssh в приложении нет. Клиент ищется в `PATH`; на Windows ещё и в
`%SystemRoot%\System32\OpenSSH` (дополнительный компонент «Клиент OpenSSH»). Не найден — ошибка «OpenSSH client (ssh) was not found» с подсказкой.
Учитываются `~/.ssh/config` пользователя, ProxyJump, агент и аппаратные ключи.

**Версия.** Пароль и пассфраза ключа приложение передаёт через askpass (`SSH_ASKPASS_REQUIRE=force`), а он появился в OpenSSH 8.4:
с более старым клиентом эти способы недоступны (ошибка с объяснением), а агент и ключ без пассфразы работают на любой версии.
В Windows 10 встроен OpenSSH 8.1: для пароля и пассфразы установите Win32-OpenSSH 8.4 или новее и проверьте, что в `PATH` он стоит
раньше встроенного `%SystemRoot%\System32\OpenSSH`; агент и ключ без пассфразы работают и со встроенным клиентом.
Версия клиента видна в шаге «SSH» проверки подключения. На Windows пароль и пассфразу через askpass перед релизом проверяют вручную
(`docs/release-checklist.md`); агент и ключ без пассфразы от askpass не зависят.

**Как запускается ssh.** По одному процессу на открытое подключение:
```
ssh -N -T -E <каталог логов>/ssh-<id>.log -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3
    -o StrictHostKeyChecking=ask -o NumberOfPasswordPrompts=1 -o BatchMode=no -o ControlMaster=no -o ControlPath=none
    [-p <порт>] [-l <пользователь>] [-i <ключ> -o IdentitiesOnly=yes -o PreferredAuthentications=publickey | -o PreferredAuthentications=password]
    -D 127.0.0.1:<порт SOCKS> -- <цель>
```
Опции командной строки главнее `~/.ssh/config`. `ControlMaster=no` и `ControlPath=none` изолируют туннель от общих соединений (`ControlMaster auto`):
туннель не присоединяется к чужому сеансу пользователя и не становится мастером, закрытие которого оборвало бы его сеансы. Порт SOCKS слушает
только `127.0.0.1`. Обрыв связи обнаруживается за минуту (`ServerAliveInterval` 15 с, три пропуска); перезапуск идёт с паузами 1, 2, 5, 10, затем 30 секунд.
После отказа во входе (неверный пароль, отклонённый ключ, заблокированный агент вроде 1Password, ключ хоста не подтверждён или изменился, `ssh` не найден)
повторы прекращаются до «Переподключить»: так устаревший пароль не вызывает неудачный вход раз в 30 секунд, чего хватило бы для блокировки учётной записи
(`pam_faillock`, AD, fail2ban). Не забывайте и о проверке подключения: каждый запуск «Проверить» (и для сохранённого подключения) открывает собственный туннель, то есть делает один дополнительный вход на бастион; при неверном пароле это одна неудачная попытка, без повторов.

**Askpass.** В режиме askpass приложение запускает само себя: путь к его исполняемому файлу ssh получает в `SSH_ASKPASS`, а пароль или пассфразу
процесс askpass читает из системного хранилища секретов (ключи `sshPassword` и `sshPassphrase`). Пассфраза отдаётся только на стандартный запрос OpenSSH
`Enter passphrase for …`; запросы кодов подтверждения и прочие вопросы сервера остаются без ответа. На macOS в неподписанной сборке (например, собранной локально) доступ
второго процесса к Keychain может вызвать запрос разрешения.

**Ключи хоста.** Неизвестный ключ бастиона приложение показывает пользователю с отпечатком; после «Доверять и подключиться» ключ в `~/.ssh/known_hosts` записывает сам ssh.
Приложение `~/.ssh/config` и `~/.ssh/known_hosts` не редактирует. Подтверждение хранится в памяти до выхода из приложения. Для управляемого парка
ключи бастионов можно раздать заранее в общесистемный `/etc/ssh/ssh_known_hosts` (macOS и Linux): тогда диалога нет. Ключ хоста, который изменился,
приложение не принимает: пользователь исправляет `known_hosts` сам (`ssh-keygen -R <хост>`) после проверки у администратора.

**Логи и служебные файлы.** Вывод каждого процесса `ssh` пишется в `ssh-<id подключения>.log` в каталоге логов, предыдущий запуск — в `ssh-<id подключения>.1.log`;
оба файла входят в архив диагностики, паролей в них нет. Файлы `ssh-unsaved-….log` — временные туннели проверки подключения: каждый запуск «Проверить», в том числе для сохранённого подключения, открывает свой туннель под временным id `unsaved-<uuid>`; следующий запуск приложения эти файлы убирает.
В каталоге данных лежит `tunnels.json` (права 0600): PID запущенных процессов `ssh` и путь их лога. Если приложение завершилось аварийно, при следующем старте
оно завершает процессы из этого файла (только те, в командной строке которых есть имя их лога `ssh-<id>.log`, так что чужой процесс с тем же PID не пострадает); то же приложение делает при выходе.
На Windows это делается через PowerShell. Файл руками не правьте.

**Ограничение.** Защиты от второго экземпляра приложения нет: второй запуск при старте завершает процессы `ssh`, записанные в `tunnels.json`, в том числе туннели первого экземпляра.
Предупредите пользователей: приложение должно быть запущено один раз.

## Данные и логи
| | macOS | Windows | Linux |
|---|---|---|---|
| Данные | `~/Library/Application Support/io.github.vvnovg.glafira.postgres` | `%APPDATA%\io.github.vvnovg.glafira.postgres` | `~/.local/share/io.github.vvnovg.glafira.postgres` |
| Логи | `~/Library/Logs/io.github.vvnovg.glafira.postgres` | `%LOCALAPPDATA%\io.github.vvnovg.glafira.postgres\logs` | `~/.local/share/io.github.vvnovg.glafira.postgres/logs` |
| Пароли | Keychain, сервис `glafira-postgres` | Credential Manager | Secret Service |

В каталоге данных лежат `connections.json` (профили без паролей), `settings.json`, `tunnels.json` (процессы `ssh` открытых туннелей, см. «OpenSSH»), `actions.jsonl` (журнал действий, см. «Диагностика» → «Действия»; рядом при ротации появляется `actions.1.jsonl`; в записях `explainAnalyze` — начало текста запроса с литералами) и каталог `snapshots/<id подключения>/<узел>/<время>.json` (в имени каталога узла `%`, `:`, `[`, `]` и другие символы, недопустимые в именах файлов Windows, заменены на `%XX`: `db1:5432` → `db1%3A5432`; каталоги прежних сборок с двоеточием на macOS и Linux читаются как раньше) — снимки `pg_stat_statements`: все строки статистики с накопленными счётчиками и тексты до 1000 запросов (500 самых долгих и 500 самых частых; тексты нормализованы расширением, значения заменены на `$N`), имя файла — время снятия в UTC. На macOS и Linux каталоги снимков получают права 0700, файлы — 0600 (на Windows доступ определяют права каталога профиля). Снимки удаляются из приложения (панель «Снимки» инструмента «Запросы») и вместе с подключением; файл больше 128 МиБ приложение не читает, но показывает в списке и удаляет;
в каталоге логов, кроме логов приложения, — `ssh-<id подключения>.log` туннелей.

Файлы MCP-шлюза (раздел «LLM-ассистенты (MCP)») в каталоге данных: `mcp.json` — адрес сокета или канала, токен и pid работающего
сервера (0600; существует, только пока сервер работает: удаляется при выключении MCP и при выходе), `mcp.sock` — Unix-сокет
сервера на macOS и Linux (0600; при длинном пути каталога данных — `$XDG_RUNTIME_DIR/glafira-pg-mcp.sock` или временный каталог
пользователя), `mcp-audit.jsonl` и `mcp-audit.1.jsonl` — журнал MCP (0600, ротация при 5 МБ; SQL модели в нём — с литералами).
Раздел `mcp` файла `settings.json` хранит, включён ли сервер, и подтверждённых клиентов. Файлы MCP в диагностический архив не
входят.

Если пароль в хранилище не сохранён, используется `~/.pgpass` (Windows: `%APPDATA%\postgresql\pgpass.conf`) или файл из `PGPASSFILE`.
На Unix у такого файла должны быть права 0600 (`chmod 0600 ~/.pgpass`): как в libpq, файл, доступный группе или всем
(`mode & 0o077`), игнорируется, и в журнале остаётся только предупреждение.
Окно «О программе» показывает эти каталоги и собирает диагностический архив (версия, логи приложения и туннелей, профили без паролей; `actions.jsonl` и снимки в архив не входят);
приложение ничего не отправляет — архив пользователь прикладывает к обращению сам.
