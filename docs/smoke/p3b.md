# Смоук P3b «Советовать и сравнивать» — рекомендации, hypopg, снимки, расширения

Сборка: `pnpm tauri dev`. Стенд и нагрузка — как в `docs/smoke/p3a.md` (преамбула): `pg-perf` (`localhost:5471`, база `perf`; PostgreSQL 17,
`hypopg` 1.4.4, `pg_stat_kcache` 2.3.2, `pg_wait_sampling` 1.1 с `profile_queries = top`), основная нагрузка `heavy.sql` на час
(проверка старого `heavy.sql` и команда остановки — там же). Для шагов 11–14 нужны ещё основной стенд (`localhost:5460`, `localhost:5451` / `5452`,
`pg-lab` на `localhost:5470`) и матрица версий (`docker compose -f dev/docker-compose.yml --profile matrix up -d --no-recreate`, затем
`scripts/wait-matrix.sh`). Шаги идут по порядку: часть шагов опирается на данные предыдущих. Рекомендованные команды на стенде **не выполнять**
(особенно `VACUUM` и `CREATE INDEX`): они меняют стенд, и правила перестанут срабатывать.

Каталог данных приложения ниже — `$DATA`: на macOS `~/Library/Application Support/io.github.vvnovg.glafira.postgres`, на Linux
`~/.local/share/io.github.vvnovg.glafira.postgres`. Id подключения — поле `id` его записи в `$DATA/connections.json`.

Подключения (кнопка «+» над деревом, окружение `dev`, пароли — известные пароли стенда):
- `perf-diag` — `localhost:5471`, база `perf`, роль `glafira_diag` / `glafira-secret` (как в P3a); шаги 1–10;
- `single` — `localhost:5460`, база `postgres`, `glafira_diag` / `glafira-secret`; шаг 1;
- `lab` — `localhost:5470`, база `postgres` (там создан `pg_stat_statements`, расширений P3b нет), `glafira_diag` / `glafira-secret`; шаги 11–12;
- `repl` — вид «Список узлов», узлы `localhost:5451` и `localhost:5452` (primary и реплика PostgreSQL 16 без Patroni), база `orders`,
  `glafira_diag` / `glafira-secret`; шаг 13;
- `m13-diag` — `localhost:5513`, база `postgres`, `glafira_diag` / `glafira-secret` (как в P3a); шаг 14.

1. **Готовность и подсказки к расширениям.** Форма `perf-diag` → «Проверить»: «Расширение hypopg» — «Установлено, версия 1.4.4»,
   «Расширение pg_stat_kcache» — «Установлено, версия 2.3.2», «Расширение pg_wait_sampling» — «Установлено, версия 1.1»; подсказок под ними нет.
   В той же форме сменить базу на `postgres` (не сохраняя) → «Проверить»: у трёх пунктов «Доступно, но не создано», под каждым — что даёт
   расширение («Проверка гипотез индексов («Проверить гипотезу» в плане)», «CPU и диск по запросам в инструменте «Запросы»», «Точный профиль
   ожиданий запроса в карточке») и строка «Включение: …»: у hypopg — «только CREATE EXTENSION, без preload и перезапуска», у pg_stat_kcache —
   preload после pg_stat_statements, перезапуск, CREATE EXTENSION и EXECUTE на pg_stat_kcache(), у pg_wait_sampling — preload, перезапуск,
   CREATE EXTENSION, `profile_queries = top` (on на старых версиях), версия 1.1+ и EXECUTE. У `pgstattuple`, `pg_buffercache`, `pg_qualstats` —
   прежний текст «Расширенные проверки (индексы, bloat, ожидания) будут недоступны». Форма `single` → «Проверить»: те же три подсказки
   при состоянии «Не установлено на сервере».
2. **Рекомендации без выполнения.** Дерево → `perf-diag` → Диагностика → Запросы → карточка «SELECT count(*) FROM shop.orders WHERE status = $1»
   → «Получить план» (пробный план, `GENERIC_PLAN`): под сводкой плана блок «Рекомендации» со строкой «Выполните план с выполнением, чтобы
   проверить ещё 9 правил» (и «Советов нет», если других советов нет).
3. **Рекомендация с индексом.** В той же карточке значение `$1` — `disputed` → «План с выполнением»: строки о непроверенных правилах нет;
   рекомендация «Индекс по колонкам фильтра: shop.orders» с уровнем «Внимание», доказательством «Seq Scan прочитал … строк, вернул …»,
   командой `CREATE INDEX CONCURRENTLY ON "shop"."orders" ("status");` и строкой «Приложение эту команду не выполняет: скопируйте и выполните
   сами»; «Копировать команду» кладёт команду в буфер (вставить в редактор). Ниже — «Эффект» и «Риски». «Показать узел» выбирает Parallel Seq
   Scan on shop.orders, раскрывает его родителей, у строки — полоса и метка «рекомендация»; клик по другой строке дерева снимает отметку.
4. **hypopg.** Перед шагом: `docker exec gp-pg-perf psql -U postgres -d perf -XAtc "SELECT count(*) FROM pg_indexes WHERE schemaname = 'shop'"`.
   «Проверить гипотезу» у рекомендации шага 3 → окно «Проверка гипотезы»: строка о том, что виртуальный индекс живёт только в сессии проверки,
   команда `CREATE INDEX ON "shop"."orders" ("status")` (без `CONCURRENTLY`), «Стоимость: A → B» с B меньше A, «Индекс использован»,
   «оценка размера …», под ним дерево «План с виртуальным индексом» с индексным сканом по индексу вида `<число>btree_orders_status`. Фокус — на
   «Закрыть», Tab не уходит из окна, Escape закрывает окно. Тот же `count(*)` в psql не изменился (реального индекса нет). Поменять значение
   `$1` в форме на `new` и, не перезапуская план, снова «Проверить гипотезу» — проверка идёт по значению показанного запуска (`disputed`),
   результат тот же.
5. **Остальные правила.** Консоль EXPLAIN (из дерева) на `perf-diag`, база `perf`; каждый запрос — «План с выполнением» (ярус «чтение»):
   - `SELECT count(*) FROM shop.audit WHERE order_id = 1 AND actor = 'ops'` → «Составной индекс для shop.audit», команда
     `CREATE INDEX CONCURRENTLY ON "shop"."audit" ("order_id", "actor");`, «Проверить гипотезу» есть;
   - `SELECT o.id, a.note FROM shop.audit a JOIN shop.orders o ON o.id = a.order_id WHERE a.actor = 'app' AND a.order_id = 1` →
     «Оценка строк занижена в … раз: shop.audit», команда начинается с `ANALYZE "shop"."audit";`, дальше `ALTER TABLE … SET STATISTICS 1000`;
   - `SELECT customer_id, sum(total) FROM shop.orders GROUP BY customer_id ORDER BY 2 DESC` → «Сортировка уходит на диск» (и/или «Хеш уходит
     на диск»), команда `SET work_mem = '…kB';`;
   - `SELECT * FROM shop.orders ORDER BY total DESC LIMIT 10` → «Индекс под ORDER BY … LIMIT: shop.orders», команда
     `CREATE INDEX CONCURRENTLY ON "shop"."orders" ("total");`; «Показать узел» отмечает и Sort, и Limit;
   - `SELECT customer_id FROM shop.balances WHERE customer_id > 150000 ORDER BY customer_id LIMIT 20000` → «VACUUM shop.balances: карта
     видимости устарела», команда `VACUUM "shop"."balances";` (не выполнять);
   - `SELECT count(*) FROM shop.events WHERE happened_at::date = date '2026-03-05'` → «Отсечение партиций не сработало» (без команды) и одна
     сгруппированная рекомендация «Индекс по колонкам фильтра в партициях (24): shop.events_… и другие» вместо 24 отдельных: команда — 24 строки
     `CREATE INDEX CONCURRENTLY ON "shop"."events_…" (<columns>);` (приведение `::date` колонку не даёт), под ней «Перед выполнением замените
     <…> своими значениями», кнопки «Проверить гипотезу» нет; «Показать узел» отмечает все 24 скана партиций;
   - `SELECT count(*) FROM shop.order_items` → «Воркеров меньше, чем запланировано», команда `SHOW max_parallel_workers;` и
     `SHOW max_worker_processes;` двумя строками;
   - `SELECT oi.id FROM shop.order_items oi WHERE oi.product_id BETWEEN 100 AND 110 AND oi.price > (SELECT avg(x.price) FROM shop.order_items x WHERE x.order_id = oi.order_id)`
     → «Подзапрос выполняется на каждую строку», без команды;
   - `SELECT sum(total * 1.07 + 3) FROM shop.orders WHERE id BETWEEN 1 AND 30000` → «JIT дольше самого запроса», команда `SET jit = off;`
     (на стенде JIT около 50 из 63 мс; под тяжёлой нагрузкой доля может упасть ниже половины — тогда повторить запуск).
   Правило «Nested Loop над Seq Scan» на стенде не воспроизводится (подходящего запроса в `heavy.sql` нет) — его проверяют unit-тесты
   `pg-advisor` (`nested_loop_seq`).
6. **Без выполнения в консоли.** `SELECT * FROM shop.orders ORDER BY total DESC LIMIT 10` → «План»: «Индекс под ORDER BY … LIMIT» есть (правило
   работает по оценкам) и строка «Выполните план с выполнением, чтобы проверить ещё 9 правил». Вкладка «Вставить план»: вставить вывод
   `docker exec gp-pg-perf psql -U postgres -d perf -c "EXPLAIN (ANALYZE) SELECT count(*) FROM shop.orders WHERE status = 'disputed'"` →
   «Разобрать» — дерево без блока «Рекомендации».
7. **Снимки.** Инструмент «Запросы» на `perf-diag` → «Снимки»: панель с подсказкой «Снимки pg_stat_statements хранятся только на этом компьютере»
   и «Снимков пока нет». «Сделать снимок» → строка со временем, узлом, числом строк и размером. Нажать «Сделать снимок» дважды подряд в одну
   секунду — ошибка «Снимок этого узла уже сделан в эту секунду: подождите секунду и повторите» (если клики попали в разные секунды, появятся
   два снимка — это не отказ). Через две-три минуты под нагрузкой — ещё снимок. Файлы:
   `ls -la "$DATA/snapshots/<id perf-diag>"` и `ls -la "$DATA/snapshots/<id perf-diag>/<узел>/"` — каталоги `drwx------`, файлы
   `-rw-------` с именами вида `2026-11-01T10-15-00.json` (время UTC). Отметить первый и последний снимок (порядок отметки любой) → «Сравнить»:
   заголовок «Сравнение A → B», списки «Деградировали», «Ускорились», «Новые», «Исчезли» (пустые списки допустимы; «Новые» обычно не пуст
   из-за собственных запросов), строка «Вызовов: … → …», собственные запросы Глафиры приглушены и с меткой «Глафира». Отметить третий снимок —
   отметка с самого раннего из отмеченных снимается.
8. **Топ между снимками.** После сравнения — «Топ между снимками»: панель закрывается, режим — «Между снимками», над таблицей «Между снимками узла …:
   A → B» и кнопка «Выйти из режима снимков», значок покрытия «2 мин между снимками» (или сколько прошло), заголовки «Stddev» и «Max»
   неактивны, колонка «CPU» сортируется (оба снимка с `pg_stat_kcache`). Поиск `shop.orders` оставляет строки с этим текстом. «Выйти из режима
   снимков» → «С момента сброса».
9. **Сброс между снимками.** Сделать снимок, затем `docker exec gp-pg-perf psql -U postgres -d perf -c "SELECT pg_stat_statements_reset()"`,
   подождать минуту, сделать ещё снимок. Сравнить эти два: строка «Между снимками статистика сбрасывалась: надёжны только новые и исчезнувшие».
   «Топ между снимками»: под находками «Сравнение: статистика сбрасывалась между снимками», покрытие — около минуты (от сброса до второго
   снимка), а не время между снимками.
10. **Удаление, повреждённый файл, без подключения.** «Удалить» у снимка → «Удалить снимок от …?» → «Удалить снимок»: строка исчезает, файла
    в каталоге нет; Escape в подтверждении отменяет удаление. Войти в «Топ между снимками» и удалить один из снимков пары — таблица выходит из
    режима «Между снимками». Положить повреждённый файл:
    `printf '{' > "$DATA/snapshots/<id perf-diag>/<узел>/2026-01-01T00-00-00.json"` → закрыть и открыть «Снимки»: строка с меткой «Файл
    повреждён», строк — «—», флажок неактивен, «Удалить» работает. Затем «Отключиться» у подключения `perf-diag`: инструмент
    «Запросы» показывает, что подключение закрыто, строку «Без подключения доступны только снимки: выберите два и откройте топ между ними» и
    панель снимков; «Сделать снимок» неактивна; два снимка → «Сравнить» → «Топ между снимками» строит таблицу, в списке режимов «С момента
    сброса» и окна неактивны. Открыть подключение снова. «О программе» → «Собрать диагностику»: `unzip -l <архив>` — файлов `snapshots/`
    в нём нет. Создать временное подключение (копия `perf-diag`), сделать в нём снимок, удалить подключение — каталога
    `$DATA/snapshots/<id временного>` больше нет.
11. **pg_stat_kcache.** `perf-diag`, «Запросы», «С момента сброса»: после колонки «I/O» колонки «CPU» и «Чтение с диска» заполнены у строк
    нагрузки; клик по «CPU» сортирует по убыванию. Карточка `SELECT count(*) FROM shop.orders WHERE status = $1`: метрики «CPU (user + sys)» и
    «Диск прочитано / записано» в обоих столбцах; «Скопировать для LLM» — в статистике строки CPU и диска. Подключение `lab`: колонок «CPU» и
    «Чтение с диска» в таблице нет, в карточке нет метрик CPU и диска.
12. **pg_wait_sampling.** Карточка из шага 11 на `perf-diag` (вкладку «Профиль ожиданий» в этом сеансе не открывать): блок «Ожидания» с
    подписью «Профиль pg_wait_sampling с момента его сброса» и таблицей событий (CPU, IO:… и т. п.) сразу, без подсказки открыть «Профиль
    ожиданий». На `lab` карточка любого запроса: подсказка открыть «Профиль ожиданий»; открыть его, вернуться, «Обновить» — таблица с подписью
    «По сэмплам «Сессий» за …» (охват — время работы сэмплера, не больше 1 ч). Выключенный `profile_queries` на стенде не воспроизводится
    без смены конфигурации сервера (параметр читает сборщик расширения) — его проверяют unit-тесты (`wait_sampling_plan_follows_the_setting_and_the_catalog`).
13. **hypopg на реплике (проверить).** Подключение `repl`, консоль EXPLAIN, узел — реплика `localhost:5452`, база `orders`:
    `SELECT * FROM shop.orders ORDER BY total DESC LIMIT 5` → «План» → «Индекс под ORDER BY … LIMIT: shop.orders» → «Проверить гипотезу»:
    окно с красной плашкой «hypopg не установлен в этой базе» и без дерева (на стенде `hypopg` нет ни на primary, ни на реплике) — проверка
    ушла на узел плана и отказала понятным сообщением, а не ошибкой сервера. **Работа `hypopg` на hot standby стендом не проверяется**: если
    доступна реплика с установленным пакетом `hypopg` (и `CREATE EXTENSION hypopg` на primary), повторить шаг на ней и записать итог в отчёт
    смоука: ожидается «Стоимость: A → B», «Индекс использован» и пустой `SELECT * FROM hypopg_list_indexes` после проверки; любую ошибку
    (например, отказ создать гипотезу в восстановлении) — дословно. Там же, в «Запросах» `repl`: сделать снимок на primary, переключить узел
    в шапке на реплику, сделать снимок; отметить по одному снимку каждого узла — строка «Снимки с разных узлов: выберите два снимка одного узла»,
    «Сравнить» неактивна.
14. **Без расширений и pgss 1.8.** `m13-diag` (PostgreSQL 13, `pg_stat_statements` 1.8): «Запросы» — колонок «CPU» и «Чтение с диска» нет;
    «Снимки» → два снимка с промежутком в минуту → «Сравнить» и «Топ между снимками» работают (времени сброса у pgss 1.8 нет, пометки о
    сбросе нет); карточка — ожидания по сэмплам «Сессий», как в P3a. Консоль на `m13-diag`: `SELECT * FROM pg_class ORDER BY relpages DESC LIMIT 1`
    → «План» — блок «Рекомендации» есть (без выполнения — строка о 9 непроверенных правилах).
15. **Справка.** Глава «Запросы» (F1 на вкладке «Запросы») содержит разделы «Рекомендации по плану», «Снимки» и «Расширения»; ссылки на них из
    вступления и раздела «Топ запросов» открывают нужный раздел.
